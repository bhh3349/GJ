# 0043 废号池：账号终态与强绑定删 key

- 状态：接受（v1.19.0，2026-11-03）
- 决策者：业主（拍板）/ 管家（实现）
- 相关：ADR-0041（透支锁存）、ADR-0018（供应商账号面）、ADR-0016（删上游子树）、
  契约 §21（新增）、§15.2（`DELETE` 语义变更）、§20.6（级联腿复用）

## 背景

业主在使用中提出三条：

1. 「加个废号池，优先判断套餐余额，如果套餐余额低于 1，余额低于 1 直接把该账号进入废号池，该账号的 key 也全部停用。」
2. 「过期的账号余额低于 1，不管套餐是否还有余额该账号一律进入废号池。」
3. 「现在 key 和账号是强绑定了吧？账号删除 key 也跟着删除，进入废号池，key 也直接停用。」

现状：§20 已有「透支锁存」（`depleted_at/reason`），判据是**余额 < 10 分**或**套餐余量 = 0**，
账号级会级联名下 key 的锁存，但**绝不碰 `enabled`**（ADR-0041 纪律 2：混在一起会被批量启用绕过）。
管理面上因此只能看到"被锁"的标记，看不到"停用"的结果；而业主要的是一个**能看见、能筛选、
能人工解除的名单** —— 且名字不叫"透支"，叫"废号"。

同时 §15.2 的 `DELETE /api/supplier-accounts/:id?force=true` 是**只解绑不删 key**：
理由写在原注释里（"账号删了 key 仍能转发，删了会打穿流量"）。

## 决策

### 1. 废号池是**独立状态**，不是 `depleted` 的别名

新增 `supplier_accounts.scrapped_at` / `scrap_reason` 两列（纯加列、`SCHEMA_VERSION` 不递增）。
不复用 `depleted_at` 的理由不是洁癖，是**两个判据的语义本来就不同**：

| | `depleted`（§20） | `scrapped`（§21） |
|---|---|---|
| 问的问题 | 这钱包付不起账吗 | 这个号还有残值吗 |
| 阈值 | 余额 < 10 分 | 余额 < 100 分 **且** 套餐余量 < 1 |
| 动作 | 只锁存 | 锁存 **+ `enabled = 0`** |
| 解除 | `undeplete` | `unscrap` |

合成一个会让"余额 0.5 元、套餐还剩 800 万"的号被 §20 的宽阈值误伤 —— 那不是业主想停的号。

### 2. 判据是「且」不是「或」—— 业主第三句是判据

「过期的账号**不管套餐是否还有余额**」这句话只有在一个前提下才有信息量：套餐余量**本来能救**
这个号，而过期把它清零了。若判据是"任一耗尽即废"，这句完全冗余（余额不足本来就已单独判废）。
反过来读，业务上也对：**一个套餐还剩 800 万、只是余额不足 1 元的号，现在还能干活** ——
停掉等于白扔那 800 万。

于是：`有效套餐余量 < 1 且 余额 < 1 元`；其中**过期把套餐余量视为 0**。
`plan_expired` 与 `plan_exhausted` 两个 reason 回答的正是"套餐那一项怎么见底的"。

### 3. 进池三件事，落库腿与判据分离

- 判据唯一实现：`src/db/scrap.ts`（纯函数，14 条单测逐条钉住）；
- 落库唯一实现：`src/db/repo/scrap-latch.ts`；
- 判定腿两个：`refresh` 与 `keys/sync`（挂既有动作，**不设独立定时器** —— 项目没有后台调度器，
  引入一个只为一个判据服务的循环，它的失败模式是"静默停摆且没人发现"）。

进池时三步：账号两列置位 → 名下 key 级联锁存（复用 §20.6 的 `latchAccountCascade`）→
名下 key `enabled = 0`。

**②③ 都做的理由**：只做 ③，一次批量 `enable` 就把废池的 key 全放回池子（批量启用只写 `enabled`）；
只做 ②，管理面显示"启用中"而它实际已被排除，操作员看不懂为什么没流量。
这与 ADR-0041 纪律 2（"绝不碰 enabled"）不冲突——那条约束的是**透支锁存**，本条是**业主要求的停用**，
两者都是"系统按事实打标"，区别在后果强度。

### 4. 删账号 ⇒ 删 key（推翻 §15.2 旧取向）

`force=true` 时软删名下全部池内 key（`enabled=0` + `deleted_at`，逐把发 `'delete'`）。

原取向的论据是"账号删了 key 仍可转发"，这在**技术上**成立，但它假设账号型 key 离开账号还有
独立价值 —— 事实相反：额度、套餐、余额全在账号那边，key 只是个凭据载体。账号没了，这把 key
打出去就是 402/404。**留着比删掉更坏**：网关会一直选它、一直失败，而池子里看起来还有候选。

代价写在明处：删除账号会让网关少一批 key（客户端可能开始报 `NO_AVAILABLE_KEY`）。
所以 `force=false` 那道 409 闸必须保留 —— 它把"你会掉流量"变成一次显式确认。

### 5. 出池是人工的，且 key 全量恢复

`POST /:id/unscrap` 不要 `revision`（与 `undeplete` 同形：解除自动标记，没有可覆盖的编辑冲突）。
恢复范围是**全量**（`enabled = 1` + 清锁），比 §20.5 的"只清 `'account'` 那批"更宽 ——
因为进池时动了 `enabled`，而这一列没有"谁停的"可回放，能还原的只有整体还原。
一把**自己**余额不足的 key 会被下一轮刷新重新锁上（判据没变），那是正确行为。

## 后果

- ✅ 业主要的"废号池"在管理面可见、可筛（`?scrapped=`）、可人工解除。
- ✅ 进池即停用，双保险（锁存 + enabled），批量启用绕不过。
- ✅ 删账号不再留孤儿 key。
- ⚠ 判据只在 refresh / keys/sync 时跑：**两次刷新之间**额度刚烧干的号仍会被选到一次，
  那是 §20 已有边界①的同款（`spentTokens` 只在内存）。运维口径：自动余额同步开着就是分钟级。
- ⚠ 出池后若判据仍成立会再次进池 —— 这不是 bug，是粘性只管"不自动清"的直接推论。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 把判据并进 §20 `depleted`（复用两列） | 阈值语义不同（10 分 vs 100 分且要求套餐见底），合并会让 §20 的七条判定腿全部漂移；且 §20 明确"绝不碰 enabled"，业主这次要的正是碰 |
| 用一个 `status='scrapped'` 枚举值 | `status` 说的是**会话/登录健康**（`active`/`login_failed`/`session_expired`/`unknown`），把一个"资金终态"塞进去会让所有读 `status` 的地方（含前端筛选、健康统计）语义污染 |
| 进池时物理删 key | `usage_logs.key_id` 还指着历史行（同 `deleteKey` 软删的理由） |
| 出池后自动恢复 key | 与"粘性 + 人工解除"的口径冲突：操作员点一次解除就期待看到结果，自动恢复会让他分不清"是解除生效了还是又进池了" |
