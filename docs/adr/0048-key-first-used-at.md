# ADR-0048：key 的「首次调用时刻」= 一次性钉住的使用态（不重算、不算配置）

- 状态：已接受（2026-11-03）
- 相关：ADR-0003（未知 ≠ 0）、ADR-0010（`key_runtime` 与 `upstream_keys` 分表 / 运行态滞后 ≤1s）、
  ADR-0014（`usage_logs` 是调用流水的唯一落点）、ADR-0036（用量攒批异步落库）
- 契约：v1.23.0（§3 Key 对象新增 `firstUsedAt`；§15.3 变更条）

## 触发

业主要求：「在 Key 管理增加一个功能，每个 key 加一个首次调用功能。」拍板口径：**两个都要，分两批**
—— 第一批 = 首次调用**时间列**（本 ADR），第二批 = 「试调一次」按钮（另行成文，本版不含）。

"每把 key 第一次被调用是什么时候"这个问题，现成的数据源看起来有两个：`usage_logs` 聚合，
和 key 行自己存一列。**选错的那个会在半年后变成最难识别的假数据**，所以要写下判据。

## 决策

### 1. 落 `upstream_keys.first_used_at`（裸 TEXT，可空），不落 `key_runtime`

- `key_runtime`（ADR-0010）是网关进程的**运行态镜像**，重启后归零、按 1s 节拍重写，
  管理端只读且滞后 ≤1s —— 「首次调用」是**跨重启的历史事实**，放进一张会被重写的表里口径就错了。
- `upstream_keys` 一行一把 key、生命周期与 key 同寿，且 `GET /api/keys` 的 DTO 本来就出自这张表。
- 可空、无默认：老行 `NULL` = 从未调用，与加列前逐字相同。

### 2. 写入方 = 用量攒批的 flush 事务（热路径纪律不变）

`src/wiring/usage-sink.ts` 的 `flush()` 事务里，写完这批 `usage_logs` 后，
对批内出现过的每把 key 调 `markKeyFirstUsed(db, keyId, ts)`：

```sql
UPDATE upstream_keys SET first_used_at = ? WHERE id = ? AND first_used_at IS NULL
```

- **同一批多条取最早**（`Map<keyId, minTs>`），同 key 一次 UPDATE；
- **只写一次**：`WHERE first_used_at IS NULL` —— 语义是 `MIN(ts)`，更晚的时刻永不覆盖；
- `keyId = null`（引擎全失败终态，"没有那把 key 可言"）跳过；key 行已不存在 ⇒ 0 行受影响，不抛；
- 这一步**不在 `/v1/*` 请求线程上**（AGENTS.md §5「热路径零同步 DB 写」不变）：
  `record()` 仍只入队，写入只发生在批量 flush 的那一个事务里。

### 3. **不递增 `revision`、不写 `change_log`**

§5 的通则「管理端改 key 必须递增 `revision`」是为了让网关重载**选路配置**。
`first_used_at` 是**使用态**、不参与选路，网关不需要为它热一轮缓存 ——
所以这里是显式登记的例外（用例钉死：补写后 `revision` 与 `updated_at` 都不动，`change_log` 零新增）。

### 4. 回填只在"这次刚补列"那一拍做，之后永不重算

`migrate()` 里 `if (!hasColumn(...))` 分支：`ALTER ADD COLUMN` + 一次性
`UPDATE ... = (SELECT MIN(ts) FROM usage_logs WHERE key_id = ...)`。

**为什么不能每次启动重扫**：`usage_logs` 会被保留期裁掉（ADR-0036 / §6 保留期）。
重扫得到的是"现存最早一条"，而裁剪会让这个值**越算越晚** —— 那是"半年前调过的 key 显示成上周调过"
的假数据形状，且只在时间过去后才暴露。一次性钉住 + 之后只由写路径增量补 NULL 行，才不会漂。

**裁光了的存量 key**：回填不到 ⇒ `NULL` ⇒ 前端渲染「未调用」。**宁可留空，不编时刻**
（与 ADR-0003「未知 ≠ 0」、§3 `balance`/`tokenPlan` 的 null 纪律同族）。

### 5. 出口形状

`GET /api/keys` 列表与 `GET /api/keys/:id` 详情的 Key 对象新增 `firstUsedAt: string | null`（ISO8601 UTC）。
纯非破坏加字段：零新端点、零枚举、零改名、`PATCH` 不收该字段。

## 备选方案

- **A. 不落列，每次从 `usage_logs` 聚合 `MIN(ts)`** —— 否决：保留期裁剪后得到的是"现存最早"，
  值会随时间漂移；且列表页每页 N 把 key 都要多打一次聚合查询。
- **B. 落 `key_runtime`**（看起来更像"运行态"）—— 否决：那张表按 §1 会被重写、重启归零，
  且 ADR-0010 已把它定义为"滞后 ≤1s 的镜像"，把历史事实塞进镜像会模糊两张表的边界。
- **C. 由 `engine.ts` 在选中 key 时同步写一行** —— 否决：直接违反 §5 热路径纪律（TTFB 被写锁吃掉）。
- **D. 补写时递增 `revision`** —— 否决：让网关为不参与选路的字段白热一轮配置同步，
  且会把 `revision` 这个"管理员改配置的证据"污染成高频噪声。

## 后果

- 升级即回填一次：存量库的"首次调用"在部署当次就有值（日志还在的话）；日志已裁光的回 `null`。
- 部署后**新**的第一次调用：随下一批用量落库出现（默认 500ms 节拍），管理端看到的延迟 = flush 节拍，
  不是 1s 镜像那一档。
- 前端渲染纪律：`null` → 「未调用」，不许 `—` / `0` / 空串（业主的表格偏好：核心数据在主页直接可见）。
- 第二批「试调一次」会新增一个真打上游的端点，届时再开 ADR；本列只读，不受它影响。
