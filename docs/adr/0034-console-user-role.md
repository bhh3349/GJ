# ADR-0034：消费面用户与角色授面 —— 「普通用户前端」是什么、不是什么

- 状态：**已接受（2026-10-17，Bo 指示「普通用户只能通过用户前端获取 url 和 key，能看自己的用量统计，还有个模型列表」）**
- 关联：契约 §0.5（授面规则）、§1（登录响应新增 `role`）、新增 **§19 消费面 `/api/console/*`**、
  `docs/adr/0034` 前身是提案 `docs/proposals/1panel-五功能-可增加性报告-v1.md` §1.4 的 **B 档**
- 车道：`src/db/`（加列 + repo）+ `src/api/`（登录分流 + 新前缀路由 + 闸门授面）+ `web/`（工作区）。
  **`src/gateway/` 零改动** —— 本 ADR 不碰路由选路、不碰限流、不碰 KeyPool
- 触发：Bo 要的是 1panel 报告 §1 里那个"用户中心 `/console`"的**真等价物**（B 档），
  不是 A 档（纯前端视图）。两者的判据差别在 ADR 末尾

## 背景：一个"看起来只改前端"的需求

Bo 的需求是三件事：**拿 URL 和 key、看自己的用量、看模型列表**。
照 1panel 报告 §1.4 的分档，最省的做法是 A 档 —— 前端加一个 `/console` 路由，
复用现有单管理员会话。**A 档做不出 Bo 要的东西**，理由不在前端：

1. **没有"普通用户"这个账号种类。** `admin_users` 只有 `username / password_hash`
   （`src/db/schema.ts:27`），没有 `role` 列。后端只有一条登录路径，
   `POST /api/auth/login` 校验的就是管理员口令。所以"普通用户登录"这件事**在服务端不存在**。
2. **`/api/*` 全量鉴权且只有一个身份。** `isPublic()`（`src/api/app.ts:118`）只豁免
   `POST /api/auth/login`；过了闸门的 `req.auth` 只有一个 `{username, expiresAt}`。
   一个普通用户即使能登进前端，他打的每一个 `/api/*` 请求都会拿到**管理员能看到的一切**
   —— 上游 Base URL、上游 key 掩码、账号池、审计日志。这不是"权限小了看不全"，
   是**根本没有权限边界**。
3. **`usage_logs` 没有 user 维度。** 它按 `group_id` 记（另有 `key_id`）。
   "我的用量"只能归到**组**。所以"自己的"必须落到"我所属的组"。

于是"加个用户前端"实际是：**引入第二种身份，并让服务端按身份授面**。
这是一笔后端改动，`web/` 只是它的出口。

## 决策

### 1. 新身份 = `role` 列，加在 `admin_users` 上，而不是新表

```sql
ALTER TABLE admin_users ADD COLUMN role TEXT NOT NULL DEFAULT 'admin';
```

`role ∈ {admin, user}`，**纯加列，`SCHEMA_VERSION` 仍为 2**（迁移判据是"列在不在"，
同 v1.1.1 / v1.4.x / v1.14.0 那几批）。老库里唯一的账号拿 `DEFAULT 'admin'` ——
这个默认值**不是随手填的**：老库里的账号本来就是管理员，填 `user` 会让升级后
**现有管理员失去管理面**，而那是一个"升级即锁死自己"的故障形状。

**为什么不新开一张 `users` 表**：会话表 `sessions` 已经按 `username` 关联
（`src/api/auth.ts` 的 `requireSession` → `touchSession`）。新开表就要在
登录、会话、闸门三处都处理"这个 username 是人还是管理员"的归并问题，
而 `role` 一列 + 一个判据函数就够。多一张表的成本是**永久**的。

### 2. 授面靠前缀，不靠"前端别调"

| 前缀 | 谁能进 |
|---|---|
| `/api/**`（既有，**一字不改**） | 仅 `role=admin` |
| `/api/console/**`（新增） | `admin` 与 `user` 都能进，但**每条路由自己只回本组数据** |

`src/api/app.ts` 的闸门在既有 `requireSession` 之后插一个判定：
`role=user` 且路径不以 `/api/console/` 开头 → `403 FORBIDDEN`。

**上表有一个精确到路径的例外**（v1.15.1 订正，见契约 v1.15.1 变更记录与
下面 §3 的"接入 URL 不新开端点"）：`GET /api/access-info`（§18）放行给
`role=user`。理由不是"它无害"（虽然确实无害），而是 §19.5 的接入 URL 公式
要用它的 `publicHost` / `portGateway` —— 那是这三个字段的**唯一来源**。
契约 v1.15.0 的 §19.1 表把它写成不放行，与同一版的 §19.5 合起来是一个
**不可能满足的公式**；按本 ADR 影响面表的裁定订正为放行。
例外是"这一个字面路径"，不是"再开一个前缀" —— 写方法打它仍 403。

**上表漏了一行，v1.15.2 补（契约 v1.15.2 / 本 ADR 遗留 5）**：
`WS /api/stats/live`（§7）。那条路径是 `app.ts` 鉴权闸门的**唯一例外**
（升级请求回不了 HTTP 401，否则浏览器只报 1006，前端分不清"会话过期"与
"服务不可用"），而例外的代价是**闸门的 `role` 判定也一起被跳过**。
于是 v1.15.0 交付的授面在 REST 侧完整、在 WS 侧有一格是空的：
实测 `role=user` 用自己的会话即可握手成功并持续收到 `metrics` 帧 ——
`qps` / `successRate` / `balanceGlobal`（**全站**余额）/ `egress_pool`
全是本 ADR §2 明写"不给普通用户"的东西（同一个身份打 `/api/stats/overview`
会 403）。**同一份数据两条通道、两种授面结果**，这就是漏判的形状。
补齐方式不是缩小闸门例外（那个例外本身是对的，1006 与 4401 的分辨只能这么来），
而是在通道自己的握手期判定里**补上同一个判据**（`role`），拒绝码 `4401`。
用例与变异见 `src/api/routes/live.spec.ts`「role=user 开实时通道」。

**为什么不是"`/api/*` 全部放行、靠前端不展示"**：那是把安全边界交给浏览器。
`/api/upstreams` 回的是上游 Base URL 与 key 掩码，`/api/supplier-accounts` 回的是
**真实账号池**。一个普通用户在 DevTools 里 `fetch('/api/upstreams')` 就能拿到全部 ——
这不是理论风险，是 A 档实现**必然**的结果。所以闸门必须在服务端，
且必须是**拒绝**而不是**隐藏**。

**为什么消费面是 `/api/console/**` 而不是复用 `/api/groups/:id` 之类**：
复用意味着"普通用户和管理员打同一条路由，路由里再判身份"。
那种写法的失败形状是**漏判**：每条路由都要记得判一次，加新路由时忘了判就全漏。
而前缀判定在闸门里判一次，**新增路由不可能绕过它**（这条与
`inReadonlyScope()` 对 `READONLY_TOKEN` 的做法是同一条纪律，见 `app.ts:130` 的头注）。

### 3. 消费面只读，且**不含 key 签发**

**〔v1.15.9 已被 ADR-0038 订正 —— 见下面这条"订正"块。本决策的最后一条纪律
（明文没有取回路径）原样成立且更强；被拆掉的是"因此不含签发端点"那一步推论。〕**

> **订正（v1.15.9 / ADR-0038 决策 1）**：本条表格下方的「为什么不含 key 签发」被推翻。
> 推翻它的不是"A 档也能做"，而是**理由的性质**：这里给的理由（"组内任一成员可无限增发"）
> 是一个**风险论证**，风险可以**用护栏消掉**（`KEY_SELF_ISSUE_LIMIT = 10` 把数 + `422`
> + 前后端同一个数字），代价比"整组 key 生命周期卡在一个管理员手上、每次经手过一次明文"
> 更低。所以 v1.15.9 下放了签发 / 改名 / 吊销三条写路由（§19.3b）。
> **被推翻的只有这一半**：表格里「不回什么」那一列（**明文**）一个字都没动，
> 而且 ADR-0038 把它写得更强了 —— 自助签发**继承了**"明文只在 201 里出现一次"，
> 同样没有"再取回"的路径，同样没有"显示明文"这个按钮。

`/api/console/*` 的读端点全是 `GET`：

| 端点 | 回什么 | 不回什么 |
|---|---|---|
| `GET /api/console/session` | `{username, role, groupId, expiresAt}` | — |
| `GET /api/console/keys` | 本组 key 的**掩码**列表（复用 §4 `GatewayKeyDto`） | **明文**（明文只在签发那一次存在，没有"再取回"的路径） |
| `GET /api/console/usage` | 本组用量时间轴（复用 §6 `GET /api/stats/usage` 的响应形状） | 别组的任何一行 |
| `GET /api/console/models` | 站内已启用模型（复用 §5 `ModelDto`） | 上游 Base URL / key 掩码 / 余额 |
| `GET /api/console/quota`（**v1.15.9 新增**，§19.3c） | 本组额度（§4 `GroupDto` 的逐字透传） | 别组的任何一格 |

**接入 URL 不新开端点**：`GET /api/access-info`（§18）已经在回端口与
`publicHost`，但它现在只有管理员能看。给 `role=user` 放行这一个**既有只读端点**
即可 —— 新开一个 `/api/console/access-info` 就等于有**两份口径**，
而这两份将来一定漂移（这正是 ADR-0033 决策 2 禁第二个字面量的同一条理由，
只是这里禁的是第二份端点）。

**为什么不含 key 签发（`POST`）**：网关 key 明文只存在于
`POST /api/groups/:id/keys` 的 201 响应体里（§4 铁律，ADR-0006）。
把它下放给 `role=user`，等于**组内任一成员可以无限增发 key** ——
而按 Bo 选的"多个用户可共享同组"，那些新 key 消耗的是**同一个配额池**。
这是一个真实的新攻击面（恶意成员把组配额烧光、或发一堆 key 分发出去），
要单独一条 ADR + 判据。**本 ADR 明确不做**，留给后续一笔。
用户端"获取 key"的语义因此是：**看到自己是哪几把（掩码）+ 从管理员那里拿明文一次**。

> **〔v1.15.9 结清〕** 上段里"要单独一条 ADR + 判据"的另一笔就是 **ADR-0038**，判据见契约 §19.3b。
> "无限增发"这个攻击面确实被护栏消掉了（`KEY_SELF_ISSUE_LIMIT` 把数），而剩下的
> "同组成员可吊销同组 key"被 ADR-0038 遗留 1 **刻意保留** —— 组在这个产品里本来就是
> 互相信任的配额池。**"用户端获取 key 的语义"那句被改口**：现在是"**自己签一把**（明文当场抄走）
> + 看掩码 + 从管理员那里懂得组里都有谁在发"。`label` 这一列（建表起就在、从来没人写过）
> 让"这是谁要的那一把"第一次有了落点。

### 4. 登录后按角色分流（前端）

`POST /api/auth/login` 的响应体**新增 `role` 字段**（纯新增可选字段，老前端不读也不破）。
前端路由守卫据此分流：`role=admin` → `/admin`，`role=user` → `/console`。

**为什么 `role` 进登录响应而不是让前端再调一次 session**：登录那一刻就要决定
跳去哪，多一次往返只会让"跳错地方"多一个时序窗口。而 `role` 不是秘密 ——
它本来就是用户自己的属性，回给它不扩大任何暴露面。

**`/admin` 与 `/console` 是同一份前端产物里的两套路由**，不是一个新站点。
域名 / 端口 / 反代都不变：管理面和消费面**同源**（都在 4001），
`SameSite=Lax` 的会话 cookie 两边都能带。这避免了"两个域 + 一个 cookie"的
CSRF 与 `SameSite=None` 那一整类问题。

### 5. `user` 能且只能看到自己所属的组

`users` 侧加 `group_id TEXT REFERENCES groups(id)`（**可空**，见下）。
`/api/console/keys` 与 `/api/console/usage` 的所有查询都带 `WHERE group_id = ?`，
参数来自**会话对应的 user 行**，**绝不接受请求体 / query 里的 groupId**。

**为什么 `group_id` 可空**：`NULL` = 这个账号还没有归属组。它的用户端体验是
"登录成功但三个列表全空 + 一句「你还没有被分配到组」"，
而不是"打谁都是 500"。一个刚建好还没分配的用户，不该因为一次误登录就看到服务端错误。

**为什么不让请求带 groupId**：那就是把"我能看哪个组"变成客户端参数。
判据必须来自服务端的会话 → user 行，这是唯一客户端改不了的地方。

## 影响面

| 面 | 变更 |
|---|---|
| `/api/*`（管理面） | **零端点变更、零字段变更**。`/api/access-info` 的**响应体不变**，只是多一种身份能读它 |
| `/api/console/*` | **新增 3 个只读端点**（§19） |
| `POST /api/auth/login` | 响应体**新增** `role` 字段（纯新增，老客户端不读即无感） |
| `/v1/*` | **零变更**。网关 key 鉴权走 `key_hash`（§10），与"谁登录了后台"完全无关 |
| `src/gateway/` | **零改动**。选路 / 限流 / KeyPool / cooldown 一行不动 |
| DDL | **纯加列**：`admin_users.role`、`admin_users.group_id`。`SCHEMA_VERSION` 仍为 **2**、零迁移分支 |
| `ERROR_CODES` | **零新增**。越权是 `FORBIDDEN`（既有），未登录是 `UNAUTHORIZED`（既有） |
| 审计动作 | 新增 `user.create` / `user.delete`（管理面建删用户，**不新增**登录审计 —— `auth.login` 已在写，且它已经区分成败） |
| 会话表 | `sessions` **零变更**：role 每次从 `admin_users` 现读（见"为什么不在会话里存 role"） |

**为什么 role 不存进 `sessions`**：存了就要处理"管理员把某用户角色改了，
他的旧会话还是老角色"这个窗口，而 `sessions` 表加列又是一件要迁移的事。
`admin_users` 现读的代价是每次鉴权多一次主键点查（`username` 是 PRIMARY KEY），
在 SQLite 单连接上这是微秒级。**正确性 > 微秒**。

## 判据

| 用例 | 钉住什么 |
|---|---|
| `role=user` 打 `/api/upstreams` → `403 FORBIDDEN` | **授面在服务端**，不是前端隐藏 |
| `role=user` 打 `/api/console/keys` → 只回本组 key，且**全是掩码** | 数据按会话归属收窄；明文无路径 |
| `role=user` 打 `/api/console/usage` → `series[].key` 恒等于本组 id | 不带别组一行 |
| `role=user` 构造 `?groupId=<别组>` → 被忽略，回的还是本组 | 归属**不来自请求参数** |
| `role=admin` 打 `/api/console/*` → 正常（管理员不因新前缀被挡） | 新面不缩小管理员 |
| 老库升级后唯一账号 `role='admin'` | 升级不锁死现有管理员 |
| `role=user` 且 `group_id IS NULL` → 三个端点回空 + 一句说明，**不是 500** | 未分配用户的可读降级 |

**全部经变异验证**（改坏 → 红 → 还原）：

| 变异 | 结果 |
|---|---|
| 闸门里的 `/api/console/` 前缀判定删掉 | **红** ← 越权那条 |
| `/api/console/keys` 的 `WHERE group_id = ?` 改成读 `req.query.groupId` | **红** ← 归属不来自请求 |
| `ALTER TABLE` 的 `DEFAULT 'admin'` 改成 `DEFAULT 'user'` | **红** ← 升级不锁死 |

## 遗留（不粉饰）

1. **配额是组级，不是人级 —— 这是既有结构，本 ADR 没改。**
   `src/gateway/limiter.ts` 的 `check(group)` 按 `groupId` 计 rpm / tpm / daily_quota，
   `usage_logs` 按 `group_id` 记。所以"多个用户共享同组"的真实语义是：
   **他们共享同一个配额池、同一批 key、同一份用量统计**。同组 10 人打满 `daily_quota`
   时，10 个人一起被 `QUOTA_EXCEEDED`。要按人拆配额必须动 `limiter` + `KeyPool`
   （`src/gateway/`，路由者车道），是**独立的一笔**。本 ADR 不假装它不存在。
2. **用户端不能自己发 key**（决策 3）。所以"获取 key"= 看掩码 + 从管理员处拿明文一次。
   下发签发权要另立 ADR（攻击面：组内成员可无限增发、共烧一个配额池）。
   **〔v1.15.9 作废 —— 那条 ADR 就是 ADR-0038〕** 它把"无限增发"用护栏消掉
   （`KEY_SELF_ISSUE_LIMIT = 10`，按组把数，到顶 `422` + `details {limit, used}`，
   判在签发**之前**），下放 `POST` / `PATCH` / `DELETE /api/console/keys[/:keyId]`（契约 §19.3b）。
   本条剩下的唯一部分（"组内成员可无限增发"的攻击面）**已经被判据钉住**；
   而同组成员**互相吊销** key 这一半被 ADR-0038 遗留 1 **刻意保留** —— 组在这里
   本来就是互相信任的配额池。
3. **没有用户自助改密码、没有 MFA、没有账号锁定**。`admin_users` 只有口令散列，
   `loginLimiter` 是 IP 级的。这些在 1panel 报告 §2 / §4 里都标了"可做但非必需"，
   单管理员 + 少数用户的场景下**收益低于成本**，本 ADR 一律不做。
   **〔v1.15.9 拆成两半：改密码那一半被 ADR-0038 决策 3 推翻，MFA / 账号锁定那半继续成立〕**
   - **改密码那半推翻了，理由是本条给错了理由的性质**："收益低于成本"是一个**成本估计**，
     而本条自己在上一条里写了"忘口令 = 删掉重建"的代价（**删号会吊销本人全部会话，
     并把他在 `audit_log` 里的 actor 断成两截**）。为一个改口令付这个代价，成本估计算错了。
     现在有 `POST /api/auth/password`（无 `:username`，改的恒是会话本人）。
   - **MFA / 账号锁定那半继续成立**，但理由与本条写的不同：不是"收益低"，是它要在
     `admin_users` 之外一整套状态（TOTP 种子 / 恢复码 / 锁定窗口与解锁路径），
     而**恢复码发不出去 = 忘了手机号账号就废了** —— 那正是本 ADR 刚消掉的那类代价。
     **身份绑定**同理，且 Bo 已明确裁定不做（它需要一个新的信任根，做半个比不做更坏）。
4. **建用户只能靠一个管理端点**，面板 UI 是后端之后的事。本 ADR 交付
   `POST /api/users` / `DELETE /api/users/:username`，前端是否做管理页另计。
   **〔v1.15.4 结清〕** 结清方式：`web/src/pages/UsersPage.tsx`（列表 + 删除）+
   `web/src/pages/users/UserFormModal.tsx`（**只有新建**）+
   `web/src/pages/users/PasswordRevealModal.tsx`（口令一次性展示）+ `usersApi` +
   侧栏「用户管理」一项 + 懒加载路由。**一个后端文件都没动** —— §19.7 的端点本 ADR
   就验收过了，这一版只是补上"不手打 curl 也能建号"这个入口。
   而 `curl` 那条路的问题不只是麻烦：**口令明文只存在于 `POST` 的响应体里**（§4 铁律），
   从 `curl` 拿口令意味着它进了 shell 历史。
   **这一页刻意没有编辑入口**：`updateUser` 只动 `groupId` / `displayName` 且没挂路由，
   所以"换角色 / 换组 / 忘口令"的答案一律是删掉重建。前端不做一个背后没有端点的表单。
   **〔v1.15.9 部分作废〕** "忘口令"这个答案**不再经由管理员**：用户自己在两个外壳的账号菜单里
   改（`POST /api/auth/password`，契约 §19.7）。**管理面这一页仍然没有重置入口，这一句照旧成立** ——
   两者的区别是**谁能发起**：管理员**替别人**重置是静默接管（原主人收不到任何通知、旧口令直接失效），
   自己改自己的口令要先验旧口令。所以"背后没有端点的表单"这条纪律没变，变的只是它不再覆盖那一格。
   口令展示照 `GatewayKeyRevealModal` 同一形状：显式复制按钮 + "现在不抄就拿不到了" +
   **不给"再次查看"**（重看只能重建号，旧口令会立刻失效）。
   `role` 默认 `user`，选 `admin` 时弹 Alert —— 管理员账号等同于把整个网关交出去，
   包括删掉包括你自己在内的所有账号。
   **手工验收不可省**（遗留 7 的原因）：建一个普通用户 → 抄走口令 → 登进 `/console`
   → 回到管理面删掉。这两个动作前端零自动化覆盖。
5. **授面曾漏过 WS 一格**（v1.15.2 补，见上面 §2）。写在这里而不是删掉那段历史：
   漏判的**成因**值得记住 —— 闸门为了一条路径开例外，而那条例外把授面一起放过了。
   教训不是"别开例外"（1006 与 4401 的分辨确实需要它），而是
   **每次给闸门开例外，都要单独回答"这条路径的授面谁来做"**。
   本 ADR 首版没回答，所以漏了整整两版。
6. **前端 `startLive()` 对 `role=user` 仍会开这条通道**（实现侧 UX 缺陷，契约不管接线，
   但记在此处以免被当成"后端又坏了"）：用户进 `/console` 会收到 4401 并被弹回登录页。
   正解是 `AppLayout` 按 `role` 决定是否订阅实时通道，而不是让用户撞一次 4401 才知道。
   **〔v1.15.3 结清〕** 结清方式比上面写的"正解"更彻底：`role=user` 现在**根本不落在
   `AppLayout`**（`router.tsx` 的 `Workspace` 按 `SessionInfo.role` 分流），而是落在
   独立的 `ConsoleLayout`，那一个外壳**不调 `startLive()`**。不是"订阅了再判断要不要"，
   是"这一侧没有这个订阅点"。代价是多一个外壳文件，收益是 `AppLayout` 里不长出一个
   `if (role === 'user')` —— 那句话一旦住下，意味着**每加一个管理面专有的全局订阅，
   都要再想起来一次**。分流放在路由层同理：判据是 `SessionInfo.role` 这一个字段，
   而判断只发生一次，新页面自动落在正确的一侧。
7. **`web/` 侧没有任何自动化测试**（v1.15.3 结清交付时依然如此）：没有 test script、
   没有 runner。所以 §19 的前端这一半，验收口径只有 `tsc --noEmit` + `vite build`
   全绿 + 三个 console chunk 各自独立分包。**这意味着"分流是否正确"这件事，
   后端有一条变异验证过的测试，前端一条都没有** —— 路由层那个 `role === 'user'`
   写反了，编译器和打包器都不会说话。补一个前端 runner 是独立的一笔（要选型、要配
   jsdom、要给现有几十个页面补 baseline），不在本 ADR 范围内；但在那之前，
   **每次改路由分流都要手工登一次两种身份的账号**，这不是可省的步骤。
   **〔v1.15.5 补记：这条手工步骤在 v1.15.3 与 v1.15.4 被跳过了两次，代价是一个 P0。**
   v1.15.4 交出了管理面建号入口（"发一个普通用户"从此不用手打 `curl`），
   验收口径写的仍是 `tsc` + `vite build` —— 于是"建出来的普通用户登不进来"
   这个缺陷活过了两版：闸门对 `role=user` 只放行 `/api/console/**` 与
   `GET /api/access-info`，而 `AuthGate` 进受保护区域第一件事是打
   `GET /api/auth/session`，它拿 403 就渲染成"无法连接管理面"的全屏错态
   （403 不是 `UNAUTHORIZED`，不派发跳登录页）—— **整个消费面够不着**。
   它是在 Bo 说"起个测试吧，放开局域网访问"、用真实浏览器从局域网 IP
   走完整流程时才撞出来的（契约 v1.15.5 / 5 条授面用例 + 1 条变异）。
   **教训不是"要写前端测试"（那仍是一笔独立的钱）**，而是
   **"每次建出一个新身份，都要真的用它登一次"** —— 建号入口交付的那一版
   恰恰是最该做这件事的一版，而它把 `curl` 步骤省掉的同时，
   也把那次手工登录一起省掉了。守则写了没人执行，等于没写。〕
8. **`consoleNav` 必须叫 `.tsx`**（v1.15.3 交付时撞出来的）：它导出含 JSX 的元素
   （`icon: <ApiOutlined />`），叫 `.ts` 则 `tsc` 报 6 个 `TS1005`，报错位置
   （第 29 / 35 / 41 行）指向的是 JSX 而不是文件名，第一次撞上会以为是语法写错了。

## 与 A 档的判据差别（为什么这不是 A 档）

A 档 = 纯前端 `/dashboard ⇄ /console` 双视图，**后端 0 改动**。
（**〔v1.15.3 订正〕** 这里原先写的是 `/admin ⇄ /console`，而**前端没有 `/admin` 这个路由** ——
管理面首页是 `/dashboard`。`/admin` 是从"管理面"这个词推出来的地址，不是仓库里存在的东西。
写成 `/admin` 不会让 A 档的论证失效（双视图的意思不变），但它是个**假地址**，
而下一个照这句话去配反向代理或写文档的人会去找一条不存在的路径。）
它做出来的东西里，"切换工作区"是真的，但**"普通用户登录"是假的**：
后端仍然只有一个管理员身份，`/api/console` 里的数据来自管理员自己的会话。
一个普通用户根本登不进去（没有他的账号），而管理员切到 `/console`
看到的还是**全站**数据。Bo 要的是前者（真有人登进来、只看自己的），
所以必须走 B 档：**加第二种身份 + 服务端授面**。
这两笔的成本差不在前端行数，在"有没有一条真实的权限边界"。
