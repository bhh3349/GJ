## 〇、结论摘要

1. **终端**：主用 **PowerShell 7+**（Windows 原生、UTF-8/JSON 友好），Git Bash 仅作 git 操作备用。所有脚本必须双终端可跑，Git 命令是唯一允许的 bash 语法。
2. **知识库**：**接入，但用轻量"仓库内三层"方案**，不引入外部重型工具。L1 = `AGENTS.md`（AI 守则入口）+ `docs/`；L2 = `.specify/`（规格驱动工件：constitution/spec/plan/tasks）；L3 = `.specify/memory/`（决策日志）。
3. **AI 守则**：参照业界 **AGENTS.md 开放标准**（OpenAI Codex / Cursor / GitHub Copilot 等已支持，Linux 基金会托管）写入根目录 `AGENTS.md`，三条职责线（网关/管理后端/前端）共用一份守则 + 各自嵌套补充。
4. 流程方法论参考 **GitHub Spec Kit（140k stars）** 的 SDD 流程：先规格后实现、每阶段留痕、实现后跑收敛（convergence）自检。CLI 工具可选试验，**不作为硬依赖**。

## 一、终端与环境约束（D1）

### 1.1 现状与选择

本机可用终端：**PowerShell** 与 **Git Bash**。约定如下：

| 用途 | 首选 | 说明 |
|---|---|---|
| 日常命令、npm/pnpm、脚本执行、PowerShell 语法 | **PowerShell 7+（pwsh）** | UTF-8 与 JSON 输出友好，Windows 原生 |
| git 全部操作 | 不限（两者皆可） | Git Bash 或 `git.exe` 均可，输出一致 |
| 一行式 Node 代码（快照/探针） | `node -e "…"` | 不要写 Unix 一行式管道依赖 |
| 长任务、服务启停 | PowerShell + `package.json` scripts | 一律通过 npm scripts 封装，避免裸命令差异 |

### 1.2 PowerShell 执行策略

- Windows 默认策略为 `Restricted`（客户端）/`RemoteSigned`（服务端）：**本地脚本可跑，网络下载脚本被拦**。
- 项目脚本统一用 `pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/xxx.ps1` 方式调用，**不修改机器级策略**（运行环境应保持最小变更）。
- 不用 `Invoke-Expression` 拼接执行；脚本参数显式传递。

### 1.3 Windows 编码与路径铁律（本项目为中文文档项目，尤其重要）

1. **源代码/文档统一 UTF-8（无 BOM）**；PowerShell 5.1 对无 BOM 文件按 GBK 读，中文会乱码 → 一切脚本用 **pwsh 7**，不用 Windows PowerShell 5.1。若必须兼容 5.1，给 .ps1 写 BOM。
2. Python 侧涉及中文时设 `PYTHONUTF8=1`（Spec Kit CLI 是 Python 工具，若引入则遵守）。
3. **路径一律正斜杠或双反斜杠**，含空格/中文的路径在命令里必须加引号；脚本不得硬编码盘符。
4. `.gitattributes` 强制 `* text=auto eol=lf`（脚本与配置），`.editorconfig` 固定缩进；禁止 CRLF 混入 sh 脚本（会导致 Git Bash 下 `\r` 报错）。
5. 环境变量与密钥走 `.env`（不入库），Windows 下用 `$env:XXX` 语法读取；脚本里禁止把 secret 回显。

### 1.4 脚本交付要求

`package.json` 的 scripts 是**唯一正式入口**（`dev / build / test / typecheck / check:sqlite / check:secrets`）；任何文档里写的命令必须实际验证可跑，**不存在于 scripts 的命令不得写进文档或门禁口径**（`pnpm lint` 因仓库无 eslint 配置、实际不可跑，已于 2026-10-06 删除）。PowerShell 专用脚本放 `scripts/`，文件名后缀明确 `.ps1`。

## 二、知识库接入方案（D2）

### 2.1 方案：仓库内三层知识库

**结论：接入。** 采用"仓库即知识库"的轻量三层结构（参考 AGENTS.md 标准与 Spec Kit 的 `.specify/` 目录形态），不引入外部知识库系统。理由：3 人小团队、单仓库、两周级项目，外部工具（向量库/wiki）的维护成本 > 收益；仓库内 Markdown 可被 AI 直接读取、可 git diff、可评审。

```
sub/
├── AGENTS.md                  # L1：AI 开发守则入口（根）
├── web/AGENTS.md              # L1：前端嵌套守则（就近覆盖）
├── CLAUDE.md                  # 一行指向 AGENTS.md（工具兼容层）
├── docs/
│   ├── 需求文档-v1.1.md        # L1：需求基线
│   ├── api-contract.md        # L1：REST 契约（管家 M0 产出，唯一接口依据）
│   ├── 开发约束-v1.0.md       # 本文
│   └── 决策日志-YYYYMMDD.md   # L3：重大拍板记录
├── .specify/
│   ├── constitution.md        # L2：项目宪法（不可妥协原则，M0 冻结）
│   ├── specs/<feature>/       # L2：每个功能 spec.md → plan.md → tasks.md
│   └── memory/                # L3：上下文记忆（术语表、踩坑记录、算法决策）
```

### 2.2 三层各自职责

| 层 | 内容 | 谁维护 | 时机 |
|---|---|---|---|
| **L1 规范层** | 守则、契约、需求、约束文档 | PM 汇总、管家/路由者/画师各自产出自己章节 | M0 冻结后变更需 PM 批准 |
| **L2 规格层** | 项目宪法 + 每功能 spec/plan/tasks 三件套 | 功能负责人起草、PM 验收 | 每个里程碑开工前 |
| **L3 记忆层** | 决策日志、术语表、踩坑记录（如"SQLite WAL 在 Windows 的锁行为"） | 全员随手追加，PM 每日整理 | 随开发持续 |

### 2.3 读取纪律（给三条职责线的硬约束）

1. **动手前必读**：对应功能的 `spec.md` → 契约文档 → `AGENTS.md`；发现文档冲突，停下来在群里提问，**不许按猜测实现**。
2. **契约唯一权威**：接口字段以 `docs/api-contract.md` 为准，聊天记录不算数；契约改了必须改文档，文档没改的契约变更无效。
3. **先 spec 后 code**：M2 之后的新功能，没有 spec.md 不开工（复用已有模式的小改动除外）。
4. **决策留痕**：凡是拍板过的事（含 Bo 的回复）进 L3 决策日志，格式：日期 / 决策 / 理由 / 影响。

### 2.4 不引入的东西（明确排除）

- 外部向量知识库、RAG 管道、 wiki 系统 —— 项目规模不匹配；
- 每个功能都写正式 spec —— 只对 M2+ 的复杂功能强制（统计、限流、余额模板），CRUD 类用契约文档即可。

## 三、AI 开发守则（D3 → 落地于 `AGENTS.md`）

### 3.1 流程纪律（参照 SDD：specify → plan → tasks → implement → converge）

1. **契约先行**：先冻结 `docs/api-contract.md` 与 KeyPool 签名，任何人不得在契约未定时写调用方代码。
2. **实现必须对照验收**：每个交付物对应 `需求文档-v1.1.md` §九 的量化验收条目；实现者交付时自报 PASS/FAIL 及证据（命令 + 输出）。
3. **收敛自检（converge）**：每个功能完成后，实现者对照 spec 与验收逐条核对，输出差异清单；差异未清零不得标记完成。
4. **单写者原则**（v1.1 已冻结）：key 健康态归网关运行态；管理端只读 + revision 失效缓存。任何跨模块写操作先查此原则。
5. **状态三态**：所有写操作（API 与前端）必须有 loading / 成功 / 失败反馈；网关转发路径禁止同步 DB 写（异步批量 + spool 降级）。

### 3.2 代码纪律

1. TypeScript `strict: true`；禁止 `any` 逃逸（确需时 `unknown` + 收窄并注释原因）。
2. **禁止假数据**：生产构建不得含 mock 兜底（画师 v1.1 已冻结，此处全局化）；没数据就空态，接口挂就错误态。
3. **禁止明文密钥落盘**：上游 key aes-256-gcm；网关 key sha256+pepper；`MASTER_KEY` 缺失即拒绝启动。
4. 错误体双轨制（v1.1 已冻结）：`/v1/*` 返回 OpenAI 格式，`/api/*` 返回 `{code,message}`；新增错误码必须先登记进契约再使用。
5. 提交信息：`<scope>: <动词开头的一句话>`（如 `gateway: 修复流式转发中断后未关闭连接`），一次提交一个意图。

### 3.3 交付纪律（Definition of Done）

一个任务算"完成"，必须同时满足：

- [ ] 四闸全绿：`pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm check:secrets`（CI 脚本就绪前，本地跑通并在群里贴输出）
- [ ] 对照验收条目自测通过，给出证据
- [ ] 涉及契约的改动已回写 `docs/api-contract.md`
- [ ] 进度汇报含**未完成项与风险**，不许只报喜
- [ ] 新增公共约定/踩坑已追加到 L3 记忆层

### 3.4 三条职责线的守则侧重（写入各自嵌套 AGENTS.md）

| 角色 | 额外守则要点 |
|---|---|
| 路由者（网关） | 热路径零阻塞；故障注入演练（401/429/超时/kill）必须有自动化脚本；性能数字（TTFB/切换耗时）用同机直连做基准对比 |
| 管家（后端） | schema 变更必须走迁移文件；任何接口不回密文；写操作落审计日志；余额刷新永不进请求路径 |
| 画师（前端） | 严格对齐契约字段名，不造字段；组件三态齐全；图表数据必须来自真实 API/WS；深色主题 token 统一管理 |

## 四、方法论：参考 GitHub Spec Kit 的 SDD（不引入硬依赖）

调研结论：GitHub 官方 Spec Kit（开源，~140k stars）把 AI 开发流程固化为 **constitution（宪法）→ specify（规格）→ plan（计划）→ tasks（任务）→ implement（实现）→ converge（收敛）**，并有独立的 bug-fix 流程（assess → fix → test，验证缺失不算修复成功）。

**采纳方式：抄流程，不装工具。**

- 采纳：项目宪法（§2.2 L2）、功能三件套、实现后收敛自检（§3.1 第 3 条）、bug 修复"验证缺失不算修复成功"原则。
- 可选试验（不阻塞 M0）：若 Bo 同意，D0 可试装 `uv tool install specify-cli` 跑一个小功能验证流程收益；收益不显则弃用，流程约定不受影响。Python 3.11+ 为其运行前提（脚本环境遵守 §1.3 第 2 条）。
- 不采纳：其多 agent 集成模板、社区扩展生态——本项目已有明确分工，不需要额外编排层。

## 七、调研来源（本轮实际访问核验）

1. **AGENTS.md 开放标准** — https://agents.md/
   - 定位"README for agents"；60k+ 开源项目采用；OpenAI Codex、Cursor、GitHub Copilot、Gemini CLI、Devin 等支持；现由 Linux 基金会旗下 Agentic AI Foundation 托管；无必填字段；就近覆盖原则（嵌套文件优先）；指令冲突时"最近的文件赢，用户即时指令最高"。
2. **GitHub Spec Kit** — https://github.com/github/spec-kit （README 原文核验）
   - SDD 流程 constitution → specify → plan → tasks → implement → converge；bug-fix 扩展 assess → fix → test（"Missing verification is not a successful fix"）；运行前提 Python 3.11+ / uv；Windows 支持；MIT 协议。
3. **PowerShell 执行策略**（Microsoft Learn 官方文档）
   - Windows 默认 Restricted（客户端）/ RemoteSigned；Process 作用域仅当前会话生效 → 项目用 `pwsh -NoProfile -ExecutionPolicy Bypass -File`，不改机器策略；执行策略是"纵深防御"而非安全边界。
