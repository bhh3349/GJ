# ADR-0029：账号绑出口的写路径与读面

- 状态：已接受（2026-10-14）
- 关联：契约 v1.13.0 §15.1 / §15.2 / §15.4 / §15.7 / §15.12 / §16.7；ADR-0021 决策 5（E 接缝）与决策 9
- 车道：管家（`src/api/` + `src/db/`）；画师消费（账号池「绑定出口」UI，等契约条目到位开工）
- 触发：交付链探查缺口 1（「出口池填了没用」）与缺口 2（「接入信息无端点」）里的**共同地基**——
  出口池的配置面（§16.7.2 七条）2026-10-13 已由画师接线，但**账号绑不上去**；
  驱动的 `egress_id` 只有 DDL 与快照读，**没有写入口**。

## 背景

`supplier_accounts.egress_id` 的三个半边各自在，独缺两条：

| 半边 | 状态（本 ADR 之前） |
|---|---|
| DDL（`egress_proxies` + `supplier_accounts.egress_id`） | ✅ 已落（§16.7 / v1.7.0） |
| 快照读（`account_egress_id` → 预算按出口分桶） | ✅ 已落（ADR-0021 决策 5 的 E 接缝，`src/wiring/store.ts`） |
| **写入口**（把账号绑到某个出口） | ❌ **不存在** —— 管理面 12 条路由里没有一条能写这一列 |
| **管理面读面**（看见这个账号现在走哪个出口） | ❌ **被三条纪律显式禁止**（§15.12 第 3 行 / §16.7 绑定纪律之三 / §7 帧本期不发射） |

后果是一条**断链**：出口池的配置面建得出条目（`/api/egress` 七条，含 SSRF 拦截与探活），
而账号**永远绑不上去** —— 于是"我要让这个号走香港那台"这个动作在界面上根本不存在；
即便绕过界面写库，用户也**看不见结果**（读面被禁），只能盲写。

## 决策

### 1. 写入口 = `PATCH /api/supplier-accounts/:id`（收 `egressId` + `revision`）

- **不新开 `/egress` 子资源**：要写的只有一格值，而"账号 ↔ 出口"是 `supplier_accounts`
  这一行自己的属性（§16.7 绑定粒度 = **账号级**，不是 key 级）。单开子资源等于把同一行的
  字段拆到两条路径上，将来加第二个可改字段又要在两处挑。
- **不落到 `POST /api/supplier-accounts`**：建账号走的是批量 `import`（§15.2），
  它一次收一行「手机号,密码」文本、**不是 REST 建行**。§16.7 裁定 6 那句
  "`POST/PATCH /api/supplier-accounts` 传**不存在或已 `retired`** 的 `egressId` ⇒ 400"
  因此落地在这一支 PATCH 上（契约本版已把该句指向本端点）。
- **`revision` 必填**（§0.2 乐观锁）—— 同一行两个字段共用同一把锁，是这一行本来的形状。
- **活性校验**（§16.7 裁定 6 账号侧对称条）：`egressId` 指向不存在或已 `retired` 的出口 ⇒
  `400 INVALID_PARAM`（`details.field = 'egressId'`）；`null` 合法（解绑 = 回宿主出口）。
  **不提供 `force`**，与出口退役那条（`409 EGRESS_HAS_ACCOUNTS` 无 `force`）同向。
- **判据顺序：活性校验 → 乐观锁 → 值未变短路。** 反过来会让"填错出口"在并发场景下
  被报成 `REVISION_MISMATCH`，前端去刷新重试，而真因永远不显示。
- **值未变 = 空操作**：不推 `revision`、不发 `change_log`。连点两次同一个出口不该白推
  一次网关快照重建 —— `applySnapshot` 会把 token-plan key 的乐观扣减清零（§9 / §3 已知副作用）。

### 2. 读面 = `SupplierAccount.egressId`（非破坏加一格）

**修改三处既有纪律的表述，并写明理由（不是悄悄推翻）：**

- §15.12 第 3 行原写 `SupplierAccount` DTO「穷尽，**不加** `egressId`」；
- §16.7 绑定纪律之三原写「`egress_id` 不进任何 DTO」；
- §7 `egress_pool` / `egress_cooldown` 帧本期不发射（那条**不动**）。

这三条原意一致且正确：**建表 ≠ 前端要处理它** —— 防的是**提前**给前端造一个永远为 `null`
的字段、和一个没有生产者的读面。但**写路径一旦存在**，缺读面就从"不做多余的事"
变成"做了一半"：用户能点、点了看不见结果，只能盲写。**纪律的目的是不造没人用的字段，
不是禁止字段存在。**

**改口后的边界（必须一起读）：**

- `egressId` 答的是"**这个账号自己绑了谁**"（配置，`supplier_accounts` 的列）；
- **出口池的状态**（在线 / 冷却 / 出口 IP / 心跳）**仍然只有 §7 帧一条读面**，不进任何 DTO。
  两条不是一件事：一个是**配置**，一个是**实时健康**。§7 三条硬约束（不得接线 / 缺省不是证据 /
  不得反推）一条不减。
- `egressId` 是**不透明字符串**（§7 同款纪律）：前端只当键用、**不得解析其内容**，
  否则 Tier 2 换形状就成了一次前端改造。
- `null` = **未绑定、走宿主出口** —— 是**配置事实**，不是"未知"、不是"不可用"
  （§16.7「`null` 的两种来源必须分开」）。

### 3. `change_log` 广播是**必需项**，不是优化

`src/db/schema.ts` 那段 ⚠ 约定（ADR-0021 决策 5）本就写死了这条，本 ADR 只是让它落地：

- 改 `egress_id` 改的是网关快照里**每把 key 的出口归属**；
- 而 `supplier_accounts` **不在** `SNAPSHOT_ENTITIES`（快照只认 `upstream` / `key` / `model` / `balance`）；
- ⇒ 必须按**受影响的每把 `pooled_key_id`** 各发一条 `entity = 'key'` / `op = 'update'`；
- **与写入同一事务**：崩在中间会让"库里有、网关看不见"成为永久状态。

**漏发的症状不是报错**：那批 key 的出口永远停在旧值 ⇒ 出口预算按 id 分桶 ⇒
**一根出口两个桶** ⇒ 放行量翻倍（§16.7 点名的第一条洞，与 `egressHostOf` 那份重复实现同源）。

### 4. 审计

新增动作 `supplier.account.update`，`detail = "egress=<id>"` / `"egress=null"`。
只放**绑定结果**、不含凭据（本路由也收不到凭据）。归属 §6「所有写操作」的下限覆盖：
"谁把这个号挪到了哪个出口"是这条链上最该留痕的一类动作。

### 5. 本版**不动**的东西（逐条登记，免得被读成遗漏）

- **`export` CSV 列清单不动**：对账表的列口径是 §15.2 另一条正文，且它已承载
  "这份表能不能用来重建账号"这类纪律。为一个新格单开一次列变更，会把"本笔只做绑定链"
  的面撑大；要加走下一笔显式决定。
- **`ERROR_CODES` 零新增**：三种失败（出口不合法 400 / 版本不符 409 / 账号不存在 404）
  全是既有码，本笔不需要新码。
- **零 DDL、零迁移**：列在 §16.7 批次就建好了；`SCHEMA_VERSION` 仍为 2。
- **`src/gateway/` 零改动**：快照读那半边早已就位，本笔只补写侧与读侧。
- **池级探活 / 心跳 / 自动摘除**：`status` / `lastHeartbeatAt` / `exitIp` 的生产者仍不存在
  （v1.6.4 那条"禁止先加字段、后补生产者"照旧管着），本笔一个字都不碰。

## 后果

- 「账号绑出口」从**不存在**变成**可写可读**：画师可按契约写 UI（账号池每行操作 /
  出口面板"已绑账号数"），PM 可活体验证「改绑 → 库变了 → 快照广播了 → 池按新出口分桶」。
- **仍不成立的两件事（写明，免得被当成已完成）**：① 出口**代理**尚未进转发链路
  （`ProxyAgent` 全仓只有 `src/api/routes/egress.ts` 的 `/test` 探活一处；数据面出站仍走裸 `fetch`）
  —— 那是**装配层接线**，属路由者车道，另开一笔；② §7 帧仍未发射，故**出口池在管理面上依然无实时状态可读**。
- 本笔只保证"绑定关系可写、可读、可广播"，**不保证流量真的从那个 IP 出去**。两者不许混说。
