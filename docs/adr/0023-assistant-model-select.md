# 23. 内置助手聊天支持按请求选择站内模型

- 状态：**已落（2026-10-13；Bo 要求 + 车道内实现）** —— 契约 §13.1 / §13.4（v1.10.0）+ 代码同批。
- 日期：2026-10-13
- 决策者：Bo（「不能在聊天框那里做个选择？站内的模型都可以选择」）+ 管家（后端落地）
- 关联：ADR-0015（§13 内置助手聊天）、契约 §5（模型档案）、契约 §13.1 / §13.4

## 背景与问题

`POST /api/assistant/chat`（§13，v1.2.0 冻结）把助手自身使用的模型名**固定在装配侧**：`src/server.ts` 读 `.env` 的 `ASSISTANT_MODEL`，经 `createAssistantInvoker({ model })` 注入，请求体只有 `messages` / `logContext` 两项（§13.1 明写「§13.1 没有 `model` 字段」）。

后果：站点里已经建档并启用了多个模型（如 `tierflow` / `tierflow_pro`）时，用户想换助手用的模型只能改 `.env` 再重启进程。Bo 要求「聊天框里能选站内模型」，即把这个选择放到请求上。

## 决策

1. **§13.1 请求体新增可选 `model`（string）。** 缺省 / 空串 = 用装配侧 `ASSISTANT_MODEL`（**零行为变更**，老前端 / 老脚本一字不改照常工作）。
2. **校验口径 = 站内已启用模型集合**，与 §5 `GET /api/models?enabled=true` / `/v1/models` **同一判据**（`models.enabled = 1` 且其上游 `upstreams.enabled = 1`）。不在集合内 → **`400 INVALID_PARAM`**（`details.field = "model"`）。这是**解析层非法**（请求写错了），不是 §13.3 那类「请求合理但太大」的 `truncated` —— 两者不许混（§13.1 既有纪律）。
3. **端口签名只增不改**：`AssistantModelInvoker.stream(messages, signal, model?)` —— 第三参**可选**，既有实现与全部桩零改动即编译通过。
4. **无状态不变**（§13 头注纪律 1）：所选模型不写进会话、不落库、服务端不保存，每轮请求自带。零新表零迁移。
5. **计量口径不变**（§13.4）：所选模型走的仍是**同一个 key 池、同一个 engine 装配**，照常计入 key 健康、不计入业务流量口径。

## 为什么不怎么做（被否掉的备选）

- **不静默回落到缺省**：`model` 拼错时若回落到 `ASSISTANT_MODEL` 并正常作答，用户会以为「切换生效了」，直到某天发现答的不是那个模型 —— 一个只能靠猜的失效模式。回 400 是**当场可见**的。
- **不新增「可选模型列表」端点**：§5 `GET /api/models?enabled=true` 已经给出**同一集合**；再开一个只读端点就有第二份口径，两处一旦漂移，选择框里会出现一个选不出结果的模型名。前端直接复用现有端点。
- **不改 `/v1/*`**：助手选择是**管理面装配选择**，与网关数据面路由无关。

## 影响

- 正面：前端一个下拉即可换模型；`.env` 的 `ASSISTANT_MODEL` 退化为**缺省值**而非唯一来源。
- 门禁：`ERROR_CODES` / `GATEWAY_ERROR_CODES` / `hintCode` **零新增**；`/v1/*` 零变更；`SCHEMA_VERSION` 仍为 2；**零 DDL**；`src/gateway/` 零改动（invoker 用的仍是既有 `chatCompletions({ model })` 入口）。
- 边界（写在这里，不留待发现）：选择面**只对已建档且上游启用的模型开放**；未建档的上游模型名（真能打通但档案里没有）在此**不可选** —— 与「档案是管理员的业务判断」这条既有口径一致（ADR-0009 / §5）。
- 责任方：后端（管家）落契约 + 端口 + 路由 + invoker；前端（画师）落聊天框选择器（复用 §5 列表端点，只调管理 API）。
