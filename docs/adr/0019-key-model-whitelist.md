# 19. key 的模型白名单：上游 `model_limits` 要落到管理面的一列上

- 状态：**生效**（2026-10-07，契约 v1.4.2 补遗；`docs/api-contract.md` §3 / §5 / §15.2 / §15.7 / §16）
- 日期：2026-10-07
- 决策者：管家 · 管理后端（契约）；路由者（网关读取面确认，待）
- 关联：ADR-0006（明文纪律）/ ADR-0018（TierFlow 账号面：账号是凭据容器、批量新建 key 为唯一入池通路）
- 触发：路由者 S1 字段依赖清单第 3 项 —— 「`model_limits` CSV 映射后的可用模型清单」

## 背景与问题

§16.3（v1.4.0）写过一句映射：TierFlow 的 `model_limits_enabled` + `model_limits` CSV
→ 网关侧 `KeyConfig.models`，"白名单语义正好对上 `matchesModel()`"。**这句话在当时是对的，也是空的**：

| 环节 | 现状（v1.4.1 为止） |
|---|---|
| 上游有 CSV | ✅ 供应商管理面 `/api/token/` 返回 |
| 网关类型 `KeyConfig.models` | ✅ 存在，v1.1 就有（`src/gateway/types.ts`） |
| 网关判定 `matchesModel()` / `keyModels()` | ✅ 已实现且语义完整（`src/gateway/key-pool.ts`） |
| **管理面存哪** | ❌ **没有列、没有字段** —— `upstream_keys` 里无处可放 |
| **网关读哪个值** | ❌ `src/wiring/store.ts` 每个 key 的 `models` **硬编码 `null`**（原注释："档案里没有 key→模型 的关联，故按 upstream 继承"） |

所以 v1.4.1 的状态是：**白名单在网关上是"永远不限"**，而契约上写着"映射好了"。
这个空洞**不会报任何错**：key 依旧健康、依旧被选中、依旧能跑白名单外的模型。
需求文档里 P6 的 `key_models`（显式 key↔model 关联）一直是"**规划中**"，不能拿它当既有载体。

## 决策 1：载体是 `upstream_keys.model_limits`（列），不是 `key_models`（表）

- 加列 `upstream_keys.model_limits TEXT`，**可空、无默认**。
- 理由：
  1. **它是上游给的一串 CSV**，1 key → N 个名字，我们**不做编辑** —— 原样存最诚实，
     与 `balance_cents` 存"上游给的数换算后的分"同一条纪律：上游事实、本地不改写。
  2. **与 P6 的 `key_models` 不是一回事**。`model_limits` 是"**上游说这把 key 能干什么**"，
     `key_models` 是"**我们本地怎么指派**"。混进一张表之后，将来没人分得清某一行是上游说的还是人配的
     —— 而这两者出错时的排查方向完全相反（前者查上游，后者查我们自己的操作）。
  3. **零新表、零数据搬迁**：走既有 `migrate()` + `hasColumn()` 守卫的 `ALTER TABLE`，
     照 `request_id` 那一批的先例；`SCHEMA_VERSION` 仍是 `2`。
- **P6 落地时的分工**（写在这里，免得以后被这张表绊住）：`model_limits` 继续当"上游事实"的只读底，
  `key_models` 负责本地覆盖，**冲突时本地覆盖优先**。本期不做 P6。

## 决策 2：出口 `models: string[] | null`，**空数组与 `null` 同义**

- §3 `KeyDto` 非破坏新增 `models`：`null` = 不限模型（老 key 恒为此值，行为与 v1.4.1 **逐字相同**）。
- **空数组按"不限"处理，不是"全禁"**。理由不是审美，是**不能制造一个实现不了的三态**：
  网关冻结件 `matchesModel(supported, model)` 对 `null` 与 `[]` **同判为不限制**
  （`key-pool.ts`，v1.1 §四"留空即按 upstream 继承"）。契约若声明 `[]` = 全禁，
  两边就会长期不一致 —— 页面显示"这把 key 一个模型都不能用"，网关照跑不误，**且没有报错**。
  契约的职责是把已冻结的实现口径**写准**，不是发明第三种状态。
- **归一化**：空串 / 空 CSV / 仅空白 / 空数组，**落库一律写 `NULL`**，不落 `''`。
  库里两个值、语义一个值，早晚有人按 `''` 写查询 —— 这次就顺手堵掉。
- **`*` 通配**：`matchesModel()` 认 `supported.includes('*')`。CSV 里若出现 `*`，**原样透出**，
  不解释、不展开。

## 决策 3：只读 —— `PATCH /api/keys/:id` 不收 `models`

上游事实不由本地编辑。手工改白名单是 P6 `key_models` 的事；在 P6 之前开放一个"改上游白名单"的入口，
等于允许页面写出一个**和上游不一致**的值，而网关会照着这个假值选路。宁可没有这个入口。

## 决策 4：`keys/sync` **不**回填该列

`keys/sync` 的掩码匹配**只按后 4 位**（§15.2：我们的 `masked_key` 是 `****后4`，与上游的
"前 4 + 后 4"取交集只剩后 4），撞号时**不更新任何行**。拿不准的匹配去写白名单，
后果是把 A 把 key 的模型限制安到 B 把 key 上 —— 表现是"某个模型静默不可用"，
**比"少同步一次白名单"难查一个数量级**。宁可漏，不写错。

## 决策 5：§5 `availableKeyIds` 必须按**生效白名单**过滤

模型档案卡的"可用 key"原先只按「已启用、非冷却、余额 > 0」，v1.4.2 起必须**同时**满足
生效白名单（`key.models` 非空取它，否则继承上游级限制 —— 网关 `keyModels()` 的既有口径）。
不补这一条，档案卡与实际选路长期对不上，且没有任何报错可追（同 §16.3 那条）。

## 影响面

| 面 | 变化 |
|---|---|
| `upstream_keys` | 加列 `model_limits TEXT`（可空、无默认；老行 `NULL` = 不限） |
| §3 `KeyDto` | 新增 `models`（非破坏；老数据恒为 `null`） |
| §15.2 `keys` 入参 | 新增**可选** `models`（省略/空 = 不设白名单） |
| §5 `availableKeyIds` | 口径补齐（**行为变化**：页面可用 key 数可能变少，这是修正，不是回归） |
| 网关 `/v1/*` | **零变更**（`KeyConfig` / `KeyPool` 签名不变） |
| `src/wiring/store.ts` | **一行取值改动**（`models: null` → 读该列），归路由者车道；**待其确认** |
| `ERROR_CODES` | 零新增 |
| `SCHEMA_VERSION` | 仍为 `2`（加列走 `hasColumn()` 守卫的 `ALTER`，**不幂等，禁靠 `user_version`**） |

## 未被采纳的方案

| 方案 | 否掉的理由 |
|---|---|
| 用 P6 的 `key_models` 表承载 | P6 是"本地指派"语义，不是"上游事实"；且一直未落地，用它承载等于把本期功能挂在一条没人排期的路上 |
| 建 key 时把白名单展开成 N 行关联 | 行数随模型数膨胀；上游加了新模型要整批重建；且这仍然是"本地指派"的形状 |
| 存上游返回的整段 JSON | 出口要把上游字段名泄给前端，前端被迫懂供应商格式（与 §15.1"出口不出现 `quota`"同一条纪律） |
| 出口 `null` / `[]` / 非空 三态，`[]` 表示"全禁" | 网关 `matchesModel()` 对 `null` 与 `[]` 同判，三态实现不了（决策 2） |

## 未决 / 待实测（不阻塞本 ADR 落地）

1. 上游创建 key 的接口是否接受 `model_limits`、回显是否带该字段 —— 与 §16.1.1 的 P0–P4 同批实测。
2. **CSV 项与我们 `models.name` 是否同构**。不同构则 `matchesModel()` 永不命中，
   表现为"白名单里的模型全不可用"。实测前一律落 `NULL`（= 不限），**不猜**。
