## 1. 终端约定 —— 结论：Git Bash 为唯一规范 shell

PowerShell 只留给 Windows 系统级操作，工程流程一律 Git Bash。

**理由**
1. 目标部署是 Linux/Docker，bash 语义与生产一致；本地用 Git Bash 能提前暴露 Windows↔Linux 差异（路径、大小写、行尾、权限）。
2. 多 Agent 并行开发，只有统一一种 shell，命令才能被复制、复现、写进文档。
3. PowerShell 与 bash 在引号、变量展开、`&&`、`$env:` 上语义不同；双规范必然出现"你那边能跑"。

**强制规则**
- 所有工程入口一律 `npm run <script>`（Node 跨平台），**禁止**把关键步骤只写成 `.ps1` 或只写成 `.sh`；CI 只按 Linux 写。
- 禁止 `NODE_ENV=xxx npm ...` 前缀写法（PowerShell 会报解析错误）→ 统一 `dotenv` / `cross-env`。
- 路径一律用正斜杠；Node 内部用 `node:path` 拼，不手拼字符串。
- `.gitattributes` 必须提交：`* text=auto eol=lf`、`*.ps1 text eol=crlf`、`*.png binary`。
- 密钥不进 shell：统一 `.env` + dotenv，`.env` 入 `.gitignore`，仓库只留 `.env.example`。
- **`better-sqlite3` 是原生模块**：锁死版本、用 `npm ci`、优先预编译二进制，避免本地 MSVC/Node 版本差异导致的构建不一致。
- **严禁依赖大小写不敏感**：Windows 本地能过、Docker 会挂 —— import 路径大小写必须与真实文件名严格一致。
- PowerShell 保留场景：端口占用排查、系统服务、注册表、证书、Windows 专属工具。

## 2. 知识库/文档：接，但**分层按需加载**

原则（Anthropic 上下文工程）：每个会话只加载"**最小的高信号 token 集**"。知识库不等于每轮都塞进上下文 —— 塞满会让真正的规则被淹没。

| 层 | 文件 | 内容 | 加载时机 |
|---|---|---|---|
| L0 | `AGENTS.md`（仓库根） | 构建/测试命令、目录约定、风格差异、安全红线 | 每次会话，**硬上限 ~150 行** |
| L1 | `CLAUDE.md` | `@AGENTS.md` 引入 + Claude 专属项（hooks/权限） | 每次会话 |
| L2 | `docs/*.md` | 需求 v1.1、`api-contract.md`、ADR、runbook | **按需**，由 L0 链接进入 |
| L3 | `.claude/skills/*/SKILL.md` | 领域流程：加接口、改 schema、改契约 | **按需**触发 |
| L4 | 代码 + 测试 | 唯一一手事实 | — |

**AGENTS.md 只写"读代码猜不到"的东西**：构建/测试命令、非默认的风格约定、环境变量怪癖、架构决策。
**不写**：文件树、逐文件说明、"写干净代码"这类默认常识、会频繁变动的信息（这些都是 Anthropic 明确列为 ❌ 的内容）。

`docs/adr/NNNN-*.md` 记录"**为什么这么选**"（如：单写者原则、金额用分），避免后续反复推翻同一决策。

## 3. AI 开发守则（可执行版）

骨架采用 spec-driven 流程：**constitution（本文）→ spec（需求 v1.1）→ plan（api-contract / ADR）→ tasks → implement → verify**。

**开工前置条件**
- `git init` 并提交首批文档 —— 当前工作区还不是 git 仓库，而"一人一分支"的协作规则依赖它。

**四条铁律**
1. **契约先行**：接口未冻结不写调用方代码；字段级定义只认 `docs/api-contract.md`，禁止各自造字段。
2. **验证闭环**：没有可执行验证 = 没做完。每个模块必须提供 `npm run test:<模块>`，交付时附命令与真实输出，不接受"看起来对"。
3. **先探后改**：跨多文件或方向不确定的改动先出 plan 再动手；单点小改直接做，不为小事走流程。
4. **上下文卫生**：任务之间清上下文；探索类工作丢给子 Agent，不污染主上下文；AGENTS.md 定期修剪（每条自问"删掉它会不会让 Agent 出错"）。

**多 Agent 协作**
- 一人一分支（或 worktree），禁止并行改同一批文件。
- 提交规范：Conventional Commits（`feat(api):` / `fix(db):` / `docs(contract):`）。
- 契约变更流程固定为：改 `docs/api-contract.md` → 群里同步影响面 → 再改代码。
- 争议以**冻结文档**为准，不以"我觉得"为准。

## 4. 管理后端模块执行细则（我认领）

1. **加密**：密文单字段存 `v1:iv:tag:ct`；`MASTER_KEY` 必须 32 字节，缺失/长度错**拒绝启动、不降级明文**；任何接口与日志都不回明文、不回密文，列表只回 `****后4位`。
2. **自动化守住红线**：写一条测试扫描 DB 文件与日志，断言**不含 key 明文**——"明文永不落盘"必须是机器检查，不是口头承诺。
3. **单位**：金额=**分(int)**、token=**int**、时间为 **ISO8601 UTC**（存储），展示按 `Asia/Shanghai`。
4. **Schema**：只走版本化 migration（禁手改库）+ 可回滚；索引至少覆盖 `(ts)`、`(upstream_key_id,ts)`、`(group_id,ts)`、`(model,ts)`。
5. **热路径**：管理 API 不做同步重活；余额刷新、统计聚合走后台任务/预聚合表，保证 P99 < 100ms。
6. **单写者**：key 健康态（cooldown/fail_count）归网关运行态，管理端只读 + 手动启停；管理端写操作递增 `revision` 通知网关失效缓存。
7. **错误体分离**：`/api/*` = `{code, message, details?}`；`/v1/*` 用路由者的 OpenAI 格式，两边不统一。
8. **分页**：`limit` 默认 20 / 上限 200，列表统一返回 `{items, total, limit, offset}`。
9. **审计**：对 upstream/key/group 的写操作全量落 `audit_logs`（who / before / after）。

**我提供的验证命令**：`npm run db:migrate`、`npm run test:api`、`npm run contract:check`（校验实际响应结构与 `api-contract.md` 一致，防文档漂移）。

## 6. 管理面鉴权与余额口径 —— 收敛结论（v0.2 追加，供 M0 并入 `api-contract.md`）

状态：**同意 PM 改判方案**，下列为可并入契约的技术细化 + 1 处需拍板的契约冲突。

### 6.1 鉴权（接受单管理员账号 + 会话，收口为可执行定义）

- 表：`admin_users(id, username UNIQUE, password_hash, created_at, last_login_at)`；`admin_sessions(id, token_sha256 UNIQUE, created_at, expires_at, last_seen_at, revoked_at, ua, ip)`。
- 密码哈希：首选 **Argon2id**；若 Windows 原生模块（`argon2` / `@node-rs/argon2`）安装受阻，降级 `node:crypto` 内置 **scrypt（N=2^17,r=8,p=1）**，schema 不变（算法+参数+盐写在 hash 字符串里）。理由：本机已有一个原生模块 `better-sqlite3`，不该让第二个原生模块卡住 M2。
- 会话 token **只存 sha256 摘要**，明文仅在登录响应出现一次；这与我方「明文永不落盘」红线同源——它不是上游 key，但泄露即后台失控。
- 会话生命周期：24h **滑动**续期（每次成功请求更新 `last_seen_at`，`expires_at = last_seen_at + 24h`），登出/改密即 `revoked_at`。
- 登录限速：5 次/分钟滑动窗口，按 `username` + `ip` 双键计数，超限 429 `TOO_MANY_ATTEMPTS`。
- `ADMIN_TOKEN` 降级为 `AUTH_MACHINE_TOKEN_ENABLED=false` 默认关闭的 CI 机器令牌，使用时审计 `actor=machine` 区分。
- 审计最小集 = **登录成功/失败、登出、写操作** 三类；保留 who / before / after，但**敏感字段脱敏**：上游 key 只记 `maskedKey`，密码 hash 与会话 token **一律不入审计**（审计表本身不能成为泄露源）。
- ⚠️ 错误码枚举缺口：现有 `/api/*` 枚举（`INVALID_KEY`/`DUPLICATE_MODEL`/`TEMPLATE_PARSE_FAILED`/`BALANCE_UNKNOWN`/`KEY_EXHAUSTED`/`QUOTA_EXCEEDED`/`UPSTREAM_UNAVAILABLE`）**没有鉴权类错误码**，而画师明确要按 code 分支「401 → 跳登录」。契约需补 `UNAUTHORIZED`(401)、`SESSION_EXPIRED`(401)、`TOO_MANY_ATTEMPTS`(429)。

### 6.2 ⚠️ 需拍板：P3「WS 首帧 auth 携 token」与 HttpOnly 会话互斥

会话 token 若存 HttpOnly Cookie（防 XSS，前端 JS **读不到**），首帧消息就无从携带它。

- **我的建议**：管理面 API 与前端同源（都在 :4001），token 走 `HttpOnly + SameSite=Lax` Cookie；REST 与 WS 握手由浏览器自动携带 —— token 不进 URL、前端不持有，同时满足防 XSS 与 P3「token 不进 URL」的**意图**。WS 保留首帧 `{type:"auth"}` 作为就绪确认，服务端 5s 未就绪即断开。
- **备选**（若坚持前后端分端口、前端持有 token）：token 走内存 + 首帧 auth，须配 CSP 且**禁止落 localStorage**。
- 影响：同源方案需在契约里写明 WS 握手依赖 Cookie；分端口方案需写明 CORS `credentials: true`。

### 6.3 余额三级口径（确认 + 2 条防造假补充）

- 单 key / 上游合计 / 全局合计三级都做；**合计只计 `category=balance` 的 key**；全局 = 上游之和。
- 补充 A：必须返回 `balanceUnknownKeyCount`（查询失败或从未查过，对应 `BALANCE_UNKNOWN`）。否则未知被当 0，合计会低估，界面误导。
- 补充 B：token-plan 单列 `tokenPlanKeyCount` + 套餐余量/到期日（可空），**不得混入金额合计**。
- 前端呈现：合计旁标注「N 个 key 余额未知」，token-plan 独立区块显示（与画师 F2 一致）。

### 6.4 M2（D3–6）工期吸收结论

后端增量约 **0.5–0.7 天**（登录+会话中间件+限速 ≈0.4 天、审计脱敏 ≈0.2 天），前端约 **0.3 天**（登录页 / 401 拦截 / 续期），**可被 M2 吸收**——需求文档 §八 M2 行本就含「鉴权/审计」，属预算内而非净增。前提：M2 内 CRUD 不再加需求。

若 M2 末溢出，砍单顺序（从先到后）：① 审计 `before/after` 降为 `who/action/target` 四列 → ② 登录限速降为进程内固定窗口 → ③ 会话续期改 24h 硬过期（非滑动）。**不可砍**：密码 hash、`/api/*` 全量 401 拦截、会话可撤销。

## 8. P3 裁定与同源 Cookie 收口（v0.3 追加）

状态：**接受 PM 裁定**——原 P3「WS 首帧 auth 携 token」作废，改为管理面与前端同源 + HttpOnly Cookie。PM 补的 Vite proxy / CSRF 两条接受，并在其基础上补 4 条硬缺口。

### 8.1 最终形态（进冻结表）

- 管理面 API 与前端**同源**（浏览器视角）；会话 token 走 `HttpOnly + SameSite=Lax + Secure(仅生产) + host-only`（不设 `Domain`）；REST 与 WS 握手由浏览器自动携带，token 从 JS 域彻底消失。
- WS 首帧降级为**就绪握手** `{type:"auth", protocolVersion}`，**不回 token**；5s 未就绪服务端断开。
- 开发态：Vite `server.proxy` 把 `/api` 与 `/api/stats/live`（`ws:true`）代理到 :4001，浏览器视角始终同源；生产由 :4001 用 `@fastify/static` 托管前端产物（或统一入口反代）。「前后端分离」只落在构建与目录层。

### 8.2 ⚠️ 补 4 条（PM 两条未覆盖，漏了就是缺口）

1. **`Origin` 白名单必须 env 驱动**：Vite proxy 下浏览器地址是 `http://localhost:5173`，写请求的 `Origin` 头就是 `:5173` 而非 `:4001`。后端若把允许源硬编码成 `:4001`，**开发态全部写操作会被自己的 CSRF 校验判 403**。→ `ALLOWED_ORIGINS` 入 `.env`（dev=`http://localhost:5173`，prod=`http://localhost:4001` 或正式域名）；校验 `Origin` + `Sec-Fetch-Site`（`same-origin` 放行，`none` 仅放行机器令牌/非浏览器）。
2. **CSRF 拒绝需要错误码**：补 `CSRF_REJECTED`(403) 入登记表。否则前端拿到 403 只能盲猜分支。`Sec-Fetch-Site` 头缺失时**不判失败**，回落 `Origin` 白名单。
3. **WS 关闭码约定**（前端据此分支，避免一律指数退避）：`4401` 会话缺失/过期/已撤销 → 跳登录；`4408` 就绪握手 5s 超时 → 重连一次；`1012` 服务重启 → 指数退避重连（沿用 1→2→4→…→15s + 重连后全量补刷）。
4. **Cookie 属性随环境切换**：`Secure` 仅生产开启——dev 走 `http://localhost`，带上 `Secure` 浏览器**根本不下发** Cookie。`SameSite=Lax` 对同源 GET 握手无影响，保持 Lax（强于 `None`）。滑动续期的 `Set-Cookie` 必须在每个成功 REST 响应回写（HttpOnly，前端无法自行续期）。

### 8.3 契约登记（M0 并入 `api-contract.md`）

- 错误码追加 4 个：`UNAUTHORIZED`(401) / `SESSION_EXPIRED`(401) / `TOO_MANY_ATTEMPTS`(429) / `CSRF_REJECTED`(403)。
- 审计最小集（§6.1）、余额两条防造假字段（§6.3）同步登记。
- WS 消息结构示例、`4401/4408/1012` 关闭码写入契约。

### 8.4 工期

后端 **0.6–0.8 天**（CSRF 校验 +0.1）仍在 M2（D3–6）预算内，**不改里程碑**；砍单顺序与不可砍三项同 §6.4。

## 9. 契约缺口收口（v0.4 追加，回应画师 3+1+1）

状态：画师反馈**全部成立**，我接受并定稿；3 项契约缺口即 M0 首版 `api-contract.md` 的内容，不另议。

### 9.1 鉴权端点集定稿（补画师的 1 项缺口）

| 端点 | 请求 | 成功响应 | 失败 |
|---|---|---|---|
| `POST /api/auth/login` | `{username, password}` | 200 `{username, role, groupIds, sessionExpiresAt}` + `Set-Cookie` | 401 `UNAUTHORIZED` / 429 `TOO_MANY_ATTEMPTS` |
| `POST /api/auth/logout` | — | 204 + 清 Cookie（**幂等**，未登录也 204） | — |
| `GET /api/auth/me` | — | 200 `{username, role, groupIds, sessionExpiresAt, serverTime}` | 401 `SESSION_EXPIRED` |

- 三个端点一律 `Cache-Control: no-store`。
- **前端 401 拦截必须豁免 `/api/auth/me` 与 `/api/auth/login`**：前者返回 401 就是「未登录」的正常信号，纳入全局「401 → 跳登录」会打成登录页无限重定向。这条请写进契约备注，不是前端实现细节。
- `serverTime`（ISO8601）为我补加：前端据此算 `sessionExpiresAt` 显示与本地时钟偏移，避免机器时钟不准导致倒计时错乱。
- `groupIds`：v1 单管理员默认全组，字段先留。**用户组隔离的权威判定在后端**（每个 `/api/*` 按会话的组范围过滤），前端按 `groupIds` 裁菜单只是 UX，不作为安全边界——契约里写明这句，防止后面有人把它当前端责任。

### 9.2 WS 鉴权与关闭码（补画师 2 项之一）

- **`4401` 确认**（会话缺失/过期/已撤销 → 前端停重连、跳登录），与 §8.2 一致；`4408` 就绪握手超时、`1012` 服务重启保留。
- 一处必须写进契约的边界：**WS 握手是浏览器发起的 GET，不能携带自定义请求头**，因此 CSRF 的 `X-Requested-With` 校验**不覆盖 upgrade 请求**。WS 的跨站防护由两层承担：① `SameSite=Lax`——跨站 WS 握手不属于顶层导航，Cookie 不会下发；② 服务端在 upgrade 阶段校验握手 `Origin ∈ ALLOWED_ORIGINS`，不命中**直接拒绝升级**（不是发关闭码）。被拒时前端拿到的是 `error`/握手失败而非 `4401`，归入退避重连，契约需注明「无关闭码也可能是被拒，不要据此判会话有效」。

### 9.3 CSRF 实现约束（接受画师的 `X-Requested-With`）

- **接受**。它是常量头、不是双提交 token，不违我 §8.2 的约束；其价值不是当秘密校验，而是**强制跨站请求走 CORS 预检**，把攻击挡在业务逻辑之前。约 +0 天。
- 适用面严格限定：仅**浏览器发起的写请求**（POST/PUT/PATCH/DELETE）；GET、WS upgrade、CI 机器令牌（Bearer）不需要该头。
- 前提条件（必须同时写进契约）：CORS 层**不得**对任意 `Origin` 反射 `Access-Control-Allow-Origin` + `Allow-Credentials: true`；仅回显命中 `ALLOWED_ORIGINS` 的源，否则不下发 CORS 头。
- 校验顺序固定：`Origin` 白名单 → `Sec-Fetch-Site`（缺失则跳过，不判失败）→ `X-Requested-With`（仅写操作）；任一明确失败 → 403 `CSRF_REJECTED`。
- 画师提的 Safari <16.4 不发 `Sec-Fetch-*` 属实，故它只能是加速器、不能是唯一依据——与上述顺序一致。

### 9.4 ⚠️ `Secure` Cookie 与部署形态（需 Bo 一行，随整包）

纯 HTTP（`http://IP:4001`）下 `Secure` Cookie 被浏览器丢弃、登录静默失败，这是部署前提，前后端都无权自决。**我的工程建议（首选）**：生产用反代（Caddy/Nginx）终止 TLS，后端 `COOKIE_SECURE=true` + Fastify 开 `trustProxy` 读 `X-Forwarded-Proto`；生产 Cookie 名可用 `__Host-sid` 前缀（强制 host-only + `Path=/` + `Secure`），dev 用 `sid`，随环境切换。**若 Bo 选纯 HTTP**：`COOKIE_SECURE=false`，且管理口**必须**绑定 `127.0.0.1`/内网、不得公网可达——同网段会话 token 可被嗅探属已知残留风险，落 ADR 记录。

### 9.5 `localhost` / `127.0.0.1` 一致性（确认画师的坑，扩大影响面）

确认。且不止 Vite proxy 一处——**三处字面量必须统一为 `localhost`**：`.env` 的 `ALLOWED_ORIGINS`、WS 握手 `Origin` 校验、`.env.example` 默认值（我会写 `ALLOWED_ORIGINS=http://localhost:5173`）。Cookie 不区分端口但区分主机，任一处写成 `127.0.0.1` 都会让 Cookie 静默丢失。

### 9.6 工期

不变，后端 **0.6–0.8 天**，仍在 M2（D3–6）预算内。
