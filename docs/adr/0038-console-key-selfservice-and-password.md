# ADR-0038：消费面 key 自助与改自己口令 —— 「不给能力」的代价被算错了

- 状态：**已接受（2026-10-18，Bo 在看过 1panel 实测差异后裁定「身份绑定和双因素认证可以不做，其他的能实现吗」→「可以按你的建议来」）**
- 关联：契约 **§1**（新增 `POST /api/auth/password`）、**§4**（`GatewayKeyDto` 非破坏新增 `label`）、
  **§19.1**（授面表三行）、**§19.3**（改写 + 新增 §19.3b / §19.3c）、**§19.5**（明文那句改口）、
  **§19.7**（"改口令=删掉重建"那句作废）
- **订正对象：ADR-0034 决策 3、遗留 2、遗留 3（口令那一半）** —— MFA 与身份绑定那半**继续成立**，
  见下「**本 ADR 明确不动**」
- 车道：`src/db/repo/groups.ts`（仓储）+ `src/api/`（路由、闸门、DTO）+ `web/`（三个面）；
  **`src/gateway/` 零改动**（本版一个字都没碰选路 / 限流 / KeyPool）
- 交付：**v1.15.9**（后端四闸 + `web/` 两闸全绿，本机真实进程两种身份手工验收，见「手工验收记录」）
- 触发：Bo 的原话「身份绑定和双因素认证可以不做，**其他的能实现吗**」—— 即 1panel 差异报告里
  被标成"可做"的那几项的**逐项可行性**，而不是"照抄 1panel"

## 背景：ADR-0034 的两条"不做"，理由不对称

ADR-0034 一次性锁掉了三件事，其中两件写在**同一段**里，但它们被拒的**理由不同**：

| 被拒的能力 | ADR-0034 给的理由 | 这个理由的性质 |
|---|---|---|
| key 自助签发（决策 3） | "组内任一成员可无限增发、共烧同一个配额池"——**一个新的攻击面** | **风险论证**（可以被护栏消掉，见决策 1） |
| 自助改口令（遗留 3） | "收益低于成本" | **成本估计**（可以被实测推翻） |

第三件（MFA / 账号锁定）理由与上两者都不同：它要`admin_users` 之外的一整套状态（TOTP 种子、
恢复码、锁定窗口），而 Bo 已明确不做 —— 本 ADR 不碰。

真正的分歧不在"该不该多给用户一点能力"，而在**"不给"的收益被高估了**：

- ADR-0034 写"用户端获取 key 的语义 = 看掩码 + **从管理员那里拿明文一次**"。
  但**明文只在签发那一次存在**，且管理面的签发发生在**组**的视角里（`GroupsPage` 的组行 →
  "签发新 key"）—— 于是"给组里第五个客户端发一把 key"这件事，管理员要：
  找到这个组 → 找到那一行 → 签发 → 把明文抄给用户（明文进 IM / 邮件 / 便签）。
  **管理面从未见过"这是谁要的那一把"**：`label` 这一列建表起就在，从来没人写、也没人读。
- 于是"没有自助"的真实形状不是"更安全"，是**整组的 key 生命周期卡在一个管理员手上**，
  而且每次经手都要过一次明文。1panel 的实测结论（差异报告）是反向的：key 由用户自己发。
- 改口令那半更直接：ADR-0034 遗留 4 自己写了"忘口令 = 删掉重建"的代价，而**删号会吊销本人全部会话、
  并把他在 `audit_log` 里的 actor 断成两截**（前一段旧名、后一段同名新行）。为一个改口令付这个代价，
  成本估计显然算错了。

## 决策

### 1. key 自助下放，**代价用护栏消掉，而不是用"不给"消掉**

新增三条写路由（§19.3b）：

| 方法 | 路径 | 语义 |
|---|---|---|
| `POST` | `/api/console/keys` | 签发一把，body `{label?}` → `201`（**明文仅此一次**） |
| `PATCH` | `/api/console/keys/:keyId` | 改名，body `{label?}` → `200 GatewayKeyDto` |
| `DELETE` | `/api/console/keys/:keyId` | 吊销（硬删）→ `204` |

- **护栏 `KEY_SELF_ISSUE_LIMIT = 10`**（把数，按组）：到顶 → **422 `UNPROCESSABLE`**，
  `details: {limit, used}`。上限是**服务端的事实**，同时经 `GET /api/console/keys` 的
  `keyLimit` 回给前端（前端据此置灰按钮 —— 前端也能数 `keys.length`，但那要求前端复刻同一个
  数字，复刻出来的那份将来一定漂移：改了上限前端还按旧数拦，用户看到的是一个"点了必然失败"的按钮）。
- **护栏判在签发之前**，不是"签了再删"：`issueGatewayKey` 不返回事务句柄，先签再判就得回滚一次写，
  而且"签了又删"会在库里留下一段没解释的 id 空洞与两条 `change_log`。
- **422 而不是 400 / 409**：请求本身完全合法（表单填得对、身份也对），挡下它的是**这个组的现状**
  （已经 10 把了）—— 与 §15.4「`UNPROCESSABLE` = 语义合法但业务拒绝」同一条判据。
- **为什么是"把数"而不是"每天几次"**：攻击面是**同一配额池被多方共享**，与"签发频率"无关 ——
  一天签 1 把烧光池子和一天签 10 把烧光池子没有区别。把数上限直接钉住"池子的份数"。
- **改名不新增端点语义**：`gateway_keys.label` 这一列**建表起就在**（`src/db/schema.ts`），
  只是从来没人写、没人读。`normalizeLabel` 是**唯一出口**，两个写入点（签发带名 / 事后改名）都走它：
  两处各写一遍 `trim` 的失败形状是"改名之后能清空、签发时清不掉"。空串与纯空白一律收成 `NULL`
  （= 没名字），不存 `''` —— 库里两种"空"并存之后，前端判空的那句就得写两遍。
- **改名/吊销的越权判据是 404 不是 403**：`WHERE id = ? AND group_id = ?`，`changes === 0` → 404。
  **403 会告诉调用方"这个 keyId 存在、只是不属于你"** —— 而那正是枚举别人 key 的反馈信号
  （§19.3 同一条，本 ADR 沿用而非新造）。
- **未分配组（`groupId === null`）在写端点上一律 400 `INVALID_PARAM`**（`details.field = 'groupId'`），
  与读端点的"可读降级"（回空 + `assigned:false`）**故意不同形**：没有组就没有配额池，
  签出来的 key 打 `/v1` 会被网关判成"组不存在"—— 把一个必然失败的东西交给用户比拒绝更坏。
  **读的失败是"看不到"（无害），写的失败是"签出一把废 key"（有害）**。
- **归属只来自会话**：写入的 `group_id` 恒取 `groupIdOf(req)`；body 里的 `groupId` **故意不写进
  schema** —— 会被 ajv 剥掉，而"剥掉之后请求照常成功、调用方以为自己指定了组"比明确拒绝更坏
  （§19.4 同一条，不声明就是明确忽略）。
- **审计复用管理面那一套动作名**（`gateway_key.issue` / `gateway_key.update` / `gateway_key.delete`），
  **不新造 `gateway_key.self_issue`**：审计的问题是"谁在什么时候动过这把 key"，而"从哪个面动的"
  不是这个问题的一半 —— actor 已经回答了。拆两个动作会让"某把 key 的全部历史"要按两个 action 查两次。
- **CSRF 照旧**：闸门在鉴权**之前**校验写方法，消费面不豁免（`X-Requested-With` 缺失 → 403
  `CSRF_REJECTED`）。这是"下放写权限"这件事真正的安全底线，它一个字都没动。

### 2. 闸门**不需要为这三条写路由改一个字**（这是前缀判定的红利）

`inConsoleScope(path)` **只判前缀、不判方法**（ADR-0034 决策 2 的原设计），所以
`/api/console/keys` 上的 `POST` / `PATCH` / `DELETE` 天然落在这道闸门里。

**但这条红利同时是一条警告**，写在这里以免下一个人误读：

> 这个前缀下**任何**写路由的授面就是"该组用户"。所以新增写路由前必须先想清楚
> **"这一下动的是不是他自己的组"**，而不是先看闸门。
> 本版三条路由的答案是"是"（`WHERE group_id = ?`，判据来自会话）。下一条写路由如果答案不是"是"，
> 那么**它是错的，不是闸门要改**。

### 3. 改自己的口令：`POST /api/auth/password`，**没有 `:username`**

body `{currentPassword, newPassword}` → `204`。

- **没有路径参数**：改的恒是会话本人。带路径参数就得判"你能不能改别人的"，而那个问题的答案在
  本版里是"不存在这个能力" —— **少一个参数就是少一类越权面**（§19.7 那条"前端不做那个表单是因为
  没有那个端点"的同一条纪律）。
- **旧口令必填且必须验**：少这一格的话，**一条被偷走的会话就能直接改掉口令、把真正的主人锁在门外**。
  校验走 `verifyPassword`（与登录同一个函数，不复刻算法）；失败 → **401 `INVALID_CREDENTIALS`** +
  审计 `fail` / `invalid_current_password`。
- **限速与登录共用同一个闸**（5 次/分钟/IP）：不共用的话这条端点就是一条**不受限速的口令猜测通道**，
  而它猜中的收益比登录页更高 —— 登录进去还得找到别的东西，改密猜中了直接接管这个账号
  （新口令一写，真正的主人再也进不来）。被限 → 429 `TOO_MANY_ATTEMPTS` + 审计 `fail` / `rate_limited`。
- **新口令与旧口令相同 → 400 `INVALID_PARAM`**（`details.field = 'newPassword'`）。不拦的话
  "改密成功"可能什么都没变（散列重算一遍、其他会话被踢，而口令还是那一串），用户以为自己换了。
- **成功之后：当前会话留着，其他会话全踢**，同一个事务：

  ```
  UPDATE admin_users SET password_hash = ?, updated_at = ? WHERE username = ?
  DELETE FROM sessions WHERE username = ? AND token_hash != ?   -- 本会话的 hash
  ```

  - **保留当前会话**：不保留的话，"我改了密码，然后我自己被踢出去、得马上再登一次"是一件
    纯粹多余的事。**前端因此绝不能在成功后跳登录页** —— 跳了用户会以为改失败了（或以为自己
    把自己踢了）。`ChangePasswordModal` 成功后就地给一张结果卡，把"谁被踢了、谁还在"写明白。
  - **其他会话必须死**：那正是这次改密的动机。
  - **用 `username` 而不是"登录时间"判会话**：同一账号在不同机器上的会话之间**没有任何可比较的
    先后**（`last_seen_at` 是最后一次请求，不是创建时刻）。
  - `keepHash === null`（理论上走不到：能到这里说明闸门验过会话、而它是从 cookie 读的）时
    **退化成全踢** —— 那是安全的失败方向：宁可让本人重登一次，也不要留下一条可能被别人持有的会话。
- **闸门放行是"字面路径 + 方法门"**（`POST` 才放，`GET /api/auth/password`**不放行**），
  **不是再开一个 `/api/auth/` 前缀**：前缀放行会把将来长在 `/api/auth/` 下的别的东西一起放掉。
  理由与 v1.15.5 那两条同形（`session` 只放 `GET`、`logout` 只放 `POST`）。
  〔**手工走查实测订正**：本 ADR 首版把"不放行"写成了 **405**，本仓**没有 405** ——
  `buildApp` 没挂 `setNotAllowedHandler`，任何方法不匹配都落进 `setNotFoundHandler`。
  真实响应：`role=user` 打 `GET /api/auth/password` → **`403 FORBIDDEN`**（方法门不放行 →
  落到 `role` 判定的 `403`），`role=admin` 打它 → **`404`**（闸门放行、无此路由）。
  一个字面路径的"方法门"在**两种身份上有两种错法**，两者都不是 405。〕
- **`role` 与"能不能改自己的密码"无关**，所以两种身份都走它：对 `role=user` 不放行的后果是
  "我永远改不了自己的密码"（消费面是他唯一的入口），对 `role=admin` 则毫无影响（他本来就在
  `/api/**` 里面）。
- **审计动作 `auth.password`**：失败两次机会（`invalid_current_password` / `rate_limited`）与
  成功一次（`other_sessions_revoked`），`detail` **只说哪一类，不回显任何口令、散列或用户输入**。

### 4. 额度卡：**透传，不算第二遍**

`GET /api/console/quota`（§19.3c）回 `{groupId, assigned, rpm, tpm, dailyQuota, dailyQuotaUsed, todayUsage}`。

- **每一格都是既有字段的透传**：`rpm` / `tpm` / `dailyQuota` / `dailyQuotaUsed` 与 §4 `GroupDto`
  逐字同源（**同一个 `todayUsage()` SQL**），`todayUsage` 就是 §4 那一格。
  所以"用量页显示的数字"与"管理面组列表显示的数字"是**同一句话**，不是两份可能对不上的账。
  契约用例钉的正是这一条：它把**管理面 `GET /api/groups/:id`** 的那几格取出来与消费面**逐字比对**
  （只断言"这次读对了"不证明"两面同一份口径"）。
- **未分配组回 `null` 而不是 0**（`assigned:false`，各格 `null`、`dailyQuotaUsed` 与 `todayUsage` 为 0）。
  "没有配额"与"配额是 0"是两件事：前者是"你还没进组"，后者是"你今天一点都不许用"。
  回 0 会让前端把第一种渲染成第二种（一排 0/0 的进度条），而用户会去查"我为什么被限流了"。
- **组被删而会话还指着它** → 回**未分配那一形状**，不是 500：对用户来说这就是"你暂时没有组"，
  而 500 会让他去报告一个不存在的问题。（会话里的 `groupId` 每次鉴权现读，所以下一次请求它已是 `null`。）
- **前端两种 0 必须画得不一样**：`null` = 不限 → 显示「不限」，**不是一根 0 长度的进度条**；
  `limit === 0` （封顶）→ 满格红色，**不是 0%**。`used / 0` 是 `NaN`，而 `0%` 会被读成"一点都没用"——
  恰恰相反，"日配额 0"是**一点都不许用**。

### 5. `web/` 三处落点（本节是画师侧的纪律，服务端不依赖它）

- **`ChangePasswordModal` 放在 `src/components/`，不在 `pages/console/`**：两个外壳都要挂它
  （`AppLayout` 给管理员、`ConsoleLayout` 给普通用户），而它改的是**会话本人**那一行、与角色无关 ——
  服务端一条路径、前端一个组件。放进 `pages/console/` 会让**管理面的 chunk 依赖消费面的 chunk**
  （方向反了），放进任一个 Layout 里则会变成两份实现、两个漂移点。
- **模型广场的筛选纪律被本版改写**（v1.15.3 写的是"不做任何本地过滤"）：
  那句话针对的是**把服务端批准的模型藏起来**（当时那个假的 `enabled` 三态就是这么来的）。
  新规则是 **筛选器必须自报家门** —— 服务端收窄 = **集合**（前端不许碰），
  用户敲的关键字 = **视图**（那是他要求的）。所以恒显 `已筛选 N / 共 M` 的橙色标签，
  筛选后为空给的是「清除筛选（共 M 个）」而不是一个空白页。
  没有这一条，"被筛掉了"会被读成"没有这个模型"。
  筛选项本身也**从返回数据里长出来**（type → count 的 Map），不是从标签表里抄 ——
  给一个必然产出空结果的筛选项，本身就是一种误导信号。
- **接口说明只列网关**真实注册**的三条**（`GET /v1/models`、`POST /v1/chat/completions`、
  `POST /v1/embeddings`），认证只写 `Authorization: Bearer <网关 key>`：
  网关把 `/v1/images/`、`/v1/audio/`、`/v1/rerank`、`/v1/moderations`、`/v1/files`、`/v1/fine_tuning`
  一律 501 `UNSUPPORTED_ENDPOINT`。照着 OpenAI 的文档列一张更长的表 = **一份半真的清单**，
  比短的那份坏 —— 用户会照着打，然后拿到一个他没做错任何事的错误。

## 判据（`src/api/routes/console.spec.ts` §19.3b / §19.3c / §1b）

| 用例 | 钉住什么 |
|---|---|
| 签发 → `201`，明文**只**在这一个响应里，`label` 落库（trim 后），审计前后差量 +1 | 明文纪律与审计都还在 |
| 到上限再签发 → `422`，`details {limit, used}`，且**库里一把都不多** | 护栏判在签发**之前** |
| 改名 → `200`，回的是**库里那个值**（入参 `"  a b  "` → 回 `"a b"`） | 归一化只有 `normalizeLabel` 一个出口 |
| 吊销 → `204` 且那一行真的没了；`GET /api/console/keys` 与 `Group.keyCount` 同步 | 硬删（不是软删） |
| 跨组改名 / 吊销别人的 keyId → **404**（不是 403） | 不泄漏 keyId 的存在性 |
| 未分配组签发 / 改名 / 吊销 → `400 INVALID_PARAM`（`field=groupId`） | 写端点拒绝，不是签一把废 key |
| 明文不落盘：签发完关库，**裸文件里搜不到那把 key**（含被吊销的） | 库内只有 sha256 |
| 额度端点：同组的 owner 在**管理面**看到的 rpm/tpm/dailyQuota/dailyQuotaUsed/todayUsage 逐字相同 | 同源（两个面是同一句 SQL） |
| 未分配组额度 → 回 `null` 而不是 0 | "没有配额" ≠ "配额是 0" |
| 组被删、会话还指着它 → 回"未分配"形状（200），不是 500 | 可读降级 |
| 改密成功 → `204`；**新口令能登、旧口令不能**；其他会话被踢、当前会话留着 | 决策 3 的全部行为 |
| 旧口令错 → `401 INVALID_CREDENTIALS` + 审计 `fail`；**口令一个字都没改** | 偷来的会话不能改密 |
| 新口令 == 旧口令 → `400 INVALID_PARAM`（`field=newPassword`） | 不产生"改成功但没变" |
| 5 次/分钟：第 6 次 → `429 TOO_MANY_ATTEMPTS` | 与登录共用限速闸 |
| `GET /api/auth/password` → **非 200**（实测：`role=user` 403 / `role=admin` 404） | 路径放行 ≠ 方法放行 |
| `POST /api/console/keys` 不带 `X-Requested-With` → `403 CSRF_REJECTED` | 写权限下放后 CSRF 仍是最低防线 |
| `PUT /api/console/usage` → **实测 404 `NOT_FOUND`**（不是 405 —— 本仓没有 405，见「手工走查」§2.6；**原样保留**，只下了 key 这一组写权限） | `/usage` 照旧无写方法 |

**变异清单**（每条删掉/改坏 → 对应用例红）：
① 护栏的 `used >= KEY_SELF_ISSUE_LIMIT` 改成 `>` → 上限用例红；
② 改名的 `WHERE id = ? AND group_id = ?` 去掉 `AND group_id` → 跨组用例红；
③ 改密的 `DELETE FROM sessions ... AND token_hash != ?` 去掉 `AND token_hash != ?` → 当前会话被踢用例红；
④ 改密不验旧口令（`verifyPassword` 恒真）→ 旧口令错用例红；
⑤ `normalizeLabel` 的 `trim()` 去掉 → 改名归一化用例红；
⑥ 写端点的 `groupIdOf` 换成读 body → 未分配组用例红（且跨组签发用例红）。

**服务端**。前端这一半的判据只有 `tsc --noEmit` + `vite build` 全绿 + 分包不串门
（四个 `Console*` chunk 的静态依赖闭包**不含任何管理面页面 chunk** —— 本版实测过，
方法见「手工验收记录」）。**"前端点得对"只能靠一次真实浏览器的走查**，见下。

## 本 ADR 明确**不动**（Bo 已裁定不做）

1. **身份绑定**（把账号绑到某个身份源）—— 不做。原因不是成本，是**它需要一个新的信任根**：
   绑谁、谁证明、证明失效了怎么办，三个问题各自都能吃掉一版。做半个（只绑不校验）比不做更坏。
2. **双因素认证 / 账号锁定** —— 不做。它要在 `admin_users` 之外一整套状态（TOTP 种子、恢复码、
   锁定窗口与解锁路径），而恢复码发不出去就等于"忘了手机号 = 账号废了"—— 那正是本 ADR
   刚刚消掉的那类代价。
3. **按人拆配额**（ADR-0034 遗留 1）—— 仍是组级。要动 `limiter` + `KeyPool`（`src/gateway/`），
   独立的一笔。
4. **逐把 key 的启用开关 / `lastUsedAt` / cached-token 指标** —— 留给 v1.15.10。
   `label` 与它们不冲突（那一列就在同一张表上），但"能停用"要把 `key` 的准入判据从
   "行存在"改成"行存在且 `enabled`"—— 那是**网关热路径上的新分支**，不该顺手带进这一版。

## 遗留（不粉饰）

1. **同一组的成员可以吊销同一组的 key**（护栏管的是"签几把"，不管"谁吊销的"）。
   这是**刻意的**：默认要三分之二个管理员才能救一把被误发的 key，而"组"在这个产品里
   本来就是**互相信任的配额池**（ADR-0034 遗留 1：同组共享配额、共享 key、共享统计）。
   真要按人隔离，第一件该做的事是**按人拆配额**（上面第 3 条），不是给 key 加 owner ——
   配额还是共享的，owner 只是一层礼貌。**审计已经把"谁吊销的"记下来了**（actor）。
2. **自助签发的 key 与管理面签发的 key 完全同形**，事后**无法从 key 本身分辨来源**。
   能分辨的只有 `audit_log.actor`。这是复用审计动作名的直接代价（决策 1 最后一条的取舍），
   登记在此以免被当成"实现漏了"。
3. **`KEY_SELF_ISSUE_LIMIT` 是常量不是配置**：10 这个数没有实测依据（组数是几十的量级、
   每组 10 把足够覆盖"几个客户端 + 几台机器"），而它一旦成为配置项就要回答
   "谁能改、改了要不要通知正在签发的人"。真不够用时改常量 + 一次发版，成本低于一个配置面。
4. **改密成功后 `web/` 不跳登录页，但这只保证"当前这条会话还在"** —— 若用户开在另一个标签页
   的会话恰好被踢（他改了两次密码），那一页会在下一次请求拿到 401 并被弹回登录页。
   这是**正确**的行为（那一步的动机就是踢掉它），但页面上不会有解释 —— 用户看到的是
   "我什么都没干就被登出了"。要消掉它得让被踢的会话知道原因，而那需要一条跨会话的通知通道，
   不在本版。

#### 2.6 「本仓没有 405」—— 走查撞出来的、本 ADR 首版写错的一条

首版 §决策 3 把"闸门不放行 `GET /api/auth/password`"写成了 **405**。走查时按**两种身份分别实测**，
拿到的不是 405：

```
role=user  GET /api/auth/password → 403 FORBIDDEN  {"message":"当前账号只能访问消费面"}
role=admin GET /api/auth/password → 404 NOT_FOUND  {"message":"接口不存在: GET /api/auth/password"}
```

成因查清了：`grep -rn setNotAllowedHandler src/` **零命中**，`buildApp` 根本没挂这个 handler，
于是**任何方法不匹配都落进 `setNotFoundHandler`**（`src/api/app.ts:607`）。所以那个"方法门"
在**两种身份上有两种错法**，**两者都不是 405**：

- `role=user` 先撞**闸门的 `role` 判定**（方法门没放行 → 落进"只能访问消费面"那条 `403`）；
- `role=admin` 过闸门、又无此路由 → `404`。

契约用例对这一格的写法本来就是**宽容**的（`expect([403, 404, 405]).toContain(res.statusCode)`，
`console.spec.ts:1409`），所以**测试没红，是文档写细了**。同一个错在**用例标题**里也有两处
（`GET /api/auth/logout` / `GET /api/auth/password` 都写着 → 405），标题改成"→ 非 200"并加注
—— **断言一个字没放宽**（本来就是对三个码容错），所以 `1050 passed` 这条数在两轮里**完全一致**。
文档侧订正四处：契约 §1 / §19.1 / 契约 v1.15.9 变更记录条目，以及本 ADR 决策 3 的闸门条目
与判据表那一行。同理 `PUT /api/console/usage` 的实测是 **404 `NOT_FOUND`**
（原样保留，只下了 key 这一组写权限）。

#### 2.7 走查**没能覆盖**的（不粉饰）

1. **前端零自动化**：`web/` 仍没有 test runner（ADR-0034 遗留 7）。上面每一条前端结论
   都只由这一次人工走查支撑 —— 路由分流那句 `role === 'user'` 若被写反，`tsc` 与 `vite build`
   都不会说话。补 runner 是独立的一笔。
2. **同一账号多标签页被踢后无解释**（遗留 4）：只验到"当前标签页活着、别的会话 401"，
   **没有**验"被踢的那一页上用户看到什么" —— 那需要跨会话通知通道，不在本版。
3. **`KEY_SELF_ISSUE_LIMIT = 10` 这个数字没有压测依据**（遗留 3）：只验到"到顶就 422 + 前端置灰"，
   **没有**验 10 这个数在实际用量下是否合适。
4. **并发签发**：只走了串行签发到顶，**没有**并发打同一个组让"判在签发之前"这条护栏在竞态下显形。
5. **走查只在局域网 HTTP 上做**：反向代理 / HTTPS / 真域名下 `publicHost` 与接入地址的行为**未验**。
6. **`POST /v1/embeddings` 只验到"没被 501 拒"**：实测回 **503**（上游/模型侧不可用，
   与本次交付无关）。所以"这条端点被网关**接受**"是验到的，而"它能**跑通**"没验。
