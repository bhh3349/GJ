# 17. M6-C：余额以上游接口同步为唯一事实源（自动同步 + 快照 + 漂移提示）

- 状态：**生效**（接口阶段由 PM 于 2026-10-07 验收放行；实现同日落库，三条口径裁定与两条实现期纪律见下）
- 日期：2026-10-07
- 决策者：管家 · 管理后端（契约 §14）
- 关联：ADR-0003（§6 余额三口径）/ ADR-0006（明文纪律）/ ADR-0011（0 次真实尝试不计消耗）/ ADR-0012（三段解析 + 失败引导）/ ADR-0016（物理删除上游子树）；**被撤销的上一版 0017（计费账本，见文末）**

## 背景与问题

M6-A 已经把「查上游余额」做完了：`upstreams.balance_query` 模板 + 内置 preset 两段解析（ADR-0012）、三个 refresh 端点、`PUT /api/keys/:id/balance` 手录、`GET /api/stats/balance` 三口径展示，全部上闸。**缺的不是"能不能查"，是"谁来按时查、查过之后留下来什么"。**

三处空白，都是静默的：

1. **只有人点才会查**。刷新全是手动端点（`POST /api/.../balance/refresh`），没人点就永远停在录入那一刻的值，而 UI 上那个值和一个刚查到的值长得一模一样。
2. **查过之后什么都不剩**。`upstream_keys.balance_cents` 是**单值覆盖**：模板刷新一次就把上一版盖掉，`balance_updated_at` 也只留最近一次。于是"上周五这个上游还有多少"这个问句**没有数据源**，趋势图无从画起。
3. **余额在动、系统不吭声**。余额掉了可能是正常消耗、可能是别处在用同一把 key；余额纹丝不动也可能是查询端点早就失效了、一直在回一个陈旧值。两者今天都表现为"一切正常"。

## 决策 0：余额的唯一事实源 = 上游接口返回值，本地不算一分钱

**系统里只有一个"余额"**：`upstream_keys.balance_cents` + `balance_currency` + `balance_updated_at` + `balance_source`，全部由**查上游**得来（模板 / preset）或人**手录**。M6-C **不引入第二个数**：

| 数 | 本版是否引入 | 理由 |
|---|---|---|
| 最近查得余额（`balance_cents`） | 已有，只读复用 | 上游说多少就是多少 |
| 本地累计消耗 `spentCents` | **不引入** | 没有它就没有扣减，没有扣减就不需要它（上一版方案的核心，已作废） |
| 推定可用 `availableCents` | **不引入** | 它是"查得值 − 本地消耗"的派生数，比查得值更容易被信以为真，却不比它更准 |
| 趋势 / 漂移 | 只读派生自**快照** | 快照存的是"那时查得值"，不是"那时推算值" |

这条是本节的地基：**凡是本地算出来的钱数，都会在"上游余额已变、本地还没查"的窗口里撒谎。**自用场景下不值得为它建账。

## 决策 1：自动同步 —— 触发 / 间隔 / 抖动 / 退避 / 单飞

**触发**：进程内**一个**拍子（固定节拍扫描），按**每上游**各自的 `nextAttemptAt` 决定这一拍要不要跑它，与手动刷新并存（手动三个端点语义**零变更**）。刻意不用"每上游一条 `setTimeout` 链"：那种写法在运行期新建的上游上要么漏挂、要么得在 CRUD 里回写调度器，而拍子扫描天然收编新上游。**首个周期同样过抖动** —— 否则开机那一刻 N 个上游同时开火，∓10% 只把它们摊在 3 分钟里，退避与单飞都救不了"同时"。并发上限**复用既有的全量刷新上限** `REFRESH_CONCURRENCY`，不新开第二个数。

| 项 | 冻结值 | 说明 |
|---|---|---|
| 基准间隔 | **15 分钟** | `BALANCE_SYNC_MINUTES`（默认 `15`；`0` = **关闭自动同步**，手动全保留）。配错（负数 / 非十进制）→ 启动失败，同 `MAX_CONCURRENCY_PER_KEY` 的纪律 |
| 抖动 | **±10%** | 每轮在 `[0.9, 1.1] × base` 上取值。理由：所有上游同时到点会让 15 分钟的边界变成一个可预测的尖峰，抖动把它摊平 |
| 退避 | `min(base × 2^n, 6h)`，`n` = 该上游**连续失败次数** | 15m → 30m → 1h → 2h → 4h → 6h（封顶）。任何一次成功/有值即归零 |
| 单飞 | 同上游同一时刻**只跑一次** | 上一轮没结束 → 本轮**跳过该上游**（不排队、不堆积）。退避与抖动都只是节奏，单飞才是"不会越跑越多"的保证 |
| 超时 | 沿用模板里的 `timeoutMs` | 不新增第二套超时 |

- **退避只由「没拿到任何有效值」推进**：该上游本轮 `failed > 0 且 ok == 0` 才算一次失败。`skipped`（没配查询方式）**不推进退避**（没做的事不该被罚），`unknown`（返回了但取不到数）**算失败**（配置错了，退到后面等人改，比每 15 分钟打一次上游强）。
- **手动刷新成功会重置该上游的退避**：用户点过了、且通了，说明失败原因可能已经修好，不该让他等 6 小时。
- **不做全局批**：每个上游各自到点各自跑，一个坏上游不拖慢其他上游的节奏，也不需要"整批一个事务"。
- 关闭自动同步（`BALANCE_SYNC_MINUTES=0`）时**不注册定时器**，`GET /api/stats/balance/sync` 的 `auto.enabled=false`、`nextRunAt=null`。

## 决策 2：取不到就**不写库**（NULL 口径，绝不清零、绝不估算）

这是本节最容易被"顺手改坏"的一条：

| 情形 | 写库行为 | `balanceUpdatedAt` |
|---|---|---|
| 查到值（`ok` 且解析出金额） | 覆写 `balance_cents` / `balance_currency`，`balance_source='template'` | **= 本次查得时刻** |
| 查失败（不可达 / 超时 / 非 2xx） | **一个字都不写** | **保持旧值**（旧值仍是"最近一次真的查到的时刻"） |
| 查到响应但取不到金额（`unknown`） | **一个字都不写** | 同上 |
| 从未查到过（新 key / 手录后撤销） | `balance_cents` 仍为 `NULL` | `NULL` |

- **绝不写 0**：`0` 是合法余额（"确实没钱了"），把"查不到"写成 `0` 会让用户以为 key 已经空了 —— 这正是 `src/db/balance.ts` 文件头那条"未知 ≠ 0"的信任基础。
- **绝不用旧值刷时间**：查失败时保持 `balanceUpdatedAt` 不动。`asOf` 的全部价值就在"它是真的查到的时刻"；查失败却把时间戳推新，等于**把陈旧读数伪装成实时读数**，比不显示更坏。
- **绝不估算**：没有单价、没有历史用量折算，一切推算都属于决策 0 已排除的第二事实源。
- token-plan 类 key 同理（`token_plan_remaining`）；本版**不改** `balanceSource` 的枚举（仍只有 `manual` / `template`）。

## 决策 3：快照与 `asOf` —— 只落"那一刻的事实"，不落"那次动作的结果"

新增纯加表 `balance_snapshots`（`SCHEMA_VERSION` 不递增、零迁移）：

```sql
CREATE TABLE IF NOT EXISTS balance_snapshots (
  id                  TEXT PRIMARY KEY,
  upstream_id         TEXT NOT NULL,               -- 抹名引用：**无外键**（ADR-0016 会物理删上游）
  upstream_name       TEXT NOT NULL,               -- 名字快照：上游删掉后历史仍可读（同 usage_logs.key_masked 的做法）
  ts                  TEXT NOT NULL,               -- 快照时刻（= 该上游本次同步完成时刻，即上游级 asOf）
  total_balance_cents INTEGER,                     -- 该上游 balance 类 key 查得合计；任一未知时仍为已知项之和，全未知为 NULL
  known_key_count     INTEGER NOT NULL,
  unknown_key_count   INTEGER NOT NULL,
  token_plan_key_count INTEGER NOT NULL,
  trigger              TEXT NOT NULL CHECK (trigger IN ('auto','manual')),
  created_at          TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_balance_snapshots_ts ON balance_snapshots(ts);
CREATE INDEX IF NOT EXISTS idx_balance_snapshots_upstream_ts ON balance_snapshots(upstream_id, ts);
```

- **快照 = 状态，不是动作**：一条快照记的是"该上游此刻所有未软删 key 的余额状态"，不是"本次刷了多少把"。所以它和 `tasks` 表里的刷新结果（`checked/ok/failed/...`）**不是一回事**，不要合并。
- **只在覆盖整个上游的同步后写**（自动同步 / 上游刷新 / 批量刷新里该上游的那部分）。**单 key 手动刷新不写快照** —— 那时上游合计里只有这一把 key 是新值、其余是旧值，记成"上游此刻的状态"会是一条半新半旧的假快照。
- **无外键 + 名字快照**：ADR-0016 起删上游会物理删除整棵子树，`REFERENCES upstreams(id)` 会让删上游在钱上再踩一次那个 500。上游删掉后快照行仍在（历史可读），展示名取自 `upstream_name`。
- **保留期**：`BALANCE_SNAPSHOT_RETENTION_DAYS`（默认 `90`，与 `HEALTH_SNAPSHOT_RETENTION_DAYS` 同一形态与理由），由**独立周期任务**清理（启动跑一次 + 此后每小时一次，`unref()`），且**该周期任务在 `BALANCE_SYNC_MINUTES=0` 时照常注册** —— 关掉自动同步不等于放弃裁剪，历史快照仍然在增长；**不参与** `pruneLogs`（那是 `usage_logs` 的 30 天口径，两件事别混）。
- **`asOf` 的两个层级，别混**：key 级 = `balanceUpdatedAt`（该 key 最近一次**真的查到**的时刻）；上游级 = 该上游最近一条快照的 `ts`。前端标注"数据新鲜度"时必须用 key 级那个。

只读暴露：`GET /api/stats/balance/sync?upstreamId=&window=`（形状与错误口径见契约 §14.3）。

## 决策 4：漂移提示 —— 只提示，而且**只能是方向级**

**为什么只能是方向级**：本地没有单价，`usage_logs` 里只有 token。**"余额掉了 3 元"和"用了 12000 token"之间没有任何可比的量纲** —— 硬要把它折成钱，就得引入单价表，那就是上一版被撤销的东西。所以判据只用**方向 + 零/非零**，明确不做量级比较，也明确不判"对没对上账"。

| 码 | 触发（相邻两次快照 + 同窗口 token 用量） | 含义 |
|---|---|---|
| `BALANCE_SPENT_WITHOUT_TRAFFIC` | 余额**下降** > 0，而窗口内本网关 token 用量 = **0** | 余额在被别人用（同一把 key 被直连 / 别处部署在用），或上游改了口径 |
| `BALANCE_UNCHANGED_WITH_TRAFFIC` | 余额**不变**（差额 = 0），而窗口内本网关 token 用量 > 0 | 查得值可能是缓存 / 套餐口径，或查询端点已失效在回陈旧值 |
| 余额**上升** | — | **不告警**（充值 / 上游按周期重置，都正常） |
| 任一端的 `totalBalanceCents` 为 `null` | — | **不判定**（未知与未知之间没有"差额"可言） |

- 出口只有两个：一条 `warn` 日志（只记**码 + upstreamId + 窗口**，不记 key 明文，ADR-0006 同纪律）+ 一个进程内计数 `balance_drift_total{code}`，经 §14.3 只读暴露。
- **不进 `ERROR_CODES`、不影响任何 HTTP 状态、不拦任何请求、不改任何数**。它是"给管理员看一眼"的东西，不是闸门。
- 阈值与灵敏度（连续几次才算）**不进契约**，PM 可后补；本版写死一条：至少在 2 条快照之后才开始判。

## 决策 5：边界（明确不做）

- **不做事前拦截（准入闸门）**。本版既没有扣减也没有本地余额，拿"最近查得值"去拒请求 = 拿一个可能已过期的数把人挡在门外。现有准入已有三条（用户组 RPM / TPM / 日配额），不新增第四条。
- **不引入单价、不做扣减、不做账单**。见决策 0 与被撤销的上一版。
- **不下线 `costCents`**。§6 的金额口径与 `usage_logs.cost_cents` 原样保留（它只是个估算展示），本版**不把它升级成账**。
- **不动 `GET /api/stats/balance`**（ADR-0003 三口径）**与三个手动刷新端点**：字段、形状、语义零变更。
- **`src/gateway/` 零改动**。本版全部落在管理面（定时器 + 读路径），`/v1/*` 请求路径新增同步读写 = **0**，TTFB 判据自动满足。
- **不追溯已有值**：快照从本版上线后开始记，"上周五多少"仍然是查不到的（历史不能凭空造）。

## 被撤销的上一版（原 0017：append-only 计费账本 + `request_id` 幂等扣减）

原方案（新表 `billing_ledger`、按单价 × token 本地扣减、`request_id` 幂等、行级对账、`availableCents` 派生）**作废**，撤销理由是产品判断，不是实现问题：

1. **它算的是一个手上已经有的数**。余额本来就能从上游查到（M6-A 已落地并上闸），本地再推算一份，等于多造一台机器去生产同一个量、且这个量必然更不准。
2. **自用项目，不存在"对账"这个需求**。账本的全部复杂度（幂等键、行级对账、补扣、保留期不可裁剪、单价快照）都是为"必须能证明收了多少"服务的；这里没人需要那个证明。
3. **它引入的失败模式比它解决的问题多**：账本与日志同事务、`NULL request_id` 拒收、删上游不删账、单价未知计 0 与"确实免费"不可区分 —— 每一条都是新的静默态。
4. **它把两套口径同时放进系统**（上游查得 vs 本地推算），而 M6-A 好不容易建立的"未知就是未知"的信任，正好死在"两个余额数不一致"上。

## PM 验收裁定（2026-10-07，实现期约束）

接口阶段由 PM 逐条核实（对 `0c175b0`：2 files `+292/−2` 全在 `docs/`、四闸绿、`spentCents`/`availableCents`/`billing_ledger` 零残留、被撤销草稿从未进 git）后放行实现。三条口径裁定 **全部同意**：取不到保留旧值不清零（清零点 = 主动销毁唯一的事实）、单 key 手动刷新不写快照（宁缺一个点，不造假点）、漂移只能方向级（这条反过来自证了改向是对的）。另加两条**实现期纪律**（改的是纪律不是口径）：

1. **保留期清理必须是周期任务**，不能只是启动跑一次 —— 长跑进程永不清理 = 快照表无界增长。
2. **首个自动同步周期也要抖动，并发上限复用既有全量刷新的上限**。

两条都已按上文落地（决策 1 的触发段、决策 3 的保留期段）。

## 备选方案

| 方案 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A. 保持纯手动**（不做 M6-C） | 现状 | 余额永远停在最后一次点击；趋势与漂移都无从谈起 | **否**（本版的起点） |
| **B. 自动同步 + 快照 + 方向级漂移**（本 ADR） | 决策 1–4 | 新表 1 张 + 调度器 1 个 + 只读端点 1 个；上游每 15 分钟多一次余额查询 | **采纳** |
| **C. 自动同步 + 本地扣减账本** | 上一版 | 见上节四条 | **否**（已撤销） |
| **D. 只自动同步，不留快照** | 省一张表 | "上周五多少""余额为什么不动"仍然答不了；决策 4 无从落地 | **否** |
| **E. 查不到就把 `balance` 清成 `NULL`** | 语义"更干净" | 会**丢掉已知的事实**（旧值 + 它真实的查得时刻），且与"未知 = 从没查到过"混成一类 | **否**（决策 2） |
| **F. 漂移按金额量级比对** | 看起来更"准" | 需要单价 → 就是被撤销的 C | **否**（决策 4） |

## 验证（实现阶段的用例清单 —— 本 ADR 只冻判据，用例随实现提交）

1. **间隔与抖动**：给定 `base` 与注入的随机源，延迟必落在 `[0.9, 1.1] × base`；`BALANCE_SYNC_MINUTES=0` 时**不注册定时器**（`auto.enabled=false`、`nextRunAt=null`）。
2. **退避**：连续 1/2/3… 次失败 → 30m / 1h / 2h …，封顶 6h；一次成功归零；`skipped`（没配查询方式）**不推进**退避。
3. **单飞**：上一轮未结束时该上游被跳过（不并发、不排队、不堆积）。
4. **NULL 口径**（三条，逐条钉）：查失败 → `balance_cents` 与 `balance_updated_at` **都不变**；`unknown` 同上；从未查到过 → 保持 `NULL`（**断言不出现 `0`**）。
5. **快照**：整上游同步后新增 1 行且 `total_balance_cents` 与三计数正确；**单 key 手动刷新不新增快照行**；全未知时 `total_balance_cents = NULL`（不是 0）。
6. **删上游后历史可读**（对偶 ADR-0016 那笔）：带快照的上游按依赖序物理删除仍 `204`，快照行仍在且 `upstream_name` 可读。
7. **漂移两态**：造「余额降 + token=0」→ `BALANCE_SPENT_WITHOUT_TRAFFIC`；造「余额平 + token>0」→ `BALANCE_UNCHANGED_WITH_TRAFFIC`；余额上升**不告警**；任一端为 `null` **不判定**；断言只产生 warn + 计数，HTTP 状态与库值零变化。
8. **`asOf` 不撒谎**：查失败后 `balanceUpdatedAt` 不变（与 4 同源，但对读路径单独断言一次）。
9. **热路径零回退**：本版 `/v1/*` 请求路径零新增同步读写；`ΔP50 ≤ 1ms / ΔP99 ≤ 5ms`（沿用 M6-A/B 冻结判据，多轮取中位数）。
10. **零新增枚举 / 零迁移**：`ERROR_CODES` 与 `GATEWAY_ERROR_CODES` 长度不变；`SCHEMA_VERSION` 不变。

闸门沿用现有四闸（`typecheck` / `vitest` / `check:secrets` / git 干净），**无新增 CI 闸、无新增测试基建**。

## 已知缺口

- **不是每个上游都吐余额**：有的只给账号级、有的只回套餐剩余、有的压根没接口。拿不到就是 `null`（"未知"）——这正是 `balance_cents NULL` 的语义，本版不为此加任何兜底。上游配不出查询方式时刷新计 `skipped` + `hintCode=BALANCE_QUERY_UNSUPPORTED`（ADR-0012），前端引导配置，不进任何"失败"口径。
- **快照不能重建历史**：本版上线前的时间点查不到，趋势图从左向右生长。
- **漂移是提示不是判据**：没有单价 ⇒ 判不了"钱对不对"，只能判方向。若将来真要判钱，那是一个新决定（且必须先把被撤销的上一版重开，届时走新 ADR）。
- **单 key 手动刷新不留快照**（决策 3 的取舍）：代价是趋势线在那段时间不产生点，而不是产生一个半新半旧的假点。

### 补遗 1：决策 5 那句「TTFB 判据自动满足」**后半句作废**（前半句仍真）

本 ADR 决策 5 原文：

> **`src/gateway/` 零改动**。本版全部落在管理面（定时器 + 读路径），`/v1/*` 请求路径新增同步读写 = **0**，TTFB 判据自动满足。

逐分句判：

| 分句 | 判定 | 依据 |
|---|---|---|
| 「`src/gateway/` 零改动」 | **仍真** | 本版确实没动内核 —— 但这只说明"耦合不在这一层"，不是"无耦合" |
| 「`/v1/*` 请求路径新增同步读写 = 0」 | **仍真** | 请求路径上确实零新增读写 |
| 「TTFB 判据自动满足」 | **假** | 耦合发生在**出口 IP 的请求预算**这一层，比 HTTP 低。管理面每 15 分钟打出的 26 次请求与数据面**共用同一条 5–6/窗口的预算** ⇒ 自动同步能把数据面挤到 429，而 TTFB 指标看不见这件事 |

**订正后的文案（供契约 §14.1 第 3 条与 §14.5 采用）**：

> **`src/gateway/` 零改动；`/v1/*` 请求路径零新增同步读写。** 但这**不等于**"与数据面无耦合"——
> 自动同步与数据面**共用同一出口的请求预算**（ADR-0020 §16.7 Tier 1.5），该预算是**隐性约束**，
> 不体现在请求路径的耗时上。**故自动同步的间隔必须由出口预算标定决定**（标定前按最坏情况 =
> 出口地板取值，见 §16.7 与本补遗 2）；TTFB 判据**不再自动满足**，须与出口预算共同验收。

### 补遗 2：退避判据改为「有值 + 成功比例 + 无 429 证据」，修「永不退让」

现状（`src/api/balance-sync.ts:204`）：`judgeRound` 只要 `ok - unknown > 0` 即判 `value` ⇒ `consecutiveFailures` 归零。
在出口预算这条约束下这是**结构性缺陷**：26 把里 6 把成功、20 把撞 429 也读作"健康"，`nextAttemptAt` 照 15 分钟
排回去 ⇒ **每 15 分钟准时再烧一次窗口，永不退让**。而实测已证出口预算按 IP 聚合、**放缓不减少被拒次数**
⇒「退让」是唯一有效动作，恰恰是现在做不到的那个。

**裁定（拟）**：归零条件由"有值"改为**三条同时成立**：

| 判据 | 内容 | 理由 |
|---|---|---|
| 有值 | `ok - unknown > 0`（不变） | 现状 |
| 成功比例 | `(ok - unknown) / (checked - skipped) ≥ 80%` | **分母排除 `skipped`**：没做的事不进分母，否则"26 把里 20 把没配查询方式"会把健康的 6 把算成 23% |
| 本轮无 429 | `rateLimited == 0` | 429 是**出口挤压**的直接证据，与比例无关：25 把成功 + 1 把 429 也退让一档。这是本补遗的核心 |

- 不满足归零条件且**确实发起了请求**（`checked - skipped > 0`）⇒ 推进退避（沿用 `min(base × 2^n, 6h)`，`n` = 连续计数）。
- `checked - skipped == 0` ⇒ `noop`，不推进不归零（现状不变）。
- 阈值 80% **不进契约**（实现常量，PM 可后调）；进契约的是**归零条件的形状**。连带影响：§14.3 的
  `consecutiveFailures` / `nextAttemptAt` 语义从"最近一轮有没有一把成功"变成"最近一轮整体健康度"，该段回显说明要跟着改。
  （第三条判据「本轮无 429」与 PM 裁决原文「**429 占比高时走退避**」同向，且更严 —— 25 把成功 + 1 把 429 也退让一档。）
- **`rateLimited` 计数**含**本地合成**的 429**（ADR-0021 决策 4a 的标记头识别）：闸接线后，出口预算耗尽会由
  fetch 装饰器合成一个带标记头的 429，它**同样计入本判据**。这是**有意**的 —— 自拒绝与上游 429 都指向
  "这一轮的额度不够"，退避该退就得退；且这样「永不退让」这条缺陷在闸接线的**当天**就消失，不必等标定。
  与 ADR-0021 决策 5 **不冲突**：那条管的是**冷却**只由上游证据推进，本条管的是**退避**（两者是不同的动作）。
- **代价（明写）**：一批**坏 key**（例如 7 把已失效的 401）会把这个上游的自动同步拖慢到 30m / 1h ——
  而这些 key 的正确处置在 §15 的重登路径上，不在同步节奏上。这个代价是**故意付**的：相比之下，
  "用共用的出口预算给 7 把死 key 每 15 分钟烧一次"更贵，且它同时烧掉数据面的额度。
- **实现暴露（零新字段）**：429 计数不需要新列 —— `QueryExecution.httpStatus` 已有，`summarize()` 与
  `groupByUpstream()` 都能现算；只需把该计数带进 `UpstreamRefreshResult`（收尾钩子用的**内部**类型，不出 REST 面
  ⇒ §14.2 的三型计数口径**零变更**）。

### 补遗 3：429 不再报成「上游坏了」（`hintForSummary` + 一个新 `hintCode`）

现状（`src/api/services/balance-query.ts:84`）：`hintForSummary` 只特判 401/403，其余 `failed` 一律 →
`BALANCE_UPSTREAM_UNREACHABLE`。于是**我们自己把出口预算烧干**这件事，在操作面显示成"上游失败 20 把"，
排障方向直接反掉 —— 与 ADR-0011 §4 修掉的是同一类错误：**把自己这边的问题报成对面坏了**。

**裁定（拟）**：新增**第 5 个 `hintCode`** `BALANCE_EGRESS_RATE_LIMITED`，优先级插在
`BALANCE_AUTH_REJECTED` 与 `BALANCE_UPSTREAM_UNREACHABLE` **之间**（最小改动：只动现有三元表达式的 else 支）：

```
failed > 0 时：
  authRejected > 0  → BALANCE_AUTH_REJECTED          （最具体且要用户动作，保持第一）
  rateLimited  > 0  → BALANCE_EGRESS_RATE_LIMITED    （★ 新增）
  否则              → BALANCE_UPSTREAM_UNREACHABLE
```

- `hintText` 文案**不得越证据**：429 无专用码、出口级与 key 级同形（§16.7 v1.6.2）⇒ 措辞写
  "**本次请求被限流（429）**：可能是出口 IP 的请求预算已用尽，也可能该 key 自身撞到限额；稍后重试即可，
  **不必改配置**"，**不得**写成"出口被限流"这类确定性归因。
- `hintForQueryResult`（自测那条同步路径）同批加 429 分支，口径同上 —— 两条路径共用一个判据，
  否则又会出现"刷新说限流、自测说不可达"的自相矛盾诊断。
- **本地拒绝同样落这个码**（标记头识别，ADR-0021 决策 4a）：闸接线后，出口预算耗尽由我们自己合成 429，
  走的是同一个 429 分支 ⇒ 同样报 `BALANCE_EGRESS_RATE_LIMITED`。文案已按"不越证据"写（"可能是出口预算、
  也可能是该 key 自身"），**不需要为自拒绝另造第二句话** —— 这正是决策 4 让本地拒绝与上游 429"证据面同形"的目的。
- **这不是零成本改动**，三处后果一起记：
  1. `HintCode` **四值 → 五值**，而契约 §14.2 现写"`hintCode` 四值**不变**" ⇒ **该句作废**；契约升 **v1.7.0**（枚举新增，非破坏）。
     **§2 引导表要改的是一行"加" + 一行"改"**：加第 5 行 `BALANCE_EGRESS_RATE_LIMITED`，**并且**把
     `BALANCE_UPSTREAM_UNREACHABLE` 的触发列从"不可达 / 超时 / 非 2xx"改成"不可达 / 超时 / 非 2xx（**429 除外**）"。
     **只加行不改列 = 触发条件互相包含**：429 同时命中两行，前端取到哪一行就退化成行序这样的实现细节，
     而现行 §2 那句"非 2xx"正是本补遗要消灭的**误读本体**（先改列才算真的摘出来）。
     **触发列全仓只有 §2 一处**：§14.2 `:1387` 那张表是**写库纪律**表（不可达 / 超时 / 非 2xx ⇒ **一个字都不写**），
     429 无论上游的还是本地合成的**同属"不写"** ⇒ 那张表**不动**，别顺手给它加"429 除外"（会把"失败不写库"这条纪律改坏）。
  2. **画师侧是硬依赖，不是可选**：`web/src/components/BalanceHint.tsx` 的 `HINT_CONFIG` 是**穷尽的** `Record<HintCode, …>`，
     且 `config.title` **无兜底** ⇒ 新码先到、前端后到会**当场抛错**（整个组件渲染失败，不只是缺文案）。
     故本批**必须**同批加第 5 项，**并**补一个兜底分支（`?? fallback`）—— 老前端 + 新后端的部署顺序无法保证。
  3. `web/src/api/types.ts` 的 `HintCode` 联合类型同批加成员。
- **备选（否）**：429 仍报 `BALANCE_UPSTREAM_UNREACHABLE`、只换文案。码与文案是 1:1（`hintText(code)`），
  换文案就得按码分叉，等于偷偷加了一个码；而给"上游不可达"配一句"出口限流"的说明，正是本补遗要消灭的误读。

### 补遗 4：漂移判据加**前置条件**（`judgeDrift`）并给 `knownKeyCount` 定语义 —— **明确不收窄 `usedTokens`**

现状两处（`src/api/balance-sync.ts:262` / `:288`）：`usedTokens = sumTokensBetween(db, upstreamId, prev.ts, ts)`
是**上游级全量**流量；而被 429 冻住的 key"一个字都不写"（决策 2 正确）⇒ 它们的余额停在旧值，
**但流量照样计进 `usedTokens`**。于是被出口限流打断的一轮会得到"余额合计不变（大部分 key 没读到）+ 窗口内有流量"
⇒ **`BALANCE_UNCHANGED_WITH_TRAFFIC` 被我们自己的 429 点着**。这条提示的含义是"查得值可能是陈旧的、没在动"，
而此刻它指向的是一个**根本没查**的 key —— 纯假信号。

**裁定（拟，两件都做）**：

1. **判定加一条前置条件**：本轮**存在出口级限流（`rateLimited > 0`）时不判定**。理由与决策 4 的
   "任一端为 `null` 不判定"同源：**那条差额里混着"我们没读到"的 key，拿它去下"读数不新鲜"的结论必然误伤**。
   宁缺勿假这条纪律在本 ADR 已用了两次（决策 2 不写 0、决策 3 单 key 不写快照），这是第三次。
   **不新增列、不新增计数、零 DDL**：判据输入就是补遗 2 已经要算出来的那个 `rateLimited`。
2. **`knownKeyCount` 语义在 §14.3 成文**：它是 **"余额当前有值的 key 数"**（含本轮没读到、沿用旧值的 key），
   **不是"本轮查到的 key 数"**；`unknownKeyCount` 才是"查了但没值"（`balance_cents IS NULL`）。
   部分冻结的一轮里这两者会**同时偏离直觉**，前端不得用 `knownKeyCount` 的变化去推"这轮查到了几把"。

- **同时否掉一个备选**：把 `usedTokens` 收窄成"只算本轮真的查到的 key 的流量"。它看着更"对齐"，
  但会引入**第二个口径**：`usage_logs` 记的是"这把网关 key 被用过"，一把余额查失败的 key 仍在转发流量 ——
  把它从窗口流量里抠掉，等于让系统对"这条上游真的有人在用"失明，而 `BALANCE_SPENT_WITHOUT_TRAFFIC`
  （"余额在掉、我们这边零流量 ⇒ 别处直连在用"）正是靠全量流量成立的。
  **一个判据的两个输入各用一个口径，好过让两个判据共用一个错口径。** 本次**收紧的是判定的前置条件**（第 1 条），**不是流量口径**。

> **⚠️ 本补遗唯一未获明示裁定的一处**：PM 上一轮给的是两个选项（收窄 `usedTokens` 口径 / 或只登记
> `knownKeyCount` 语义），本文落的是**两者的合成** —— 取第 2 条（登记语义）+ 一个**前置条件**（有出口级限流则不判定），
> **明确不取**"收窄 `usedTokens`"。理由已写在上面（收窄会让 `BALANCE_SPENT_WITHOUT_TRAFFIC` 失明，且引入第二个口径）。
> 若 PM 判"只要登记、不要前置条件"，**删掉第 1 条即可**，两段相互独立、不影响落地清单其余各行。

| ② | §16.7 计价单位 | **一次上游 HTTP 请求 = 一枚 token**（**不是一把 key**）。§15.5「刷新 = 2 请求/账号」据此换算：刷新一个账号消耗 **2 枚**，一轮 27 账号 ≈ **54 枚** | 路由者 §3 |
| ③ | §16.7 `RATE_LIMITED` 触发条件 | 加**第四条路径「出口预算耗尽」**：**0 次真实尝试、不计任何 key 健康、不写出口冷却、一律带 `Retry-After`**；与 §10「0 次真实尝试不是上游故障」同刀。**零新码值**（复用 `RATE_LIMITED`，与 ADR-0011 的池饱和同形） | 路由者 §4 裁定 2/3 |
| ④ | §16.7 保留额度 | 写一句「**管理面消费者不得占用数据面保留额度**，否则单次人工刷新可合法饿死客户端流量」，并登记占位值 `reserveForData: 1`（与 `capacity: 5` 同条） | 路由者 §4 裁定 1 + PM 裁定 |
| ⑤ | §16.7 键一致 | 桶钥匙 = `egressId`，与 Tier 1 冷却键**同源**；Tier 2 落地时两处**一起**换成 `egress_proxies.id`；**禁止"桶按代理、冷却按 host"的分裂脑**；**`egressHostOf` 随迁退休**，归一化唯一入口 = `egressIdOfUrl`（解析失败 → `null` → 放行） | 路由者 §4 裁定 4 |
| ⑥ | §15.5 表 + 0.6s 间隔 | 「27 个账号一轮刷新 ≈ 1 分钟」**必须重算**，新口径 = `ceil(总请求数 / 有效容量) × 窗口`，**有效容量要扣掉数据面保留额**（占位值下 = 4）。**契约只写最保守的一条**（路由者终版三口径，全表见 ADR-0021 决策 8）：`ceil(52/4)×60s` = **13 min**（26 key 记账）/ `ceil(54/4)×60s` = **14 min**（27 账号记账，**本节取这条**）；**恒定补桶 ≈10.4 min 只作实现说明，不进契约承诺**。并写清「**0.6s 账号间隔保留**为账号级**内层纪律**，出口级速率**由 Tier 1.5 取代**」 | 路由者 §8 + 终版 §10 排期账 |
| ⑦ | §16.7 冷却写入来源 | **两条来源分列**：出口冷却**只由上游证据写入**（同出口第 2 把不同 key 亦 429）；**桶拒绝**走"终止本轮轮换 + `Retry-After`"，**不推进阶梯、不写冷却、不发射 §7 帧** | 路由者 §4 裁定 2 + PM 裁定 |
| ⑧ | §16.7 终态形状 | 桶拒绝的客户端终态**必须是 `429 RATE_LIMITED` + `Retry-After`，不是 `502 UPSTREAM_ERROR`**；`attempts` 恒为 **0**（本地拒绝 = 0 次真实尝试，收尾分型 `attempts === 0` 的分支必须成立）；**不写 key 失败行**（KeyPool / `key_runtime` 健康计数不变；管理面任务级 `failed` **照记** —— 那是任务结论，不是 key 归因）；事件流**不得出现假失败行**、`inner` fetch 零调用、出口 `consecutive`/`until` 逐字节不变。**只断言"零上游调用"的验收会按 502 通过**，故这四条断言必须落进用例清单（见下「验收口径」，代码锚点见 ADR-0021 决策 4b） | 路由者 §4「实施细则 6」+ 终版 §10 清单第 8 条 |
| ⑨ | §16.7 + §15.5 检测器转正 | `egressLimitedOnSecondKey` **默认值替换**（换掉 `neverEgressLimited`）+ `distinctKeysFailed429` **参数化为「当前作用域」**（`request` / `batch`）；两个识别器退休，判据唯一化到闸内 | §16.7 v1.4.8 裁定 ① 的启用 + PM 明文放行 |

- **⑦ 与 §7 帧的连带（要一并改，不能只改 §16.7）**：检测器转正 ⇒ **上游确认**的出口级 429 会真的置起冷却
  ⇒ §7 `egress_cooldown` 帧**从此开始发射**，v1.4.9「本期不发射 / 前端不得接线」随之作废；
  但**帧的成因只有"上游确认"一种**，桶拒绝**不发射帧** —— §7 的「本期状态」段与 §16.7 两处措辞必须同时改，
  只改一处就会出现"契约说帧会来、实际桶拒绝也发帧"或反过来的错读。
- **① 的作用域必须点名**，因为 §16.7 原文的作用域（v1.4.8）是**按"刷新 / 建 key / 重登 / 探活 / 数据面"写的**，
  而 §15.2 那六个端点在契约里是**另一节**、字面上不在那句话里；不点名就等于"管理面最重要的一半消费者没进闸"。
- **本节全部容量口径都是「单出口」口径**（Bo 2026-10-07 的出口 IP 约束；容量是**每个出口**的数，
  推理与触发条件见 ADR-0021 **决策 8 v5**）：② 的"一枚 token = 一次上游请求"、⑥ 的"有效容量 4 枚/窗口"
  与 ≈14 分钟，前提都是**一轮的全部请求从同一个出口打出**（本期部署形态，ADR-0020：「1 个出口 IP +
  27 个账号 + 全部 key」）。**出口 > 1 时这些数逐出口各自成立**，不得跨出口加总 ——
  落 §15.5 正文时把这句话一并写进去，否则口径会漂成"总量够就行"。

### 补遗 6：重新开启自动同步的**量化门槛**（不是"标定完就开"）

PM 裁决第一条要求先 `BALANCE_SYNC_MINUTES=0`，但"什么时候能开回来"必须是**可判定的数**，否则它会变成一句口头承诺：

> **门槛**：15 分钟内管理面可用的 token 数 **≥ 一轮全部请求数**（占位 = 27 账号 × 2 = **54 枚**），
> **且数据面满载时仍满足**。

- 占位值下管理面 = `capacity − reserveForData` = **4 枚/窗口**（**瞬时上限口径**，也是契约唯一承诺的那条）⇒
  **60 枚/15min ≥ 54 枚** ⇒ **跑得完，但余量只有 6 枚（10%）**；按 26 把 key 记账（52 枚）余量 **8 枚（15%）**。
  **两种记账都不够一整轮重试** ⇒ 结论与口径无关：**不是跑不动，是重试即欠账**。
  **数据面满载时保留额归数据面，管理面吞吐不承诺** ⇒ **不满足**第二条。**故占位值下不重开**，
  与 PM「先关自动同步」的裁决一致。**恒定补桶 ≈10.4 min 是实现说明，不得用来放宽本门槛** —— 门槛取瞬时上限。
- 这条门槛的必要性在于：**"余量 10%"与"跑不动"是两回事**。前者是"能跑但一有重试就欠账"，
  后者会让人得出"自动同步永远不该开"的错误结论 —— 而容量回填到 20+/窗口 后它是可以开的，
  且**只改数、不改代码**（ADR-0021 决策 8 的回填纪律）。
- 门槛数随 `capacity` / `reserveForData` / 账号数**一起重算**：这三个数任一变化，本节结论即失效。
- **本门槛按「单个出口」记（Bo 2026-10-07 的出口 IP 约束）**：前提是**一轮的全部请求都从同一个出口打出** ——
  本期部署形态正是单出口（ADR-0020：「1 个出口 IP + 27 个账号 + 全部 key」）。**出口 > 1**（Tier 2
  `egress_proxies` 落地，或 key 被分布到多个出口）时，门槛**逐出口各自成立**：
  每个出口上"**该出口承运的请求数** ≤ **该出口管理面可用 token 数**"，且 `capacity` **逐出口回填**。
  **不得把多个出口的 token 加总去凑一轮总数** —— 那是把"总量够"错当"某一个出口够"，
  与决策 2 的"同一出口两个键"同一种账目错误，只是量纲从桶换成出口。
- **标定输入的来源在这里钉死**（与 ADR-0021 决策 8 的标定纪律同一句）：标定必须从**承运那 26 把 key 的
  同一个出口 IP** 打；从别的机器、别的出口量出来的数字，量的是**另一个桶**，与本门槛无关。
