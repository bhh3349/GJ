# ADR-0035：管理组与首库种子 —— 管理员账号为什么必须持有一把网关 key

- 状态：**已接受（2026-10-17，Bo 指示「第一个用户组没有管理组，管理员的账号无法使用路由」）**
- 关联：契约 **§4**（`Group` 对象与组端点不变，用户端新增一条 PATCH）、
  **§19.7**（「没有任何改用户的端点」这句口径订正为"只有一条 PATCH，且只改 `groupId`"）、
  §10（`/v1/*` 口径不变）、ADR-0034（`group_id` 列与"现读"性质是本篇的前置）
- 车道：`src/db/repo/`（一个新查询 + 一处错误翻译）+ `src/api/auth.ts`（引导条件分支）
  + `src/api/routes/users.ts`（一个新端点）+ `web/`（归属组可改）。
  **`src/gateway/` 零改动** —— 本 ADR 不碰选路、不碰限流、不碰 KeyPool
- 触发：Bo 报「用户组没有管理组，管理员的账号无法使用路由」——
  即"功能做了、但管理员自己用不了"

## 背景：一个"每一环都在、整条链不可达"的形状

实测（本机实例，`admin` 用自己的会话）：

```
GET /api/console/session  →  {"username":"admin","role":"admin","groupId":null}
GET /api/console/keys     →  {"groupId":null,"keys":[],"assigned":false}
```

把这条链拆开看，**每一环都是好的**：

1. `groups` 表、`POST /api/groups`（建组即自动签发第一把网关 key）、
   `gateway_keys` 的 `key_hash` 鉴权、组级 rpm / tpm / daily_quota 限流 —— 全套可用；
2. 管理面有 `GroupsPage`：建组、签发 key、重置、吊销都在；
3. `/v1/*` 认的只有 `key_hash` → 组上下文，**从不看后台身份**。

缺的是**连接点**：`admin_users.group_id` 对管理员是 `NULL`，而
**没有任何端点能把一个已存在的账号放进组里**。建号时能带 `groupId`
（`POST /api/users`）—— 那是唯一一次"把一个账号放进组"的机会，
而 §19.7 明写"换角色 / 换组 / 忘口令的答案一律是删掉重建"：
`updateUser` 在仓储层只动 `groupId` / `displayName`，却**刻意没挂路由**。

于是管理员要拿到一把能打 `/v1/*` 的 key，只剩两条路：

- **删掉自己的账号重建** —— `deleteUser` 的第一条下限（不能删自己）直接挡住；
- **手改数据库** —— 这不是功能，是逃生口。

**"功能做了但用不了"就是这个形状**：不是缺能力，是缺一条从"我的账号"
到"我的配额池"的正常路径。而且它对**每一个**新部署都成立 ——
管理员建站的第一件事通常就是给自己发一把 key 试试通不通。

## 决策

### 1. 新库种子「管理组」，并把首个管理员放进它

`bootstrapAdmin`（`src/api/auth.ts`）在"库里一个账号都没有"那一刻多做两步：

1. 建一个名为 `管理组` 的组 —— **复用仓储层 `createGroup`**，因此自动走 §4 的
   C1（建组即签发第一把网关 key），不另写一条插 key 的路径；
2. 把刚建的那个管理员 `group_id` 指过去。

明文 key 只在进程内存里存在一次，写进**启动日志一行**并明确标注"仅此一次"
（理由与反向代价见「遗留 1」）；落库的仍然只有 `key_hash` 与掩码，**§4 铁律一字不改**。

**为什么种子必须待在"库空"这个分支里**：那是"这个库是新的"的**唯一**判据。
把它放进 `migrate()` 会让**每一个**测试 harness 都长出一个组
（`openDatabase` → `migrate()` 是所有用例的公共前置），而既有用例里有按
**全局计数**断言的 —— 例如 `console.spec.ts`「消费面没有 key 签发路径」那条，
判据是 `SELECT COUNT(*) FROM gateway_keys` **恒等于 1**（"没落一把新 key"）。
种子进了 `migrate()` 就等于悄悄改了几十条用例的前置条件：红的会是它们，
而它们测的根本不是这件事。**判据要落在最窄的那个分支上，不是最方便的那个。**

**为什么建一个"真的组"而不是给管理员插一把隐式 key**：
`gateway_keys.group_id` 是 `NOT NULL`（`src/db/schema.ts:118`），
key 必须挂在某个组上；而一个"看不见的隐式组"会让管理员在管理面
看到自己不认识的配额、且删不掉（删了 admin 又没 key 了）。
种子用的是**普通组**：它出现在 `GroupsPage` 里，管理员能改它的配额、
能给它加更多 key、也能删掉它 —— 而这正是他要的（给自己调限流），不是特权旁路。

**老库不动**：`bootstrapAdmin` 的第一行是 `if (adminCount(db) > 0) return;`，
升级上来的库**零动作**。老库管理员要组，走本版新增的那条 PATCH（明确、可见、有审计），
**不做**"启动时发现 admin 没组就替他补一个"：那会在每次启动替用户做一个他没要求的
配额决策，而且会对**每一个**没组的管理员生效 —— 包括那些刻意不给自己发 key 的部署。

**幂等**：种子落在一个天然只走一次的判据后面。如果 `groups` 里**已经有**同名组
（老库有组、账号全被删空这种边角），种子**复用**它、只记一行"已存在、未新建 key"，
**不**再签发第二把（新生的 key 意味着新的一份可被滥用的凭据，而没人要求过它）。

### 2. 组归属从"删了重建"变成一条 PATCH —— §19.7 口径订正

新增 `PATCH /api/users/:username`，body **只接受 `groupId`**（`{groupId: string | null}`），
其余一律不动：

| 字段 | 可改 | 为什么 |
|---|---|---|
| `groupId` | ✅（本版新增） | 它是"这个账号归哪个配额池"，**不是身份**。归属错了要能修 —— 逼人删号重建的代价是连带吊销他的会话、并把他从审计的 actor 里抹成两截 |
| `role` | ❌ | §19.7 那条理由原样成立：可改的 `role` 让"把自己降级"变成一次普通请求，而降完改不回来（不可逆） |
| `password` | ❌ | 忘了口令 = 删掉重建；重设口令会让"谁在什么时候知道过这个口令"变成一笔糊涂账 |
| `displayName` | ❌（本版不开） | 仓储层 `updateUser` 支持它，但**本版不给它开口子**（见下） |

**为什么 `groupId` 可改而 `role` 不可改**：两者的失败形状不同。
改错组 = 那个人进了错配额池，改回来即可，而且**下一个请求就是新的组** ——
因为 `SessionInfo.groupId` 每次鉴权从 `admin_users` **现读**（ADR-0034 落下的性质，
`src/api/auth.ts` 的 `touchSession`），本版白拿这个正确性，不需要"改完强制重登"。
改错角色 = 一个管理员把自己或别人降成普通用户，而那是不可逆的。

**为什么不顺手把 `displayName` 也开了**：本版的每一行都要有"为什么必须现在加"的理由，
`displayName` 没有（没人报它的 bug）。一次开两个字段的代价是
"这条 PATCH 到底为谁服务"从此说不清，下一版要拆开会更难。

**未知 `groupId` 必须是 `400` 而不是 `500`**：`foreign_keys = ON`
（`src/db/database.ts:32`），一个不存在的组 id 会撞 FK 约束。
`users.ts` 仓储层的 `updateUser` 目前**没有**把这条错误过 `translateWriteError`
（`createUser` 过了），所以本版要顺手补上 —— 一个坏入参变成"服务端炸了"
是最容易被误诊成产品故障的一类错。

### 3. 管理员在网关面上**不特殊**

管理员的 `admin_users.group_id` 与普通用户的**是同一列**，`/v1/*` 鉴权链上
没有任何"这是管理员"的判定。**这条明确写下来是为了防止将来有人为了"管理员的便利"
在这条链上加分支**：一旦 `/v1/*` 开始看后台身份，网关面就有了第二个授权维度，
而那个维度上的每一条判据都要单独验证 —— 现在它只有一条：`key_hash` → 组。

### 4. 管理员的"用路由" = 管理面那把 key，不是消费面

管理员拿 key 的地方是 `GroupsPage`（管理面），不是 `/console`。
他的 `role` 仍然是 `admin`，消费面刻意不给他管理入口。
**"管理员能用自己的 key 打 `/v1/*`"与"管理员能用消费面"是两件不同的事**，
本 ADR 只做前者。

## 影响面

| 面 | 变更 |
|---|---|
| `/v1/*`（网关面） | **零变更**。管理员的 key 走的是与任何用户完全相同的 `key_hash` 鉴权链 |
| `src/gateway/` | **零改动**（选路 / 限流 / KeyPool / cooldown 一行不动） |
| `/api/users` | **新增 1 个端点**：`PATCH /api/users/:username`（`{groupId}`） |
| 新库首启 | **多两个动作**：建「管理组」+ 把首个管理员放进去；启动日志多一行明文 key |
| 老库升级 | **零动作**（`adminCount > 0` 直接返回） |
| DDL | **零**。`groups` / `gateway_keys` / `admin_users.group_id` 全是既有表列，`SCHEMA_VERSION` 仍为 **2**、零迁移分支 |
| `ERROR_CODES` | **零新增**（未知组 = `INVALID_PARAM`，走既有 `translateWriteError`） |
| 审计动作 | **新增 `user.update`**（改归属是管理动作，§6 最小集覆盖） |
| `web/` | `UsersPage` 加"归属组"编辑（一条 PATCH 的出口）；**零新依赖** |

## 判据

| 用例 | 钉住什么 |
|---|---|
| 新库 + `ADMIN_PASSWORD` → 库里恰有一个 `管理组`，首个管理员的 `group_id` 指向它 | 开箱即用 |
| 引导那一刻签发的那把 key，拿它打 `/v1/models` → `200` | **"管理员账号能用路由"是可执行的事实**，不是"表里有条记录" |
| 删掉那个组 → 管理员账号仍在、`group_id` 退回 `NULL` | 复用既有 `deleteGroup` 的成员处置（组是普通组，不是特权） |
| `PATCH {groupId: 存在的组}` → `200`，且该用户**同一个会话**打 `/api/console/session` 立刻看到新组 | `groupId` 现读：改动即时生效，不需要重新登录 |
| `PATCH {role: 'admin'}`（或任何其它字段）→ 角色与其余字段不变 | 只有 `groupId` 可改 |
| `PATCH {groupId: 'grp_不存在'}` → `400 INVALID_PARAM`，**不是 500** | 坏入参不是服务端故障 |
| 连起两次（第二次 `bootstrapAdmin` 是 no-op）→ 组数仍为 1、没有第二把 key | 种子不长尾巴 |
| 老库（已有账号）引导 → 组数不变、无新 key | 老库不被动 |

**变异验证**（改坏 → 红 → 还原，实测记录）：

| 变异 | 结果 |
|---|---|
| 删掉"把首个管理员放进管理组"那一步 | **红** ← `runtime.spec` 开箱即用那条（`/v1/models` 从 200 变 401） |
| PATCH 的 schema 列上 `role` 并透传 | **红** ← `console.spec` 角色不可改那条（role 从 `user` 变 `admin`） |
| 把种子从"库空分支"挪进 `migrate()` | **红** ← 16 个既有用例（`store.spec` / `model-probe.spec` 等），它们的前置库里凭空多出一个组与一把 key |

**实测验收**（v1.15.6 交付时真跑过，不是设计意图）：

| 面 | 事实 |
|---|---|
| 新库首启 | 启动日志出现三行（建组 / Base URL / 明文 key），库里 `groups=1`、`group_id` 指向它 |
| 管理员路由 | 抄日志里那把 key 打 `/v1/models` → **200**；不带 key / 假 key → **401** |
| 老库升级 | 重启前后 `admin_users=2` / `groups=1` / `gateway_keys=1` 三个计数全不变，启动日志无种子行 |
| 老库补组 | `POST /api/groups` 建组 → `POST …/keys/:id/reset` 拿新明文 → `PATCH /api/users/admin {groupId}` → 同一把 key 打 `/v1/models` → **200**（返回上游真实模型列表） |
| 坏入参 | `PATCH {groupId:'grp_不存在'}` → **400 INVALID_PARAM**，`details.field='groupId'`（不是 500） |
| 提权尝试 | `PATCH {groupId: G, role:'user', password:'…'}` → 200，而 `role` 仍是 `admin`、`scrypt` 散列逐字节不变、新口令登录 401 |
| 即时生效 | 改组后**同一个 cookie** 打 `/api/console/session` 立刻看到新 `groupId`，且 `/api/console/keys` 同时切到新组的 key |
| 界面 | 用户页「归属组」那一格是就地可编的下拉；选完当场变字、不整页刷新；读库确认 `admin_users.group_id` 同步 |

## 遗留（不粉饰）

1. **明文 key 会出现在启动日志里一次，这与 `bootstrapAdmin` 拒绝把口令打进日志的纪律矛盾。**
   `src/api/auth.ts` 那段注释写得很清楚：日志常被收集、转发、留存，
   把凭据打进去等于把它复制到一个生命周期不可控的地方。我仍然选了打这一行，
   因为两个凭据的**替代路径**不一样：管理员口令他能记得、能存密码管理器；
   网关 key 明文**没有任何其它路径**（§4 铁律：只在签发响应里出现一次），
   不写日志 = 那把 key 从此不可知 = 管理员还是用不了路由 = 本 ADR 要解决的故障原样保留。
   **缓解**：只在首次引导打一行、明确标注"仅此一次"、并写明"改 key 的办法是重置或删掉重建"。
2. **种子组不设配额**（`rpm` / `tpm` / `dailyQuota` 全 `NULL` = 不限）。
   这是"开箱即用"最省的解释，但它的代价与遗留 1 叠加：一个从日志里抄到 key 的人
   可以无限打。**所以本 ADR 明确不做另两件事**：不预置 `dailyQuota`
   （一个数字要由我替所有部署决定，而它是个政策不是默认值），
   也不给种子组任何豁免。管理员建站后**第一件该做的事**就是给这个组设配额。
3. **`管理组` 是字面量名字匹配**（`groups.name` 有 UNIQUE）。
   一个把自己的组改名成"管理组"的部署，会让下一次首启引导把它当成种子组而**跳过新建**
   （并打一行"已存在"）。本版不修：把判据从名字换成别的需要一列新 DDL，
   而这条边角的代价只是"少建一个组、并说了出来"。
4. **`displayName` 仍是"建号时可填、之后冻结"**（决策 2 表）。
5. **新建的种子组没有回填给老库**（决策 1 末段）。老库管理员必须自己 PATCH 一次 ——
   这是刻意的：宁可让他看到"我还没组"，也不要让服务在启动时替他决定配额。
6. **前端归属编辑没有自动化测试兜底**（`web/` 无 test script、无 runner，
   ADR-0034 遗留 7 同一条）。所以本版**必须手工验收**：
   起一个新库 → 从启动日志抄 key → 打一次 `/v1/models` → 在用户页把归属改成另一个组 →
   确认消费面立刻变了。
