# 3. 余额三级口径，且"未知"不得等于 0

- 状态：已接受
- 日期：2026-10-06
- 决策者：管家 · 管理后端（提案）、画师 · 前端（字段依赖）、PM（拍板）

## 背景与问题

上游供应商的余额接口极不统一：有的给了 `balance`，有的只给总量单位，有的**根本不提供余额接口**（对应需求文档里的"尽力查询 + 手动录入"）。同时 key 分两类：

- **balance 类**：有可查询/可录入的货币余额。
- **token-plan 类**：包月/套餐制，没有货币余额，只有套餐余量与到期日。

如果只做一个 `balance` 字段，会得到两个错误结论：

1. 查不到余额的 key 被当成 `0`，前端显示"没钱了"，运营误判。
2. 套餐 key 的货币余额恒为 0，把合计金额拉低，看起来像亏损。

## 决策

**三级口径 + 显式未知计数**：

- **三级**：单 key / 上游合计 / 全局合计。
- **合计只统计 balance 类 key**。全局合计 = 各上游合计之和。
- 聚合响应**必须**携带 `balanceUnknownKeyCount`（本层有多少 key 余额未知）。
  **未知 ≠ 0**，是独立维度，前端必须单独呈现，不得并进金额。
- token-plan 类**单列** `tokenPlanKeyCount`，附套餐余量与到期日，**不进货币合计**。

## 为什么用"显式计数字段"而不是让前端自己数

前端如果自己推断"多少个 key 余额未知"，就得自己复刻后端的口径规则（哪些算 balance 类、disabled 的算不算、cooldown 中的算不算）。规则一旦调整，前后端必然分叉。把口径钉在后端响应里，前端只做渲染，是唯一不会漂移的做法。

同时这也挡掉一类造假：余额数字必须带着"样本覆盖率"一起出现，孤立的一个金额数字在 UI 上不可呈现。

## 影响

- 正面：运营不会把"查不到"误读成"没钱"；套餐 key 与余额 key 分开看；口径集中在后端一处。
- 负面：响应结构更啰嗦；前端必须为 `balanceUnknownKeyCount > 0` 设计明确的呈现（不能静默省略）。
- 硬约束：聚合接口**不得**为了"好看"把未知 key 的余额补 0 后计入合计。任何这样的实现视为缺陷。
