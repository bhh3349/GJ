# ADR-0049：key 探活（「试调一次」）= 管理面直连上游的一次性诊断

- 状态：已接受（2026-11-03）
- 相关：ADR-0024（能力探测的计量隔离四条 —— 本 ADR 逐字继承）、ADR-0026（共享凭据选择器，
  本 ADR 明确**不**用于探活）、ADR-0048（`firstUsedAt`：「用过没有」由数据面记，探活答「现在能不能用」）、
  ADR-0010（`key_runtime` 是网关运行态，管理端只读）
- 契约：v1.24.0（§3 `POST /api/keys/:id/probe`；§15.3 变更条）

## 触发

业主：「在 KEY 管理增加一个功能，每个 key 加一个首次调用功能。」第一阶段拍板「两个都要，分两批」：
第一批 = 首次调用**时间列**（v1.23.0 / ADR-0048），第二批 = **试调一次按钮**（本 ADR）。

两者回答的是不同问题，不能互相顶替：`firstUsedAt` 说「它被用过没有、什么时候」；试调说「它**现在**
能不能用」。一把三天前被用过、今天已欠费的 key，前者为真、后者为假 —— 面板上必须两者都在。

## 决策

### 1. 管理面直连上游，不动 `src/gateway` / `ports.ts`

业主与路由者都确认了三个候选，取第三个：

| 方案 | 否决/采纳理由 |
|---|---|
| A. 复用网关 `chatCompletions` port | 否决：要么让探活进选路与健康记账（污染运行态），要么在冻结面上开一个"副作用关闭开关" —— 后者比不加更难维护 |
| B. 在 `ports.ts` 新增 probe 方法 | 否决：动冻结面；且仍要绕开 KeyPool 的健康/冷却副作用，问题没解决只是搬了位置 |
| **C. 管理面直连上游**（采纳） | 与 `POST /api/keys/:id/test-balance` 同族：管理面本来就有直连上游的出口（`fetchFor(egressId,'management')`） |

代价明确接受：探活**不经过我们的转发引擎**，所以它验证的是「上游认不认这把 key」，不是「引擎能不能用它」。
对业主的问题（新发的 key 能不能用）足够；要测引擎链路是另一个端点，届时另开 ADR。

### 2. 测的正是**这一把**：401 就是结论，绝不换把

能力探测（ADR-0024）用共享凭据选择器轮换 key，因为那测的是**模型**、换把能提高结论覆盖率。
探活相反：换把等于「用另一把 key 的成功证明这一把能用」，结论直接失真。所以：

- 凭据只经由 `decryptedKeyRefs`（SecretsResolver 的同一出口）取，不另开解密路径（AGENTS.md §4）；
- 单次出站，失败即结论。

### 3. 判据与数据面同口径

- 2xx + `success:false` 信封（§16.2，TierFlow 的 `rejected`）⇒ **fail**（`UPSTREAM_ERROR`）：数据面把它当失败，
  探活说 ok 就是自我矛盾；
- 401/403 ⇒ `AUTH_REJECTED`；402 或含 `quota` 的 429 ⇒ `QUOTA_EXHAUSTED`；其余 429 ⇒ `RATE_LIMITED`；
  400/404/422 ⇒ `MODEL_REJECTED`；5xx ⇒ `UPSTREAM_ERROR`；2xx 但无 `choices`/`data` ⇒ `EMPTY_RESPONSE`；
- 模型三段解析：`body.model`（须在白名单内，否则 400）→ 白名单第一条 → 都无则退化为 `/v1/models`
  （零 token）。**绝不硬编码默认模型**：猜错模型名的 4xx 会被读成「key 不可用」，这正是要防的假结论。

### 4. 计量隔离四条（逐字继承 ADR-0024，改代码前必读）

1. **零 `reportFailure` / `reportSuccess`**：探活不进引擎、不碰 `KeyRuntimeState`。特别是 `reportSuccess`
   会清 `autoDisabled` —— 一次手点把「401 风暴里被自动停用的死 key」探活复活，比不动更坏；
   探活是**纯观测**，健康态只由数据面写。
2. **零 `usage_logs`**：不是客户流量。
3. 出站走调用方注入的 `fetchImpl`（`fetchFor(egressId,'management')`），禁止裸 fetch。
4. 计量随动作走：只进响应 + 审计 `key.probe`。**审计是本次对 `test-balance`「绝不写库」的唯一偏离**，
   理由：这一动作真花上游 token / 真用额度，必须能查「谁、何时、哪把 key、结果如何」。
   审计 detail 只放 kind/model/结论/状态码/错码/耗时 —— **零 key 明文、零上游 body 原文**。

### 5. 频控与并发

- 同一把 key **10 秒一次**（6 次/分钟）：超限 `429 TOO_MANY_ATTEMPTS` + `details.retryAfterSeconds`
  —— **复用既有错误码，零新增枚举**；
- 进程内全局并发上限 **2**：管理员手点的保险，不是限流器（多实例各算各的）；
- 超时缺省 **12s**（`2000..15000` 可覆盖）：120s 的数据面默认对一次手点太长，10–15s 是路由者给的量级。

## 备选方案

- **每次探活顺便刷新 `balance` / `tokenPlan`** —— 否决：探活只证明「此刻一句 chat 能过」，
  不能推出余额数字；把推测写进库正是本项目反复否决的形状（ADR-0003 未知 ≠ 0）。
- **探活失败自动降权 / 进冷却** —— 否决：见决策 4.1。管理员点两下就能把好 key 踢出选路的形状，
  比"探活没结论"坏得多。
- **批量探活（一次测 N 把）** —— 本期不做：真打上游 × N 的额度消耗与失败噪声都不适合一个按钮，
  需要时另开 ADR（含预算、限速、任务化）。

## 后果

- 面板新增「试调」按钮：点击 → 同步返回结论（ok / 错码 / 耗时 / 上游文案），前端展示即可；
- 每次点击产生 1 条 `key.probe` 审计 + 1 次上游请求（chat 模式约 1 个 token 的成本）；
- 运行态零污染：`key_runtime`、`usage_logs`、`upstream_keys` 三张表都不因探活而变；
- 冻结面零改动：`src/gateway/`、`ports.ts` 一行未动。
