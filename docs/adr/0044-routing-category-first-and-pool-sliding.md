# ADR-0044：选路顺序语义修订 —— 类目第一、到期优先、单请求滑池

- 状态：**已接受（Accepted，2026-11-03）**——业主派单 B1/B2/C 三件事（见「触发」），Chief 核对通过并拍板两点
  （键序到期优先于 weight、`reserve=1`）。**契约 v1.20.0 落地前不写任何实现代码**；实现与本 ADR 同车道
  （`src/gateway/`），判据清单见「判据」。
- 编号说明：本条原以 0043 起草；`ADR-0043`（废号池 + 删账号强绑定，契约 v1.19.0）已先行合流，故本文顺延为
  **0044**，与 0043 **零交互**（那条只动 `src/db` + `src/api`）。契约版本相应为 **v1.20.0**。
- 关联：**ADR-0011**（排序四键与「返回顺序即优先级」，被本文修订）、**ADR-0030**（套餐优先追认，被本文修订：
  其保证此前隐含「weight 相同」前提）、**ADR-0041**（透支锁存——闸不动，交互登记）、**ADR-0021**（出口轴——零交互）、
  **ADR-0042**（`attemptTrail` 归因——语义不变，值分布变化）；
  契约 §3（Key 对象）/ §9（边界）/ §10（错误码，零新增）/ §16.3（key 映射与选路）/ §13.4（助手同源）；
  `docs/dev-constraints.md` §三.6（排序口径原文，需同批改）。
- 车道：`src/gateway/key-pool.ts`（排序键）、`src/gateway/engine.ts`（尝试预算）。`ports.ts` / `types.ts` **零改动**
  （排序是内部实现面，冻结面三函数签名不变）。
- 触发（业主原话摘要）：
  - **B1**：同一请求内，套餐类 key 失败后**要能继续尝试余额类 key**（总尝试上限仍受 `maxAttempts` 约束，分配方式由路由者设计）；
  - **B2**：**类目（套餐 vs 余额）成为第一排序键，weight 只在类内生效**（对 ADR-0030 的语义修订）；
  - **C**：套餐类内**快到期的 key 先烧**（`token_plan_expires_at` 升序、排在余量之前；无到期日的排已知到期之后，再往回 LRU）。

## 背景：现状与三件事的差距（只读核查，基线 e6499ab；`src/gateway` 与 `src/egress` 自 c01a837 至今 diff 为空）

1. **排序**（`key-pool.ts:212-225`）四键：`weight` 降序 `:213` → `remainingQuotaOf` 降序 `:214-216` →
   `lastFailureAt` 升序（30min 时效窗）`:217-219` → `lastUsedSeq` 升序 LRU `:220-222`，快照序兜底 `:224`。
   ADR-0030 的「套餐优先」是键2 的常量（`UNKNOWN_PLAN_QUOTA=1` `:125`；balance 恒 0 `:136`）——
   **只在 weight 相同时成立**：`weight=2` 的余额 key 排在所有套餐 key 前（`schema.ts:75` 默认 1，
   `repo/keys.ts:409-410` 可改，无告警）。
2. **单请求截断**（`engine.ts:202 DEFAULT_MAX_ATTEMPTS=3`、`:425 if (attempts >= maxAttempts) break;`）：
   候选里套餐 key 多于 3 把且逐把失败时，第 3 把失败即收尾 502，**本请求不滑到余额 key**；
   切池只在下一次请求的重排里发生。
3. **无池级概念**：只有逐把过滤（`isUsable` `key-pool.ts:139-159`：余量 0 `:158` / 到期 `:154-157` /
   `depleted` `:144` / 余额 ≤0 `:151`）与逐把冷却（`:254-262`）。「套餐池用光→切余额」是每次请求重排的涌现结果。

## 决策

### 1.（B2）类目是第一排序键，weight 降为类内键

`ready.sort` 比较器改为**七道键、六个生效维度**（最终序，Chief 拍板 ④）：

```
0. 类目升序：token-plan(0) 在前，balance(1) 在后          ← 新增（B2）
1. 到期升序（token_plan_expires_at；balance 类恒 null ⇒ 类内恒等跳过） ← 新增（C，拍板④置前）
2. weight 降序（只在类目内生效）                          ← 原键1 降位
3. remainingQuotaOf 降序（UNKNOWN_PLAN_QUOTA=1 原样）      ← 原键2
4. lastFailureAt 升序（30min 时效窗原样）                  ← 原键3
5. lastUsedSeq 升序 LRU                                   ← 原键4
6. 快照序兜底（纯防御）                                    ← 原键5
```

- **语义修订的成文**：ADR-0030 的「套餐 key 一律排在余额 key 之前」从「weight 相同时的排序结果」升级为
  **无条件不变式**。weight 从此**表达不了跨类目优先级**——这是本决策的目的（业主裁定），不是副作用；
  若将来真需要「某把余额 key 插队」，那是新的显式机制（如 per-key pin），本期不做、不预留。
- weight 仍在其**类目内**生效：余额类到期恒 null，键1 恒等 ⇒ weight 在余额类内直接起序；套餐类内则只在
  「到期相同或同为未知」时才有机会起序（见决策 2 的拍板理由）。
- 余额类内部仍由「weight → 失败时效 → LRU」轮转，ADR-0011 的验收 §九.1（每健康 key ≥10% 出量）不受影响；
  `rotation.spec.ts` A/B/C 回归面继续全绿。

### 2.（C）到期优先，且排在 weight 之前（Chief 拍板 ④）

- 键1：`token_plan_expires_at` 升序。解析一次缓存进比较（`Date.parse` 有限值取 epoch）；
  **`null` 与不可解析（NaN）一律视为 +∞ 排在已知到期之后**——与 `isUsable` 的到期判定（`:154-157`，
  NaN 不判过期）同向：「未知到期」≠「已过期」，只参与排序不参与过滤。
- **为什么排在 weight 之前**（拍板理由，逐字留档以免后人重排）：业主原话「优先使用快到期的账号 key」是
  **业务硬约束**（不用就作废，是实际损失），weight 只是管理员的**软偏好**；**显式管理员意图压自动策略**这条论据
  已在**类目**一层用掉（那是防跨类目插队），层内再用一次就过头——等于允许一次 weight 调整把整条到期策略压掉。
- **为什么排在余量之前**：余量还有 8M 但今晚过期的 key，等到余量排序起作用时额度已作废；到期是**时间硬约束**，
  余量是**消耗软约束**，硬约束先排。哨兵 `UNKNOWN_PLAN_QUOTA=1` 的两条约束（`>0`、`≤ 最小真实余量`）不受影响
  ——它仍在键3，语义不变。
- 被否的备选（保留记录）：*weight 在到期之前*——好处是管理员保留类内绝对干预手段、与 weight 既有语义（显式压自动）
  一致；代价是一次 weight 调整可整层压掉「快过期先烧」，且业主原话是业务硬约束不应被软偏好覆盖。**采用拍板④**。

### 3.（B1）单请求滑池：类目预留预算 + 未用预算滚入（Chief 拍板 ⑤：`reserve=1`）

引擎循环（`engine.ts:424`）改动最小化——**不动候选顺序、不动跳过逻辑、只加一道类目预算**：

```
reserve      = (存在余额类候选 且 maxAttempts ≥ 2) ? 1 : 0
planCap      = maxAttempts − reserve            // 套餐类本请求最多消耗的真实尝试数
planAttempts = 0                                // 只数套餐类的真实尝试
```

- 循环内，尝试**套餐类**候选前判 `planAttempts >= planCap` → 剩余套餐候选**整段跳过**（`skipped` 事件照发，
  不耗 attempts），继续走余额段；尝试余额类候选不受此帽约束。
- `attempts`（真实尝试总数）仍 ≤ `maxAttempts`；套餐段未用完的预算（`planCap - planAttempts`）**自然滚入**
  余额段（同一个 `attempts` 计数器，无需显式转移）。
- `reserve` 只保证「**至少一次**余额尝试」：`maxAttempts=3` 的最坏形状 = 2 次套餐失败 + 1 次余额尝试。
  **不预留更多**的理由：`maxAttempts` 是对外成本上限（§13.4 同源、env `MAX_ATTEMPTS`），预留 k>1 会把
  单请求最坏耗时翻 k 倍，而「至少试一次余额」已经兑现业主的「要能继续尝试」；再多属重试策略，不属选路。
- 边界逐条钉死：
  - `maxAttempts = 1`：`reserve=0`，行为与现状逐字节相同（一个预算塞不进两个类，诚实降级并在本 ADR 登记）。
  - **跳过不耗预算**：冷却/饱和/密文/死绑定的 `skipped` 不计入 `planAttempts`（现状 `attempts` 只数真实尝试，
    `engine.ts:481` 之前跳过——本决策沿用），全套餐候选被跳过时余额段拿到**全额**预算。
  - `crossUpstreamRetry=false` 原样生效：跨类目通常即跨上游，到边界照旧 `break`（不因为滑池绕过该开关）。
  - 出口轴零交互：`observeLimited` 归因出口的 429 仍即刻终态返回（`engine.ts:645-674`），滑池不改变它；
    预算拒绝的整池收口（`:577-589`）也原样。
  - ADR-0041 闸零交互：`depleted` 是 `isUsable` 过滤（进不了候选），与排序/预算无关。
  - 0 次真实尝试的分型（ADR-0011：429 饱和 / 503 密文 / 503 池空）判据 `attempts === 0` 原样成立。
- **被否的方案**：
  - *双类目独立满额预算*（套餐 3 + 余额 3）：突破 `maxAttempts` 总上限，最坏耗时与上游成本不可控；
  - *首次套餐失败立即滑池*：违背「先用套餐」——套餐段应有机会用它的其它 key（可能是前一把的偶发故障）；
  - *按剩余预算比例动态分配*：不可解释、不可测，两类语义相同的请求可能拿不同预算。

### 4. 契约 §16.3 可直接引用文本（逐字，勿两处措辞漂移）

> `getAvailableKeys` 的返回顺序即引擎尝试顺序，比较键依次为：**①类目**（套餐 key 一律排在余额 key 之前，
> 不可被其它键跨越）**②`tokenPlan.expiresAt` 升序**（快到期先烧；`null` 或不可解析 = 未知到期，排在所有已知到期之后，
> 仍参与选路、不被过滤）**③`weight` 降序**（仅在类目内生效，不可跨类目插队）**④剩余额度降序**（套餐类有值者优先，
> 未知额度按最小正值参与）**⑤最近失败时间升序**（30 分钟时效窗）**⑥最近使用序升序**（LRU），快照序兜底。
> 引擎按此序尝试，单请求**真实尝试总数 ≤ `maxAttempts`**；当候选中存在余额类 key 且 `maxAttempts ≥ 2` 时，
> 套餐类在本请求内最多消耗 `maxAttempts − 1` 次真实尝试，剩余预算（含未消耗部分）留给余额类；
> 被跳过（冷却 / 饱和 / 密文 / 死绑定）的候选不计入尝试数。`maxAttempts = 1` 时不预留，行为与本修订前一致。

## 判据（实现阶段执行，清单先钉）

`key-pool.spec.ts`（排序）：
1. `weight=2` 的余额 key 仍排在 `weight=1` 的套餐 key 之后（B2 正向）；
2. 套餐类内 `expires_at` 早者在前，**即使后者的 weight 更大**（C 压 weight，拍板④的正向判据）；
   `null` 与不可解析字符串排最后（仍可用、不被过滤）；
3. 同类目同到期（或同为未知）才回落 weight 降序，再回落剩余额度 → 失败时效 → LRU（链式兜底逐层验证）；
4. 余额类内到期恒 null ⇒ weight 在类内直接起序，其余轮转仍 LRU（ADR-0011 回归）。

`engine.spec.ts`（滑池）：
5. 5 把套餐 key 全失败 + 2 把余额 key，`maxAttempts=3`：attempts=3，trail = 2 套餐 + 1 余额（B1 正向）；
6. 1 把套餐失败 + 2 把余额：余额消耗 2 次（预算滚入）；
7. 套餐全被冷却跳过（0 真实尝试）：余额段拿满 3 次；
8. `maxAttempts=1`：无滑池，与现状逐字节同形（诚实降级用例）；
9. `crossUpstreamRetry=false` 且余额在上游 B：仍 break，不跨上游滑池；
10. 余额段也全失败 → 502 终态 `attemptTrail` 含两类、`keyId` = 最后摸过那把（ADR-0042 语义不变）。

**变异验证**（业主纪律，每条新用例先改坏实现看红再还原）：至少覆盖——删类目键（用例 1 红）、
键1/键2 对调（到期与 weight 换序，用例 2 红）、删 reserve（用例 5 红）、`reserve` 改成 2（用例 5 红）、
reserve 条件不看 `maxAttempts≥2`（用例 8 红）。

**门禁**：`pnpm typecheck` / `pnpm test` / `pnpm build` / `pnpm check:secrets` 四闸全绿（Node 22.23.4），
外加 `pnpm test:gateway` 单独跑一遍车道面。

## 已知边界（写清楚，不留待发现）

1. `maxAttempts=1` 时不滑池（预算不可分），诚实降级；运维要滑池就把 `MAX_ATTEMPTS` 配 ≥2。
2. 到期排序依赖回填质量：`token_plan_expires_at` 为 NULL（从未同步）的 key 排最后但仍可用；
   同步侧纪律（ADR-0030 决策 2 / 契约 v1.14.0 ⑤：两格任一未知整行跳过）不变。
3. 到期键置前后，**套餐类内 weight 的干预面收窄**：管理员给某把套餐 key 加 weight，压不过一把更早到期的同类 key。
   这是拍板④的直接后果；真要干预到期顺序，改同步侧/手工填 `expiresAt`，或用余额类（无到期键）。
4. 滑池不改变「单请求最多 3 次真实尝试」的成本上限；上游仍可能收到最多 3 次失败请求，其中可能出现
   「2 次套餐 + 1 次余额」的新分布——监控侧若按 key 类目拆错误率，分布会变，属预期。
5. weight 失去跨类目语义后，既有部署里若真有人配了 `weight=2` 的余额 key 并依赖插队，本版会**静默改变**
   其流量分布（这正是业主要的行为）；部署侧核对一次 key 列表的 weight 即可确认无此依赖。
