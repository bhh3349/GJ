# 25. 助手页错误汇总面板：复用观测面取数，`citations` 不加默认快照

- 状态：**已落（2026-10-14；Bo 要求 + 管家契约裁决）** —— 契约 **§13.6（v1.11.1）** 为本笔唯一文本产物，**零代码**（`src/api/` + `src/gateway/` + `src/db/` 一行未改）；消费侧由画师落前端。
- 日期：2026-10-14
- 决策者：Bo（「不是价格错误汇总。是日志的错误日志汇总表，这样方便和助手对话复制」）＋ 画师（取证与最小修法提案）＋ 管家（契约裁决与落笔）
- 关联：ADR-0013（§12 观测只读查询）、ADR-0015（§13 内置助手聊天）、ADR-0014（`x-request-id` 关联键）、契约 §12.1 / §12.2 / §12.3 / §13.1 / §13.2 / §13.3

## 背景与问题

Bo 要在助手页看到一张**错误日志汇总表**，动机是「方便和助手对话复制」—— 现在他想让助手解释某条错误，得自己开日志页翻、复制、粘贴进对话。

一句话根因（画师提出，管家复核为真）：助手页的观测取数**只有 §13.1 那份白名单参数**（`window` / `from` / `to` / `category` / `severity` / `model` / `requestId`），前端**从不上传任何错误事件行**；`done.citations` 又是 all-or-nothing（没选过滤条件就 `[]`，选了也只是截到 120 字符的短摘要）。所以这不是「UI 少画一块」，是**没有可复制的数据入口**。

## 取证（落笔前先实测，不采信转述）

1. **`observabilityApi.errors()` 零调用点**：全量 grep `web/src/` 只有 `web/src/api/endpoints.ts:212` 的定义处。画师订正的那句「仪表盘错误分型用的不是 §12.3」核实为真 ——
2. **仪表盘「错误分型」读的是 §12.2**：`web/src/pages/DashboardPage.tsx:172–176` 取 `health.data.events.byCategory`，不是 §12.3 那个错误事件端点。也就是说 §12.3 的列表端点**前端一次都没接过**，而
3. **§12.3 后端早已实现且活性实测 `200`**（2026-10-12 全模块扫）。

⇒ 缺的不是后端能力，是**消费侧**。因此本笔**零新端点**，也不该开新端点。

## 决策

1. **契约新增 §13.6「助手页错误汇总面板（数据口径）」** —— 性质是**前端消费口径登记**（不是新接口）。它进契约的理由只有一条：面板与对话共用 §12 / §13 同一份数据面，口径必须只有一处事实源。
2. **面板行 = §12.3 `GET /api/observability/errors` 的原样响应**，默认窗口（不传 `from`/`to` = 近 1h）、默认排序 `ts DESC, id DESC` 全部照该端点既有口径。前端**不得**换字段、重排行、自造聚合，也**不得**截 `message` 省地方（`summary` 那个 120 字符截断只有 `citations` 有权做）。
3. **顶部 9 分型计数条 = §12.2 `events.byCategory`**，**禁止**用面板那份分页响应现算计数 —— 分页只覆盖第 1 页，计数是全窗口，两个数不同口径。§12.2 那条「只列出现过的分型、不补 0」原样适用。
4. **点行注入 = §13.1 `logContext` 白名单字段的受控更新**（`category` / `severity` / `model` / `requestId` / `from` / `to`，字段名与取值域一字不改；事件 id 本身不是注入项；`model` 为 `null` 的行**不注入该字段**）。**禁止把行文本塞进 `messages`**：§13 头注纪律 3「日志隔离」明写助手取数只收结构化 DTO 过滤参数、**不接受自由文本查询**，行文本注入等于绕过白名单。非法取值仍走 `400 INVALID_PARAM`（解析层非法），与 §13.3 的 `truncated` 不混。
5. **裁定：`done.citations` 不加「进页即注入近 1h 快照」**（画师提的那条行为变更，答 `no`）。§13.2 语义一字不动 —— citations 仍是「本次实际注入了才有引用」。三条理由：
   - **量级**：自动快照每轮都注入观测事件，极易撞 §13.3「50 条 × ≤24h」上限 ⇒ `done.truncated` 常年 `true` ⇒ 那个「上下文已被截断」提示失去区分力，而它存在的意义正是「这一轮真的被截了」。
   - **价值**：Bo 的痛点是**可复制的错误行**，已由第 2 条的面板解决；自动快照不新增任何一行可复制的内容。
   - **成本**：每轮注入 = 每轮多一段日志进 prompt = 每次会话都付钱去买用户自己已经看得见的数据。
   要翻这个案走新 ADR，不在 §13.6 顺手改。
6. **全局视野靠点行注入，不靠自动快照**：要看「近 1h 错在哪几类」就点计数条（等价于手填 `logContext.category` 多值）。计数条是导航控件，**不是** `logContext` 字段。
7. **面板与计数条允许不同窗口**（`from`/`to` vs `window`），后端只负责各自回显（§12.3 `range` / §12.2 `window`），一致性判定归前端渲染层，**不新增字段**把两者绑成一个。

## 为什么不怎么做（被否掉的备选）

- **不开聚合端点**（如 `/api/observability/errors/summary`）：§12.2 的 `byCategory` 早已是那份聚合，再开一个必有第二份口径，两处漂移时面板与计数条会显示互相矛盾的数（同 v1.10.0「不新开端点」那条纪律）。
- **不做默认快照注入**：见决策 5 三条理由。
- **不用自由文本替代白名单**：把 `message` 原文拼进 prompt 看似「信息更全」，实际破的是**日志隔离**这条纪律，而且 `message` 是 scrub 之后的内部归因文案 —— 它的可读性不足以让助手答得更准，`category` + `requestId` 才是可定位的量。
- **不新增绑定两窗口的字段**：绑成一个会带来「面板窗口一变、计数条也得跟着重取」的隐性耦合，而 §12.2 的 `window` 枚举只有 `60s|5m|1h`，撑不住面板的任意 `from`/`to` 跨度。

## 影响

- 正面：「复制错误行去问助手」有了唯一数据入口；面板与计数条的口径差异写成硬规则（不再各猜各的）；**后端零待办**。
- 门禁：`ERROR_CODES` / `GATEWAY_ERROR_CODES` / `hintCode` **零新增**；`/v1/*` **零变更**；`SCHEMA_VERSION` **仍为 2**；**零 DDL、零迁移**；`src/api/` + `src/gateway/` + `src/db/` **零改动**。
- 边界（写在这里，不留待发现）：面板只能覆盖 §12.1 **产出边界**内的事件 —— 仅 `/v1/*` 产事件、上游 4xx 原样透传不产事件、未过鉴权的行 `model` 恒 `null`。所以**表里没有 ≠ 没出错**，前端空态文案要体现这条，但不得为此新增字段。另一条：§12.1 明写**三层口径不可互相替代**，本面板画的是「事件分型」那一层，**不得**在同一张表里混排 `usage_logs` 的状态码行。
- 责任方：**管家** = 契约 §13.6 + 本 ADR（本笔，纯 docs，已完成）；**画师** = 面板 + 点行注入 + 助手页 50/50 分栏（契约已定，可即刻动工）；**路由者** = 无（网关侧零改动）。
