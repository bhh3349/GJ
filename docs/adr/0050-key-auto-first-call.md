# ADR-0050：建 key 自动首调保活 —— 每个新 key 落库后立刻被真实调用一次

- 状态：已接受（2026-11-03）
- 相关：ADR-0049（探活实现 —— 本 ADR **整支复用** `probeKey`）、ADR-0048（`firstUsedAt` 口径隔离）、
  ADR-0021（管理面出站唯一出口 `fetchImpl`）、ADR-0017 / §15.5（账号级节流与「建 key = 2 次」的计数口径）
- 契约：v1.25.0（§3 `POST /api/keys` 行 + §3 新增「建 key 自动首调保活」小节；§15.2 `keys` / §15.13 `rotate-key` 同批生效）

## 触发

业主（2026-11-03，两次原话，第二次是因为第一次被理解成了"加个开关/标签"）：

> 「首次生成key的时候，需要每个key都要有一次调用，不然可能被封号，就一次就行。别整那么复杂。」
> 「关于调用，我再说一次，就是首次生成key的时候，需要每个key都要有一次调用……跟标签状态什么的没关系，
> 别把调用这个改到标签上面好吗？以前的显示套餐名称挺好的」

两句合起来给出三条硬约束：

1. **动的是创建动作本身，不是界面**：每个新 key 落库后要**真的打一次上游**；
2. **就一次**：不重试、不做重试队列、不做"多久没调用再补一次"这类后台策略；
3. **不许变成 UI 上的列或标签**：标签列照旧显示套餐名称（`套餐-轻享版`），调用状态不进任何标签。

业主的动机是**外部风险**：上游可能把"从未被调用过的新 key"当僵尸 key 处理（封号）。这件事发生在**上游侧**，
我们能控制的只有"落库即用一次"这一个动作 —— 所以它必须是**创建路径的一部分**，而不是管理员记得去点某个按钮。

## 决策

### 1. 三条建 key 路径全部覆盖，动作放在"落库之后"

| 路径 | 落点 | 说明 |
|---|---|---|
| `POST /api/keys`（手动建 key） | `src/api/routes/keys.ts`：`createKey` + `auditWrite('key.create')` 之后、`201` 之前**发起** | 只发起不等待，`201` 的时延不受影响 |
| `POST /api/supplier-accounts/keys`（账号池建 key） | `createKeysForAccount` 里每把 key `createKey` + `linkSupplierAccountKey` 之后 | 一批 N 把 = N 发，逐把一次 |
| `POST /api/supplier-accounts/rotate-key`（套餐 key 轮换） | `poolRotatedKey` 里 `createKey` + 台账挂链之后 | 轮换出的新 key 与新建等同 |

顺序是刻意的：**先落库、再调用**。反过来的话，一次上游失败会让"key 已经在上游扣了额度、池里却没有它"这种
最难对账的形状出现（§15.13 的「先落库、后失效」同一条纪律）。

### 2. 复用 `probeKey`，不新增实现、不新增端点

首调就是「试调一次」（ADR-0049）的**自动版**：同一套判据表、同一套模型解析、同一套超时与频控。
理由：两处实现必然会漂 —— 而"自动的这次"和"手点的这次"如果判据不同，面板上的结论就会互相打脸。

由此继承的四条计量隔离（ADR-0049 决策 4，逐字不改）：

- 零 `usage_logs`、零 `key_runtime`（不调 `reportFailure` / `reportSuccess`）、零 `upstream_keys` 写入；
- **不写 `firstUsedAt`** —— 它是**客户流量**的时刻（ADR-0048），管理面首调混进去会让「首次调用」这一列
  在"刚建完、还没被客户用过"的 key 上显示一个假时刻。业主也说过这件事跟标签状态无关，口径上同理。

### 3. fire-and-forget：不 await、不挡响应、不重试

`probeKeyOnce()` 返回 `void`，内部 `void probeKey(...).then(...).catch(...)`。三条理由：

1. **不挡建 key**：`201` / `202` 与任务的逐行进度都只反映"建没建成"，探活是事后观测；
2. **不重试**：业主"就一次"是字面意思。一次失败（上游 504 / 网络抖）就是一次失败，写进审计即可，
   补做只会让"到底调用了几次"变成一笔糊涂账；
3. **绝不抛**：这条链上的任何异常（解密失败、上游 4xx、**库已关**）都只落一条 `fail` 审计；
   写审计本身再失败就吞掉。后台动作把异常抛回进程，等于让一次建 key 变成一次随机崩溃。

### 4. 证据只落审计 `key.probe`，`detail` 前缀 `auto=1`

- 形状与手动探活**同形**：`kind=… model=… ok=0|1 status=… code=… Nms`，前面加 `auto=1`；
- **手动建 key** 记 `captureAuditActor(req, config)` = 真操作者 + IP；
- **账号池建 key / 轮换** 记 `actor=system`、`ip=-`：那两个动作发生在任务里，那一刻**没有请求对象**。
  写成人名会造出"某人探活了一把 key"的假记录；它属于哪一批，由同时间段那条
  `supplier.keys.create` / `supplier.rotate-key`（带着真 actor）对上；
- 没打出去（被 10s 频控挡下、解密失败）落 `code=SKIPPED` 的 `fail` 审计 —— **宁可有痕也不要无声**。

### 5. 10s 频控共享，不另开一条计数

自动首调也盖 `lastProbeAt` 时间戳，于是「刚建完立刻手点试调一次」会拿到 `429 TOO_MANY_ATTEMPTS`
（带 `details.retryAfterSeconds`）。这是**特性**：`retryAfter` 让前端把"等 10 秒"说清楚，
而不是允许同一把 key 在 2 秒内被烧两次。

### 6. 不做的事（全部显式登记）

- **不做 UI 呈现**：不加列、不加标签、不改标签列的套餐名称文案（业主点名的边界）；
- **不做后台"保活巡检"**（定时扫"从没被调用过的 key 再打一次"）：那是策略，业主只要求"建的时候调用一次"；
- **不做开关 / 环境变量**：一个"可以关掉"的保活等于把风险留在默认配置上；
- **不碰 `src/gateway/` 与 `ports.ts`**：首调走的是管理面出站缝，与数据面选路无关。

## 代价（明确接受）

1. **一轮建 N 把 key 就多 N 发出站请求**。与 §15.5「建 key = 2 次请求」**分列统计、不合并** ——
   那条说的是"拿到凭据要几个往返"，这条是"新 key 要被用一次"，两件事都会真实占用出口预算（§16.7 Tier 1.5）；
   要控量就少建几把，不是悄悄跳过保活。
2. **上游会看到"建完立刻用"这个形状**。理论上可能被上游的风控注意到；但相对于"僵尸 key 被封"，
   业主明确选了前者 —— 一次 `max_tokens=1`（或在无白名单时零 token 的 `/v1/models`）是最轻的一次调用。
3. **探测结论不影响任何状态**：自动首调失败不会禁用 key、不会写冷却、不会改余额 ——
   它只是让面板/审计上"这把 key 现在能不能用"有一个当时的事实。要不要处理由人看审计决定。

## 验证

- `src/api/services/key-probe.spec.ts`：`probeKeyOnce` 五条 —— ok 腿（零 `usage_logs`、`first_used_at` 仍 `null`、
  key 行一字不动）、fail 腿（401 → `code=AUTH_REJECTED`）、连不上（`UPSTREAM_UNREACHABLE`）、
  频控挡下（`code=SKIPPED` + 自动首调只出站一次）、**库已关不产生未接管 rejection**；
- `src/api/api.spec.ts`：`POST /api/keys` → `201` 后审计落一条 `auto=1`（`actor=admin`、出站正好一次打
  `/v1/models`、`first_used_at` 为 `null`、`usage_logs` 0），紧接着手点探活 → `429`；
- `src/api/routes/supplier-accounts-write.spec.ts` / `-tokenrhythm.spec.ts`：管理面路径判据按**路径**过滤
  （首调走的是数据面 `/v1/*`，不是驱动器路径），驱动器"不许打数据面"这条断言仍成立。
