# 20. 出口级（IP 级）限流：归因从 key 上移到出口，冷却期内不换 key

- 状态：**生效（归因纪律与处置方向）**；Tier 2（出口 IP 池）**未拍**，待 Bo 定代理资源
  （2026-10-07，契约 v1.4.4 补遗；`docs/api-contract.md` §16.4 / §16.7 / §15.5）
  ——— **v1.6.2 补记：决策 4 的第 2 样输入（原始响应）已实测到手**，见文末「补记 v1.6.2」
- 日期：2026-10-07
- 决策者：管家 · 管理后端（契约与归因口径）；路由者（`src/gateway/` 实现面）
- 关联：ADR-0011（0 次真实尝试不计 key 健康 —— 本 ADR 用的是同一把刀）/ ADR-0018（TierFlow 账号面：同一 host、27 个账号）/ ADR-0019（`model_limits` 白名单）
- 触发：Bo 2026-10-07 报回上游返回 `Error: too many requests from your client ip`

## 背景与问题

上游按**来源 IP** 计数限流。而 TierFlow 的部署形态是「**1 个出口 IP** + 27 个账号 + 全部 key」，
所以这条限制**不落在任何单把 key 上，落在整个池共同的出口上**。

§16.4 当时只写了两层（上游级 / 账号级熔断），没有这一层。而当前实现里，
**它会被当成一把 key 的失败来处理，并由轮换把它放大成全池故障**。

### 逐环取证（读的是当前 `main`，不是推测）

| 环 | 位置 | 行为 |
|---|---|---|
| 1 | `src/gateway/classify.ts:18` | `429 → 'RATE_LIMITED'`。**纯状态码驱动**，不看 body —— IP 级与 key 级在这一步就不可能被分开 |
| 2 | `src/gateway/engine.ts:399` | `pool.reportFailure(candidate.keyId, 'RATE_LIMITED', {retryAfterMs})` —— 记在**当时正在打的那把 key** 的账上 |
| 3 | `src/gateway/cooldown.ts:56` | 无 `Retry-After` → **60s** 起步；连续失败按阶梯 1m → 5m → 15m → **30m** |
| 4 | `src/gateway/key-pool.ts:30` | 池的对外面只有 `reportFailure(keyId, reason)` —— **没有上游级 / 出口级状态**，`upstreamId` 只用于候选列举 |

于是的连锁：

```
IP 级 429  →  key₁ 被冷 60s  →  引擎换 key₂ 重试
                                   ↑ 出口 IP 没变
           →  key₂ 也被 429    →  key₂ 被冷 60s  →  换 key₃ …（同一个客户端请求内）
           →  候选被逐把冷光    →  后续请求 503 NO_AVAILABLE_KEY
           →  重回候选的 key 再撞一次，consecutiveFails 升档  →  最长 30min 全池不可用
```

**根因不是"上游限流了"，是「换 key 能救」这个前提在 IP 级限流下不成立，而引擎照换不误。**
上游给的是"慢一点"，我们回敬的是"把 27 把 key 全打一遍"—— 这个形状本身也在**加重**风控判断。

## 决策 1：定性为**第三层**限流，单列一节（§16.7），不并进 §16.4

§16.4 的两层是「上游级（共用 host）」「账号级（单个账号被风控）」，处置方向是**换 key / 冷却该账号名下的 key**。
出口级**方向相反**：换 key 无意义（同出口），要冷却的是出口本身。
把方向相反的两件事写在同一节里，实现时最容易顺手沿用旧的处置路径 —— 那正是这次的故障形状。
故单列 §16.7，并在 §16.4 末尾留一句反向指引。

## 决策 2：IP 级 429 **不计入任何 key 的健康计数**

判据是**归因**，不是"谁撞上的"。这与 ADR-0011 里「0 次真实尝试不计 key 健康」是同一条纪律的延伸：

> **谁没错，不给谁记过。**

错记的代价不是"数字难看"，而是**这个数字会驱动行为** —— 冷却是自动的，
于是"记错账"直接变成"把好 key 停掉"，再由轮换放大到全池（见上）。

## 决策 3：冷却对象**由 key 上移到出口**，且**冷却期内不换 key**

- 本期"出口" = `upstream.host`。同出口下的 key **共用一道冷却**。
- 冷却期内引擎**不做换 key 重试**，径直回客户端 `429 RATE_LIMITED` + `Retry-After`。
  理由：同 IP 轮换必然再撞，**轮换在这里不是容错，是放大器**。
- 对客户端的对外口径**零变更**：仍是 §10 既有 `429 RATE_LIMITED` + `Retry-After`。
  **不新增错误码、不新增 HTTP 状态** —— 出口被限流与"池饱和"在调用方那侧同形（都是"退避后可重试"），这个同形是对的。
- 缺口明写：`429` 在管理面事件流里目前无法区分"出口被限流"与"key 自己撞限流"。
  **本期不动事件口径**（要动就得动 `failureReason` 枚举与 §12.1 分型，那是另一笔），
  先靠 `message` 与出口级冷却的时长特征在值班侧人肉分辨。

## 决策 4：**识别规则不写死** —— 只有一句 message 文本，按悬空件登记

现在手上只有 Bo 转述的一句 `too many requests from your client ip`。
凭一句话去实现"文案匹配"是这类改动里最容易埋雷的做法（文案会变、会被本地化、会随上游版本漂）。
因此：**识别规则留空**，按 §16.1.1 同款悬空件登记，需要的输入是三样 ——

1. 报错的**来源**（工作台 / 本仓网关 / 别的脚本）—— 决定它是历史遗留还是现网在流；
2. **原始响应**：状态码 + 完整响应体 + 响应头（尤其 `Retry-After`）；
3. **退避多久恢复**：能自愈 = 限速窗口（Tier 1 可治）；长时间不恢复 = 封 IP（**必须** Tier 2）。

补到 (2) 后分两种世界落地：**(a) 与普通 429 同形** → 走 §16.2 同款 pre-first-chunk 识别窗口；
**(b) 上游给了专用码/字段** → 直接按码判，**不解析文案**。

> **v1.6.2 便读提示**：本决策首段「现在手上只有 Bo 转述的一句」**已过期** —— 第 2 样输入实测到手，
> 且 **(a)(b) 两条路都不通，只剩 (c)**。理由与推论见文末「补记 v1.6.2」，**裁定 ① 不变**。

**v1.4.8 裁定（补记）**：路由者据本决策实现时留了识别缝（`EgressLimitDetector`，
默认 `neverEgressLimited` 恒 `false`），并报回第三条可选路径。裁定：**本期三条都不启用** ——
默认关闭**是对的**，但必须说穿它的后果：

> **识别器默认关闭期间，Tier 1 是"缝"，不是"修"。** 运行时行为与改动前**逐字节相同**，
> "IP 级 429 被轮换放大成 30min 全池故障"这条**自伤回路还没有被掐断**。

新增登记第三世界 **(c) 纯自证据**：同一出口上**第 2 把不同 key 也 429** 即判出口级
（实现即 `egressLimitedOnSecondKey`）。它**不需要上游吐原始响应**；代价一并记下 ——
**确认之前的第一把 key 仍会被按 key 级记过**（受害者 27→1，不是零成本）。
启用条件二选一：**(i)** Bo 的原始响应到手 → 按 (a)/(b) 落地（有专用码则 (b) 优先）；
**(ii)** PM / Bo **明示放行** (c) 作过渡。**在此之前识别器保持默认关闭**，
且不得据此宣称"自伤回路已掐断"。

## 决策 5：处置分三档，按证据与资源分级推进

| 档 | 内容 | 依赖 | 车道 |
|---|---|---|---|
| **Tier 1** | 识别后**不调 `reportFailure(keyId)`**；改落**出口级短冷却**（= **`max(Retry-After, 60s)`**，无该头则 60s 起、封顶 30min）；冷却期内不换 key | 只需 (1)(2) 两项证据 | 路由者 |
| **Tier 1.5** | **出口级令牌桶**：所有发往同一出口的请求（刷新 / 建 key / 重登 / 探活 / 数据面）共用一条速率 | 需 (3) 的实测退避时长 | 路由者 + 管家 |
| **Tier 2** | **出口 IP 池**：账号分组绑不同出口，把"27 账号 = 1 个 IP"拆成"N 个 IP" | 需 Bo 拍**代理资源** | 管家 |

**Tier 2 已进 DDL、DTO 未动**（v1.4.8 订正旧文"未拍"）：新表 `egress_proxies` + `supplier_accounts.egress_id`
（**可空**，缺省 `null` = 用宿主出口）已落在 `src/db/schema.ts`，**纯加表 + 加列**。
三条绑定纪律：**绑定粒度 = 账号级非 key 级**（27 个账号本就是 27 个风控指纹，key 挂在账号下自然继承）、
**每出口账号数上限 = 6（占位，待标定回填）**、**`egress_id` 不进任何 DTO**。

**Tier 1 的冷却地板**（v1.4.8 裁定）：把「尊重 `Retry-After`」读作「**不短于**它」，
即 **出口冷却 = `max(Retry-After, 60s)`**。本节此前只写"尊重"没写地板，是**契约漏写、不是实现偏差** ——
路由者 `egress.ts` 复用 `cooldown.ts` 的 RATE_LIMITED 口径**保持不动**。
取舍：地板会在上游给短退避时**多冷一段**（`Retry-After: 45` → 仍冷 60s），代价是可用性、
收益是不给"上游吐个小值就秒回"留缝 —— 安全侧，且不发明第二套算法。

> **v1.6.2 订正这句取舍的前提**：实测下上游**从不发** `Retry-After`，
> 所以「会给短退避」这个前提**当前不成立** —— 式子**永远取右边**，实际就是 **60s 固定起步**。
> **值不改、实现不改**（`max()` 保留：该分支是"上游哪天开始发就自动生效"的兼容路径，
> 删它收益为零），**订正的是理由**：从「**尊重**上游的退避」改为「**上游什么都不给**」。

## 决策 6：§15.5「0.6s 未触发限流」那条依据**降级**（值不变）

§15.5 原写：`账号间间隔 0.6s —— 工作台 29 号跑下来未触发限流`。
这条**只在"单出口 + 当时那种请求密度"下成立**。IP 级限流已被触发过，说明**条件变了，或它本来就是侥幸**。

**值为 0.6s 不改**（无新数据前不拍脑袋换数），但它的**依据**从"实测未触发"降级为
"**待 Tier 1.5 按出口级口径重新标定**"。关键区分：0.6s 是**每账号**礼貌间隔，
对**按 IP 计数**的限流**不成立** —— 27 个账号各自守 0.6s，出口侧照样可以超速。

## 决策 7：出口冷却的**唯一读面**是 §7 新增帧 `egress_cooldown`，**不新增 HTTP 端点**

决策 3 把冷却对象上移到出口之后，出口状态对运营是**看不见的** —— 而"看不见"在这里有实际代价：
出口被限流与"池饱和"对调用方**同形**（都是 `429 RATE_LIMITED`），前端若从 429 / `Retry-After` / 日志反推，
**必然猜错**，然后把它渲染成"某些 key 坏了" —— 正是本 ADR 要消灭的那个误读。

因此新增一条实时帧 `egress_cooldown { serverTime, egressId, cooldownUntil }`：

- **只走已存在的 `WS /api/stats/live`**：不新增 HTTP 端点、§14 端点侧不加字段。
  出口状态是**秒级瞬态**，给它开一个 REST 端点等于让它天生滞后。
- **`egressId` 定为不透明字符串**：本期取值 = 出口 host（归一为小写、含非默认端口），
  Tier 2 落地后 = `egress_proxies.id`。前端只当 Map 的键、**不解析内容** ——
  这样 Tier 2 换的是**值**不是**形状**，前端零改造。
- **`cooldownUntil` 是 ISO8601 时间戳**，与 `key_health.cooldownUntil` 同名同形；
  解除时推同一帧、`cooldownUntil: null`；差分指纹必须带它（冷却会**自然到期**，那一刻没有任何写入动作）。
- **投递语义 = 每 tick 差分帧，不是纯事件推**（v1.4.10 收口）：v1.4.8 写的「开始 / 变更 / 解除时
  **立即**推」是从 `key_health` 抄的，而本决策第一条已经关掉了 REST 兜底 ⇒ 纯事件推会让
  **刷新 / 重连拿不到"此刻正在冷却"**，把「全部 key 暂停路由」渲染成正常（最长 30min），
  且反推被明令禁止、前端**无合规自纠手段**。故与 `key_health` 同列：`id: egress:${egressId}`、
  `sig` 必带 `cooldownUntil`、新连接 `seen` 为空 ⇒ **首 tick 全量**。代价：最多晚 1 tick（1s）可见。
  （同批订正一条证据：`key_health` 的基线来自它自己的差分帧首 tick，**不是** `metrics` 帧 ——
  `live.ts` 的 `metrics` 帧不带 `keyHealth[]`。）
- **零新增错误码、零新增 HTTP 状态。**
- **无 `reason` 字段**（v1.5.0 删；本决策首版曾含它）：`EgressCooldown` 只有**一个**变更入口
  `cool(host, retryAfterMs?)`，其 `reason` **硬编码 `RATE_LIMITED`**，表内（`EgressState = {consecutive, until}`）
  **不存它** ⇒ 在本帧里它是**常量、不是状态**。**常量字段比没有字段更贵** —— 前端会照它写一个恒真分支，
  而它携带的信息量为零。且该帧**从未发射过、零消费者**（三个自检信号全 0），**删除此刻是免费的**。
  将来若真出现第二种出口级冷却成因，**同批把字段与生产者一起加回**（**禁止先加字段、后补生产者**）。
- **生产者读面 = 全量 + 绝对 `until`**（v1.5.0 放行）：放行一次**纯增量只读**
  `snapshot(): readonly { host: string; untilMs: number }[]`（**签名只增不改**，`KeyPool` / `KeyConfig` /
  engine 零改动）。它是**已冻结语义的缺件**，不是新功能：本决策上一条钉了「`sig` 必带 `cooldownUntil`」，
  却没查过生产者供不供得出 —— `egress.ts` 原只有 `isCooling(host)` / `remainingMs(host)`（**都要先知道 host**）、
  **无枚举读、无 `until` 读口**。两条语义：**(a)** `untilMs` 是**绝对时刻**，发帧侧**不得** `now() + remainingMs()`
  反算（否则指纹每 tick 变 ⇒ **每 tick 白推**）；**(b)** 快照是**全量**（该层记录过的全部出口），
  **不是"只在冷却期内的"** —— 差分通道**无墓碑**（id 消失只从 `seen` 删、不发帧），只报冷却中的话
  **解除帧永不发出**。推论：冷却层**不得 prune 已过期条目**（要 prune 得先加墓碑，另一笔）。

**命名说明**：PM 的派单里写作 `egressCooldown` / `until`，本决策按本契约 §7 的既有口径
归一为 **`egress_cooldown` / `cooldownUntil`**（帧类型名一律 snake_case；时间戳字段与 `key_health` 同名 ——
同一个概念在这条通道里只留一个名字）。

## 补记 v1.6.2：决策 4 的第 2 样输入（原始响应）**实测到手**，且它**本来就不该卡凭据**

（2026-10-07，路由者零凭据探针，群内报告；正文落点见契约 §16.7「v1.6.2 实测登记」与 §16.1.1.a）

本 ADR 至此第一次拿到**实测**而非转述。决策 4 登记的三样输入里，第 2 样（原始响应）一直挂着 ——
而它**不需要 key 就能触发**（出口级限流按 IP 计数，不看 key）。**它从来就不该挂在"等凭据"上。**
这条本身是方法教训，值得单独记一行：**"卡凭据"要按观察对象分，不能按"探针整体是否需要 key"一刀切** ——
否则一条**零成本就能消掉**的未知，会跟着另一条真卡凭据的未知一起停摆（§16.1 判据表那两支同理）。

三条实测与各自的影响：

1. **形状**：OpenAI 信封 `{error:{code,message,type}}`、`code: rate_limit_exceeded`、
   响应头**不含 `Retry-After`**（全部响应头见契约 §16.7）。
   → **决策 5 的冷却地板式子在实测下永远取右边**：`max(Retry-After, 60s)` 实际就是 **60s 固定**。
   **值不改、实现不改**（路由者 `egress.ts` 保持不动）；**订正的是决策 5 末段给的理由** ——
   从「**尊重**上游的退避」改为「**上游什么都不给**」。
   并写明**不得**据此把 `max()` 简化成裸常量：它是"上游哪天开始发该头就自动生效"的兼容路径，
   **删它的收益是零，代价是未来的一次静默降级**。
2. **触发 ≈8 次 / 自愈 1–2 分钟** → Tier 1.5 **拿到触发证据，仍没拿到数值**：**窗口长度未测**，
   速率仍是占位；能写进结论的只有「出口级可持续速率**远低于**每账号 0.6s（27 账号 ≈ 45 req/s）」——
   **决策 6 的降级因此从"可能是侥幸"变成"有实据"**。
   > **一处别读错**：约 1–2 分钟自愈 ≈ 我们拍的 60s 地板，看着"正好"。这是**巧合性一致，不是标定结果** ——
   > 上游没给退避值，60s 是我们自己定的。**不得把它读成"上游要求冷 60s"**，
   > 否则下一次有人看到自愈只花 40s，就会以为实现错了。
3. **无专用码 / 无专用字段** → 决策 4 的**世界 (b) 由实测排除**；(a) 退化为"只能解析文案"，
   而文案解析被本 ADR 自己禁止 ⇒ **(a)(b) 两条路都不通**。
   但「key 级 429 同码」**从未观测**（需带 key 往返）⇒「按码分不开两个世界」**是推断、不是结论**，
   与 §16.1.1.a 的旁证同级：登记，不据此改判。
   **裁定 ①（本期不启用、默认关闭）不变**，只把理由从「**没有证据**」改成「**有证据，且证据指向 (c)**」——
   于是待办变明确了：**(c) 不再是"没证据时的过渡方案"，而是证据指向的那条路**；
   但**启用仍需 (i)/(ii) 之一明文放行，本批不放行**。

**新增未证实风险（登记，不动手）**：畸形 `sk-` → **403 `routing_override_forbidden`**，而 403 落 `AUTH_INVALID`。
**若一把有效 key 在某种写错的客户端参数下也能拿到它，一个调用方的低级错误会把整池 key 烘掉。**
这与决策 2 是同一把刀（**谁没错，不给谁记过**）的另一个切面，但**证据不足以判断**：
**不据此改 `classify`、不据此动冷却**，等带 key 往返。

## 决策 8：出口池心跳生产者的状态机参数（v1.7.1 补遗，随接线笔落盘）

（2026-10-09 落盘；生产者本体先行提交（`c113b1a`，`src/egress/heartbeat.ts`）并引用本节 —— 本节就是它等的那份"冻结依据"。PM 代路由者落盘，Bo 既有技术授权，一句话可推翻。）

§7 `egress_pool` 帧的 `status` / `exitIp` / `lastHeartbeatAt` 三条冻结字段需要一个生产者（v1.6.4 那句「生产者不存在」由此关闭）。本节冻结它的**状态机参数与证据语义**：

1. **节奏三参数（保守起步值，标定输入到了只改数、不改结构）**：心跳 **30s** 一拍（`HEARTBEAT_INTERVAL_MS`，契约 §7 的 30s）；连续 **3** 次失败摘除（`HEARTBEAT_EVICT_AFTER_FAILURES`）；摘除后 **5min 滞回**回池（`HEARTBEAT_REJOIN_HYSTERESIS_MS`，滞回期内的成功**不回池**、但记 IP，也不推翻失败计数）。
2. **冷启动 = `online` + `null`**（exitIp / lastHeartbeatAt 皆 null）。摘除/回池是**内存态、不落库**（ADR-0021 决策 9(4)）：重启回到冷启动是**契约内行为**，不是 bug；写进 `egress_proxies.status` 才会造出第二套健康语义。
3. **`status` 只由证据翻转，不做新鲜度推断**。契约 §7 禁前端按 `lastHeartbeatAt` 新鲜度算健康；同一把刀对生产者成立：心跳断供、进程停摆、收件箱断写都**不**翻转状态 —— 停摆时该看到的是 `lastHeartbeatAt` 变旧，**不是**状态翻转。`lastHeartbeatAt` = 最近一次**真证据**的绝对时刻（ISO8601 UTC）；**失败证据照记**（心跳到了，只是报告坏消息），连败 +1。
4. **本地合成拒绝 = 零证据**（决策 4a 同源）：入口 B 探活走 `fetchFor(egressId,'management')`，"预算耗尽 / 正在冷却"会以**合成 429** 回来 —— 那是我们自己拒的，不是对面挂了。判据唯一处 `isLocalEgressReject()`（字面量归 `src/egress/port.ts`），被拒**不计连败、不进帧**，只在内存计数供验收。缺了这条，一次人工全量刷新就能把整池出口摘除（ADR-0011 §4 修掉的错误同形）。
5. **两个证据入口、一台状态机**（`applyEvidence` 唯一入口）：
   **A 文件收件箱**（默认、推荐；`EGRESS_HEARTBEAT_INBOX_DIR` 配了才开）：VPS 侧 `pool-probe.sh --json` 由 systemd timer 定时写入，生产者每拍取「最新且未吃过的那份」（内容 SHA-256 记账防重吃）—— **0 次上游请求**，不占 TierFlow 配额；证据时刻取文档 `checkedAt`（VPS 真跑的那一刻），不是网关读到它的时刻 —— 收件箱天然滞后，用读取时刻会把传输延迟抹平成 0。
   **B 进程内探活**（默认关）：接线传 `probe: true` 才开。代价写死：它吃 `management` 预算（capacity 5/60s − reserveForData 1 = 4 枚），两节点按 30s 一拍就是 4 枚/60s，会把 /test 与余额刷新的额度吃干 —— **开启要另有一笔明确决策**。
   同一拍 **A 优先**：A 已给证据的节点不再跑 B（一份证据 = 一次采样，叠加会把「连续 3 次失败」变成「连续 3 拍 6 个样本」，节奏口径当场失真）。
6. **导出面（七字段终局名，别改名）**：`startHeartbeatProducer` / `HeartbeatProducer.{setIntervalMs|tick|poolSnapshot|stop}` / `EgressPoolNode`（`egressId|name|status|exitIp|expectedExitIp|lastHeartbeatAt|cooldownUntil`，与契约 §7 字段表逐字对应）。`poolSnapshot()` **同步、无副作用**；`cooldownUntil` 从 `EgressGate.cooldownUntil()` **现取**（探活态与上游限流态各有唯一事实源，两种不可用并列展示、不互相盖掉）。`stop()` 是同步清定时器形状，适配 `ShutdownTarget.stops?`。
7. **落位与依赖**：`src/egress/heartbeat.ts`，**不 import `src/db`**（AGENTS.md §8）—— 节点清单由接线层（`src/server.ts`）注入，「读哪张表」留在装配层；也不 import `src/api` / `src/gateway`（同 §8 反向依赖禁令）。
